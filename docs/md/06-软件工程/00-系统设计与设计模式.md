### 2.1 系统设计通用方法论（4 步法）

```
1. 需求澄清（Clarify）
   - 功能需求（核心功能）
   - 非功能需求（QPS / 存储 / 可用性 / 一致性）
   - 边界场景

2. 估算（Estimate）
   - QPS / DAU 推算
   - 存储量
   - 带宽

3. 设计（Design）
   - High-Level：画架构图（Client / API / Service / DB）
   - Data Model：核心表结构
   - API Design：RESTful 接口
   - 关键流程：读流程 / 写流程

4. 深入（Deep Dive）
   - 单点故障 → 多副本
   - 性能瓶颈 → 缓存 / 异步 / 分片
   - 数据一致性 → CAP / BASE / 共识算法
```

### 2.2 经典案例速记

#### TinyURL（短链系统）
- **生成方案**：Hash(id) / 自增 ID + Base62
- **写流程**：长链 → ID → 短码 → 写 DB + 缓存
- **读流程**：短码 → 查 DB → 302 跳转
- **关键**：Hash 冲突处理、缓存预热

#### News Feed（信息流）
- **推模型（Fanout on Write）**：发消息时写入所有粉丝收件箱
- **拉模型（Fanout on Read）**：读时聚合关注列表
- **混合**：明星用推，普通用户用拉
- **关键**：分页策略、热点用户限流

#### 限流（RateLimiter）
- **固定窗口**：简单但有突刺问题
- **滑动窗口**：更平滑
- **令牌桶**：允许突发流量
- **漏桶**：强制匀速

### 2.3 导出一致性：分批查询 vs 并发写

**问题本质**：分批导出时每一批都是独立事务、独立快照，最终文件是多个时刻数据的"时间拼接"。并发写造成四类破坏：

| 破坏类型 | 场景 | 后果 |
|---|---|---|
| 重复行 | 行被 UPDATE 后满足查询条件且排序位置落在已扫过的前段 | 同一行出现两次 |
| 丢行 | 已扫区间的行改后不再满足条件，或前面的行"挤后"了后面的行 | 部分行永远查不到 |
| 幻影新数据 | 导出过程中 INSERT 的新数据 | 可能混进一部分 |
| 新旧值混杂 | 同一行不同字段读到不同时刻的值 | 数据自相矛盾 |

> 即使没有并发写，`LIMIT offset, n` 深分页在无稳定排序键时本身也会重复/丢失，需要 keyset 分页（`WHERE id > lastId ORDER BY id LIMIT n`）。

**第一步是定契约，不是选技术**：导出数据代表哪个时刻？三种契约：

| 契约 | 含义 | 业务典型 |
|---|---|---|
| 导出发起时刻的快照 | 文件 = 用户点按钮瞬间的数据 | 财务对账、审计（最常见） |
| 导出完成时刻的最新数据 | 允许包含过程中的变更 | 运营粗看 |
| 时间锚点过滤 | 只导"锚点前已存在"的数据 | 日志、流水类 |

契约要显式化：任务表记录 `snapshot_time`，文件水印标注数据截至时间。

**数据层解法（由轻到重）**：

| 方案 | 机制 | 约束 |
|---|---|---|
| 单事务一致性快照 | InnoDB RR 级别下 `START TRANSACTION WITH CONSISTENT SNAPSHOT`，事务内所有分批查询共享同一 ReadView | 长事务：undo 无法清理、history list 膨胀，只适合分钟级导出 |
| 单次游标流式读 | `fetchSize` 流式（MyBatis Cursor / JDBC `useCursorFetch`），一次查询分批传输 = 天然单快照 | 中小数据量首选，同时解决一致性 + 内存 |
| 两段式 ID 锚定 | 先一次查询冻结 ID 清单（`created_at <= :anchorTime`），再按 `id IN` 分批取内容 | 集合不重不漏；字段值仍是最新，严格快照需配 `updated_at <= :anchorTime` |
| 影子快照表 | 先物化 `INSERT INTO snapshot_xxx SELECT ...`，再对静态表分页读 | 适合反复读，代价是存储 + 一次全量 INSERT |

**架构层解法（实际项目主答案）**：导出这类重负载长任务的真正问题是**和在线交易抢同一个数据源**。

- **异步任务化**：导出走 export_task 表 + MQ + OSS 下载链接，不做同步接口（即 Outbox + 幂等消费 + SXSSF 那条链路）；
- **读路径隔离**：导出走从库 / 专用只读实例 / OLAP（ClickHouse/Doris），把长查询、大批量 IO 从主库摘掉；代价是从库延迟导致快照时刻偏移，绝大多数场景可接受；
- **T+1 数仓快照**：ETL 物化不可变快照，数据不可变就没有竞态，财务/审计级解法；
- **跨服务聚合**：单库快照失效，弱一致用各源带时间锚点并行查 + 标注快照时间，强一致走 CDC/Event Sourcing 统一物化，或业务侧账期冻结（金融月结锁单）。

**按规模选型**：

| 场景 | 推荐组合 |
|---|---|
| 十万行以内、单库 | 单事务快照 / 游标流式读 + SXSSF |
| 百万行、高频导出 | 异步任务 + 从库 + 两段式锚定 ID + keyset 分页 + SXSSF |
| 千万行/报表级 | 数仓/OLAP 物化快照 |
| 金融审计级 | 账期冻结 / T+1 不可变快照 |

> 💡 补充：核心记忆点--一致性先是业务契约再是技术问题；"单事务 + RR"和"单次游标流式读"是免费的快照方案但受长事务约束；ID 锚定把"集合一致"与"值一致"解耦；架构正解是读写分离 + 异步任务化，让导出离开 OLTP 库。与「消息队列」文档 6.6 Outbox 可靠投递配套阅读，构成大数据量导出的完整可靠性骨架。
