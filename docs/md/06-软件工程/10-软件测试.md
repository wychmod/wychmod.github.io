## 一、核心主题概述

软件测试是验证程序正确性、发现缺陷、评估质量并为发布决策提供依据的系统工程。本文围绕**测试基础理论**、**用例设计与执行**、**白盒与自动化进阶**、**全链路质量体系建设**、**JaCoCo 代码覆盖率**、**Chrome 插件与浏览器提效**六个维度，对归档笔记进行结构化整理。

## 二、测试基础

### 2.1 软件与测试的本质

> 📚 完整资料：[测试基础/软件测试基础知识.md](../archive/old-testing-notes/测试基础/软件测试基础知识.md)

- **测试定义**：在规定的条件下对程序进行操作，以发现程序错误、衡量软件质量，并对其是否能满足设计要求进行评估的过程。
- **软件十大特性**：无形性、智能性、开发个体性、质量不可完美性、复制简单性、管理特性（架构师为软件行业特有角色）、环境依赖性、维护升级性、难以废弃性、应用广泛性。
- **软件分类**：系统软件（操作系统、数据库、语言程序、服务程序）与应用软件（浏览器、支付工具等）。
- **软件生命周期**：从计划开发开始到软件报废为止的整个历史阶段，按阶段分解出具体任务，每个阶段以标准文档作为开发成果。经典八阶段划分：问题定义 → 可行性研究 → 需求分析 → 概要设计 → 详细设计 → 编码和单元测试 → 综合测试 → 软件维护。
- **开发文档链**：需求分析文档 → 概要设计文档 → 详细设计文档 → 测试设计文档 → 测试用例 → 测试报告。
- **项目进程中测试的参与方式**：编程阶段做单元测试（白盒，测试参与）→ 编程完成后开发联调（集成测试，开发为主）→ 提测后冒烟测试（自动化为主、手工为辅，测试执行）→ 系统测试（黑盒功能为主、自动化/接口为辅，按项目进行性能与安全测试）→ 验收测试（测试配合用户或需求方）。
- **开发模型**：
  - 瀑布模型：线性推进，错误修正成本高；
  - 原型模型：与客户紧密迭代；
  - 螺旋模型：计划 → 风险分析 → 实施工程 → 客户评估，循环推进；
  - 敏捷模型：以人为核心、短周期迭代、增量交付。

### 2.2 测试原则与策略

- 所有测试追溯到用户需求；尽早启动测试；遵循 Pareto 法则（分析、设计、实现阶段的复审和测试能发现并避免 80% 的缺陷，系统测试再找出其余缺陷中的 80%，最后约 4% 只会在用户大范围、长时间使用后暴露）；穷尽测试不可能；注意“杀虫剂怪事”，需持续更新用例；“前进两步、后退一步”——每次修复后需回归原有全部用例。
- **尽早测试的经济学依据**（修改一个错误的相对成本）：需求分析 1 倍 → 设计 3~6 倍 → 编码 10 倍 → 开发测试 15~40 倍 → 系统测试 30~70 倍 → 实际操作（上线后）40~1000 倍。
- **测试策略九要素**：测试安排与发布计划、测试范围、测试资源、测试环境、测试方法、用例设计方法、文档管理、风险管理、上线跟踪验证。
- **测试过程模型**：策划（需求&计划）→ 设计 → 执行 → 评估 → 总结；「控制」贯穿设计到总结全程，评估与总结阶段均有反馈回路可回到设计、执行乃至策划。
- **需求规格说明书检查列表**（每项按 是/否/NA 勾选）：覆盖用户提出的所有需求项；用词清晰、语义无歧义；清楚描述软件做什么与不做什么；描述目标软硬件环境；需求项合理编号；前后一致、彼此不冲突；说明每个输入输出格式及输入输出的对应关系；描述性能要求；优先级分配合理；描述各种约束条件。

### 2.3 测试用例设计方法

> 📚 完整资料：[测试基础/测试用例设计方法.md](../archive/old-testing-notes/测试基础/测试用例设计方法.md)

| 方法 | 核心思想 | 适用场景 |
|---|---|---|
| **等价类划分** | 输入域划分为有效/无效等价类，每类选代表 | 取值范围、必须成立条件、离散可选值 |
| **边界值法** | 取边界及略超边界的值 | 范围校验、越界检测 |
| **因果图法** | 描述输入条件与输出结果的逻辑关系 | 多条件组合、相互制约 |
| **判定表法** | 条件桩 + 动作桩 + 条件项 + 动作项 | 复杂条件组合决策 |
| **正交实验法** | 用正交表挑选有代表性的试验点 | 多因素多水平组合爆炸 |
| **场景法** | 基本流 + 备选流 | 用户端到端流程 |

**方法细则**：

- **等价类划分三原则**：输入条件规定了取值范围或值的个数 → 确定一个有效等价类和两个无效等价类；输入条件说明了“必须成立”的情况 → 划分一个有效等价类和一个无效等价类；输入条件规定了一组可能的值且程序对每种值处理方式不同 → 为每种值划分一个有效等价类，再划分一个无效等价类。某一类中的一个例子发现了错误，该等价类中的其他例子也能发现同样的错误。
- **因果图法流程**：等价类划分与边界值法只着重考虑输入条件，不考虑输入条件的各种组合与相互制约关系；因果图法从规格说明中找出因（输入条件）与果（输出结果或程序状态的改变），再将因果图转换为判定表，为判定表中的每一列设计一个测试用例。
- **边界值法要点**：不仅取输入范围边界内及刚超边界的值，也从输出域导出测试用例。
- **正交实验法三术语**：指标（判断试验结果优劣的标准）、因子（所有影响试验指标的条件）、水平/因子的状态（因子变量的取值）；依据伽罗瓦理论导出的正交表，从大量试验点中挑选有代表性的点。
- **场景法**：基本流是从开始用例到结束用例的成功路径；备选流可以从基本流分流后回归基本流、在备选流中再次分流、循环回之前的步骤，或直接异常结束用例。示例（购物结账）：基本流为“登录网站 → 选购商品 → 放入购物车 → 结账时登录账号 → 登录成功后生成订单”；备选流包括账号不存在、账号错误、密码错误、无选购商品、退出系统。
- **判定表示例（读书指南）**：条件桩为“觉得疲倦？/ 对内容感兴趣？/ 内容糊涂？”三个是否条件组合成 8 列，动作桩为“回到本章开头重读 / 继续读下去 / 跳到下一章去读 / 停止阅读休息”，是条件桩、动作桩、条件项、动作项的完整示范。

### 2.4 执行用例与缺陷管理

> 📚 完整资料：[测试基础/执行测试用例.md](../archive/old-testing-notes/测试基础/执行测试用例.md)

**执行流程**：项目提测 → 冒烟测试（未通过则打回、重新提测；通过则进入系统测试）→ 用例执行 → 通过则测试通过，失败则提出缺陷并回归验证。

**生命周期各测试方法对比**：

| | 单元测试 | 集成测试 | 冒烟测试 | 系统测试 | 验收测试 |
|---|---|---|---|---|---|
| 测试阶段 | 编码后 | 单元测试完成后 | 提测后 | 冒烟测试通过后 | 发布前 |
| 测试对象 | 最小模块 | 模块间的接口 | 整个系统 | 整个系统 | 整个系统 |
| 测试人员 | 白盒测试或开发 | 白盒测试或开发 | 黑盒测试 | 黑盒测试 | 最终用户或需求方 |
| 测试依据 | 代码、注释、详细设计文档 | 单元测试模块、概要设计文档 | 冒烟测试用例 | 需求说明文档、测试方案、测试用例 | 用户需求、验收标准 |
| 测试方法 | 白盒测试 | 黑盒与白盒结合 | 黑盒测试（手工或与自动化结合） | 黑盒测试 | 黑盒测试 |

**准入标准**：
1. 开发编码结束，并在开发环境完成单元测试；
2. 需求规定的功能均已实现，未实现部分提供测试范围；
3. 集成测试完成，基本流程可走通、界面功能齐备，代码评审通过并符合编码规范；
4. 开发提交最新版本代码作为基线，并通知测试组进行测试；
5. 兼容性测试要求明确，安全测试和性能测试的范围与要求明确。

**暂停标准**：冒烟测试发现重大缺陷、流程卡壳，可暂停测试打回开发；被测项目因需调整而暂停时，测试同步暂停。

**准出标准**：满足需求原型要求；用例评审通过并全部成功执行；测试覆盖率达标；所有缺陷录入缺陷管理系统；一二级错误修复率 100%、三四级 95%；遗留问题均有解决方案；性能、兼容性、安全性达标；产出系统测试总结报告。

### 2.5 缺陷管理

- **软件缺陷判定五条**：软件未达到产品说明书标明的功能；出现了说明书指明不会出现的错误；功能超出说明书指明范围；未达到说明书虽未指出但应达到的目标；测试员认为软件难以理解、不易使用、运行缓慢，或最终用户认为不好。
- **BUG 重现排查**：不想当然接受任何假设、做好记录；查找时间依赖和竞争条件问题；边界条件、内存泄露和数据溢出等白盒问题可能慢慢显露；状态缺陷仅在特定软件状态中显露；考虑资源依赖性以及内存、网络、硬件共享的相互作用。无法重现的缺陷也应详细记录并尽快提交开发；对难以再现的缺陷要合理安排时间，必要时暂时搁置以保证项目整体进度。
- **缺陷报告组织架构**：标题、基本信息、测试软硬件环境、测试软件版本、缺陷类型、严重程度、处理优先级、复现步骤、实际结果描述、期望正确结果、注释与截取的缺陷图像。复现步骤需提供预备步骤和信息、一步一步引导复现、每个步骤尽量只记录一个操作并编号、完整准确。
- **缺陷报告 5C 原则**：Correct（准确）、Clear（清晰）、Concise（简洁）、Complete（完整）、Consistent（一致）。
- **缺陷报告原则**：组织（谨慎执行测试，尽量定位最早出现问题的地方）、重现、隔离（区分变量，为开发调试提供思路）、归纳（排查其他模块是否有相同情况）、对比（以前通过现在未通过的要做对比）、总结（报告第一行写缺陷总结）、精简（剔除无关步骤与词语）、消除歧义、中立、检查。
- **缺陷跟踪流程**：提交缺陷 → 指派缺陷 → 确认缺陷（否 → 直接进入回归验证）→ 是否推迟处理（是 → 遗留缺陷、后续版本处理；否 → 处理缺陷）→ 回归缺陷（通过 → 关闭缺陷；未通过 → 重新打开并回到确认缺陷）。

> 💡 补充：缺陷标题建议采用「执行完 A 后，发生 B」或「发生 B，当 A 执行完后」的格式，避免模糊词汇并加关键字方便检索。

### 2.6 易用性与浏览器兼容测试

- **易用性测试**：考察用户使用软件是否方便，如是否最多点击鼠标三次即可达到目的。易用性区别于可用性：可用性指是否可以使用，易用性指是否方便使用。五个子特性：易理解性、易学习性、易操作性、吸引性、依从性。
- **浏览器兼容测试**：主流浏览器覆盖 Chrome（Blink 内核）、Firefox、IE、Safari、Edge、360、搜狗及 Linux ChromeOS。归档时期的常用兼容工具有 IETESTER、BrowserShots、SuperPreview。

> ⚠️ 已过时：IETESTER / BrowserShots / SuperPreview 均为 IE 时代的兼容测试工具，现已停止维护，现代项目建议改用云端跨浏览器测试平台。

## 三、测试进阶

> 📚 完整资料：[测试基础/测试进阶提升.md](../archive/old-testing-notes/测试基础/测试进阶提升.md)

### 3.1 白盒测试

- **代码审查**：业务逻辑、算法效率、代码风格、编程规则、内存管理（及时释放内存、避免缓冲区溢出）、性能优化（减少对象创建、减少循环体代码、优化异常处理、减少 I/O）。
- **单元测试**：软件测试中最基础的测试，集成测试、功能测试和系统测试都建立在单元测试之上；测试对象是构成软件产品或系统的最小独立单元，如封装的类或对象、独立的函数、进程、子过程、组件或模块。用例设计四原则：对所有独立执行路径至少测试一次；对所有逻辑判定的真、假两种结果至少各测试一次；进行边界检查（如数据越界检验）；检验内部数据结构的有效性。
- **逻辑覆盖**：语句覆盖 → 判定覆盖 → 条件覆盖 → 判定-条件覆盖 → 条件组合覆盖，覆盖强度逐级递增。各级基本思想：

| 覆盖级别 | 基本思想 |
|---|---|
| 语句覆盖 | 设计若干测试用例，使每个可执行语句至少被执行一次 |
| 判定覆盖 | 使每个判断的取真值和取假值都至少经历一次 |
| 条件覆盖 | 使每个条件的取真值和取假值都至少经历一次 |
| 判定-条件覆盖 | 所有条件的可能取值至少被执行一次，同时所有判断的可能结果也至少被执行一次 |
| 条件组合覆盖 | 每个条件的真假结果的所有可能组合都至少出现一次，且每个判断本身的判定结果也至少出现一次 |

### 3.2 自动化测试

- 意义：缩短周期、提升效率、节省人力、增强稳定性与精确度。
- 主流工具：OpenText UFT One（原 QTP/UFT）、Selenium WebDriver、LoadRunner、Sikuli、Appium 等。
- **实施流程**：功能和业务流程分析 → 自动化测试用例设计 → 测试脚本生成 → 测试数据和测试环境 → 测试调度，全程以自动化测试框架为底座支撑。
- **Selenium 环境要点**：不同浏览器需引入对应驱动，且驱动版本与浏览器版本保持一致——IE 用 IEDriverServer、Firefox 用 geckodriver、Chrome 用 chromedriver。
- Selenium Java 示例依赖：

```xml
<dependencies>
    <dependency>
        <groupId>org.seleniumhq.selenium</groupId>
        <artifactId>selenium-java</artifactId>
        <version>4.27.0</version>
    </dependency>
    <dependency>
        <groupId>org.testng</groupId>
        <artifactId>testng</artifactId>
        <version>7.10.2</version>
        <scope>test</scope>
    </dependency>
    <dependency>
        <groupId>io.cucumber</groupId>
        <artifactId>cucumber-java</artifactId>
        <version>7.20.1</version>
    </dependency>
    <dependency>
        <groupId>io.qameta.allure</groupId>
        <artifactId>allure-testng</artifactId>
        <version>2.29.1</version>
    </dependency>
</dependencies>
```

### 3.3 安全测试

- **WASC 六大威胁分类**：Authentication（验证）、Authorization（授权）、Client-Side Attacks（客户侧攻击）、Command Execution（命令执行）、Information Disclosure（信息暴露）、Logical Attacks（逻辑性攻击）。
- **OWASP Top 10**：注入；失效的身份认证和会话管理；跨站脚本（XSS）；失效的访问控制；安全配置错误；敏感信息泄露；跨站请求伪造（CSRF）；使用含有已知漏洞的控件；攻击检测和防范不足；未受保护的 API。
- **AppScan 扫描范围**：完整技术栈自上而下为 Web 应用、第三方组件、Web 服务器配置、Web 服务器、数据库、应用、操作系统、网络，AppScan 扫描范围覆盖第三方组件、Web 服务器配置、Web 服务器与数据库。安全审计工具虽节省大量时间，但会带来误报等问题，需人工复核。

### 3.4 性能测试

- 目标：评估生产准备状态、判定性能基准、对比系统配置、定位瓶颈、系统调优、确定吞吐量。
- 分类：负载测试、压力测试、容量测试、配置测试、并发测试、可靠性测试、稳定性测试。
- LoadRunner 核心组件：虚拟用户脚本生成器、压力产生器、用户代理、压力调度、监视系统、结果分析工具。

### 3.5 手机 App 测试

- **Appium**：开源跨平台框架（2.x 版本），支持 iOS/Android，Android 使用 UiAutomator2 驱动，iOS 使用 XCUITest 驱动。环境配置：JDK → Node.js → Android SDK → `npm install -g appium` → IDE → Appium Server 或 Desktop。
- **Monkey**：Android SDK 自带工具，生成伪随机事件流（点击、触摸、手势及若干系统级事件），所有事件随机产生、不带主观性，用于压力测试。环境配置：JDK → Android SDK → adb 连接手机或虚拟设备。

## 四、测试工具与实战

> 📚 完整资料：[测试全链路/测试全链路.md](../archive/old-testing-notes/测试全链路/测试全链路.md)

## 五、JaCoCo 与代码覆盖率

> 📚 完整资料：[jacoco/jacoco工具.md](../archive/old-testing-notes/jacoco/jacoco工具.md)

### 5.1 插桩原理

JaCoCo 通过 probe 探针注入实现覆盖率统计，支持两种模式：

- **on-the-fly 模式**：通过 `javaagent` 在类加载时动态插桩，无需提前处理，最简单常用。
- **offline 模式**：测试前预先插桩，再执行插桩后的 class/jar，适合不支持 javaagent、无法设置 JVM 参数、字节码需转换成其他虚拟机、动态修改字节码与其他 agent 冲突或无法自定义用户类加载的场景。

### 5.2 Maven 集成示例

```xml
<plugin>
    <groupId>org.jacoco</groupId>
    <artifactId>jacoco-maven-plugin</artifactId>
    <version>0.8.12</version>
    <executions>
        <execution>
            <goals>
                <goal>prepare-agent</goal>
            </goals>
        </execution>
        <execution>
            <id>report</id>
            <phase>test</phase>
            <goals>
                <goal>report</goal>
            </goals>
        </execution>
    </executions>
</plugin>
```

查看报告：

```bash
mvn clean test
# 报告路径: target/site/jacoco/index.html
```

### 5.3 覆盖率指标

| 指标 | 含义 |
|---|---|
| 行覆盖 | 至少执行一次的代码行 |
| 分支覆盖 | if/else 等分支都被执行 |
| 方法覆盖 | 至少被调用一次的方法 |
| 类覆盖 | 至少被加载执行的类 |

### 5.4 增量覆盖与命令行用法

- **增量覆盖**：统计两次提交之间新增或修改代码的覆盖情况。
- 启动带 JaCoCo agent 的服务：

```bash
java -javaagent:jacocoagent.jar=includes=*,output=tcpserver,port=6300,address=localhost,append=true -jar demo-0.0.1.jar
```

- dump 生成 exec 文件：

```bash
java -jar cli-0.8.12.jar dump --address 127.0.0.1 --port 6300 --destfile jacoco-demo.exec
```

- 生成 HTML/XML 报告：

```bash
java -jar cli-0.8.12.jar report jacoco-demo.exec \
  --classfiles D:\xxx\target\classes \
  --sourcefiles D:\xxx\src\main\java \
  --html html-report --xml report.xml --encoding=utf-8
```

> 💡 补充：增量报告可结合 `cli-0.8.12-diff.jar` 与 `code-diff.jar` 生成，将 Git diff 信息以 JSON 形式传入 `--diffCode` 参数，实现仅对新变更代码的覆盖率门禁。

## 六、Chrome 插件与提效

### 6.1 测试助手 Chrome 插件设计

> 📚 完整资料：[chrome插件设计/测试助手chrome插件设计文档.md](../archive/old-testing-notes/chrome插件设计/测试助手chrome插件设计文档.md)

**插件架构组件**：manifest.json（声明版本信息）；后台脚本 Background Scripts（在插件后台运行，监听浏览器事件、处理数据，浏览器启动时执行初始化）；内容脚本 Content Scripts（注入网页，修改或获取网页内容）；UI 组件（popup 弹出窗口、options page 选项页，承担用户交互）；数据存储（JSON 文件）；UI 设计采用 V0 生成方案。

技术方案采用 Manifest V3 + Plasmo 框架，以 JSON 工具为核心场景，包含：

- **核心功能**：JSON 输入/输出、序列化与反序列化、实时校验与纠错、转义/反转义；
- **体验增强**：Monaco/CodeMirror 编辑器、行号/折叠/括号匹配、树形视图、暗黑模式、历史记录、一键复制；
- **高级扩展**：数据排序/过滤/模拟、Base64、时间戳转换、JSON Schema 校验、大文件分块、XSS 过滤（DOMPurify）、Service Worker 离线缓存；
- **导入导出与协作**：导出 .json/.txt 文件、生成 JSON Schema 或 TypeScript 类型定义、URL 分享、双 JSON 差异对比、基于结构生成 API 文档草稿；移动端做响应式与手势优化。按优先级分阶段实现：先完成核心链路（输入 → 校验 → 格式化 → 复制），再逐步叠加高级特性。

Manifest V3 示例：

```json
{
  "manifest_version": 3,
  "name": "Test Helper",
  "version": "1.0",
  "permissions": ["activeTab", "storage"],
  "host_permissions": ["<all_urls>"],
  "background": {
    "service_worker": "background.js"
  },
  "content_scripts": [{
    "matches": ["<all_urls>"],
    "js": ["content.js"]
  }]
}
```

常用 Chrome API：

- `chrome.tabs` — 标签页操作
- `chrome.storage` — 本地存储
- `chrome.runtime` — 消息传递
- `chrome.contextMenus` — 右键菜单

## 七、2026 年测试工程趋势

结合归档内容与当前工程实践，软件测试正向以下方向演进：

1. **左移与右移并行**：单元测试、契约测试继续左移，生产可观测性、混沌工程、影子流量右移。
2. **AI 辅助测试生成**：基于需求文档或现有代码自动生成测试用例、填充测试数据、修复脆弱断言。
3. **精准测试与增量覆盖**：以 JaCoCo 增量覆盖、代码 diff 驱动用例推荐，减少无效回归。
4. **统一质量门禁**：将单元、接口、UI、安全、性能、覆盖率统一纳入 CI/CD Pipeline。
5. **浏览器端可编程提效**：Chrome 插件、Recorder、DevTools Protocol 成为测试工程师日常工具链。

> 💡 补充：2026 年团队应优先建立“可重复、可度量、可追踪”的测试基线，再逐步引入 AI 与精准测试，避免为追新而增加维护成本。

## 八、常见坑与补充

1. **覆盖率≠质量**：高覆盖率不能保证无缺陷，低覆盖率通常意味着风险。覆盖率应作为辅助指标而非唯一准出标准。
2. **自动化用例脆弱**：过度依赖页面 XPath、未做等待策略、未隔离测试数据，会导致用例频繁失败。
3. **忽略浏览器兼容性**：测试计划需明确目标浏览器及版本，国产浏览器（360、搜狗）与 IE 兼容仍需关注。
4. **缺陷报告不规范**：缺少复现步骤、环境信息、截图，会大幅增加开发定位成本。
5. **JaCoCo 与 JDK 版本匹配**：使用新版 JDK 时需注意 JaCoCo 版本兼容性，避免出现 `Unsupported class file major version` 错误。
