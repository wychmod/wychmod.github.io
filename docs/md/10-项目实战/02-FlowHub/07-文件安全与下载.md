# FlowHub：文件安全与下载

> **代码仓库**：[wychmod/FlowHub](https://github.com/wychmod/FlowHub)
> **代码位置**：`export/service/ExportFileService` + `DownloadableExportFile` / `PublishedFile` + `common/web/util/RootedPathGuard` / `ContentDispositionUtils`
> **接口**：`GET /api/v1/export-jobs/{job_id}/download`
> **本章目标**：导出文件涉及用户数据，下载接口是一扇门——学会用「受控根目录 + 路径双层防腐 + 只按任务查文件」把门看住。
> **原文对照**：仓库 `doc/07-文件安全与下载.md`

## 一、威胁模型：下载接口怕什么

| 攻击 | 剧本 | 后果 |
|---|---|---|
| 路径穿越 | 任务数据里混入 `file_path=../../etc/passwd` 或文件名带 `..\..\` | 读走服务器任意文件 |
| 符号链接劫持 | 在导出目录里放置指向敏感文件的软链接 | 「合法路径」读到非法内容 |
| 越权下载 | 枚举 job_id 拿别人的导出 | 数据泄露（本项目无鉴权，属已知边界） |
| 半成品文件 | 写了一半的 `.tmp` 被下载 | 脏数据（已由原子发布杜绝，见[第 05 章](05-导出执行与Excel生成.md)） |

## 二、受控根目录：文件的「监狱」

所有导出文件只允许生活在 `exportRoot`（默认 `export-files/`）里，内部按三层定位：

```text
export-files/
└── 2026-09-11/          ← UTC 日期
    └── 42/               ← 任务 ID
        ├── 1.tmp        ← 第 1 次尝试的半成品
        └── 1.xlsx       ← 第 1 次尝试的正式文件（发布后）
```

exportRoot 在**启动期提纯**：转绝对路径 → normalize → 创建目录 → `toRealPath` 解析真实路径。之后所有文件操作都从这一个「已知干净」的根出发。

## 三、路径双层防腐：文本层 + 物理层

每个涉及路径的入口（临时分配 / 发布 / 下载解析 / 补偿删除）都要过 `RootedPathGuard` 的两道检查：

```mermaid
flowchart TB
    IN["路径请求（可能含恶意内容）"] --> L1
    subgraph L1["第一层：文本检查（normalize）"]
        A{"含 '..' 组件？"}
        A -->|"是"| X1["拒绝 EXPORT_PATH_INVALID"]
        B{"是根组件 / 绝对路径？"}
        B -->|"是"| X1
    end
    L1 --> L2
    subgraph L2["第二层：物理检查（逐段验真）"]
        C["逐段检查符号链接<br/>+ toRealPath 解析真实路径"]
        C --> D{"真实路径仍在 exportRoot 内？"}
        D -->|"否"| X2["拒绝"]
    end
    L2 --> OK["放行，返回受控解析结果"]
```

为什么是**两层**而不是一层：

- 文本层挡「字符串层面就想逃跑」的路径（`..`、绝对路径、根组件）；
- 物理层挡「字符串合法但磁盘上被动了手脚」的场景（符号链接指向外面、大小写/编码欺骗）——`toRealPath` 解析的是文件系统的**真实**位置，骗不过去。

## 四、下载流程：一切以数据库为准

```mermaid
flowchart TB
    D["GET /export-jobs/{job_id}/download"] --> A{"任务存在？"}
    A -->|"否"| E1["404 EXPORT_JOB_NOT_FOUND"]
    A --> B{"status=SUCCEEDED 且未过期？"}
    B -->|"否"| E2["409 / 410（错误 Envelope 说明原因）"]
    B --> C["从 DB 读 file_path<br/>（文件路径只认数据库登记值，不认请求）"]
    C --> G["RootedPathGuard 受控解析"]
    G --> E{"文件存在？"}
    E -->|"丢失"| E3["EXPORT_FILE_MISSING<br/>不重新生成（见下）"]
    E -->|"存在"| F["文件流 + Content-Disposition<br/>（RFC 5987 编码中文文件名）"]
```

三个决策值得展开：

- **文件路径只认数据库**：`file_path` 是 `markSucceeded` 时写入的登记值，下载时绝不接受请求参数里的任何路径暗示——请求里只有 `job_id`，一切字段从事实源查；
- **文件丢失不重新生成**：直接报 `EXPORT_FILE_MISSING`。为什么不悄悄重跑一次导出？因为重生成会**绕过审计**（attempt 语义混乱、高水位快照已不可重建）、可能耗费大量资源，且把「文件丢了」这个事实掩盖成「一切都好」——诚实报错，让人决定要不要重试；
- **文件名三段兜底**：响应头 `Content-Disposition`（`filename*=UTF-8''` 优先解析非 ASCII）→ 数据库 `file_name` → 任务编号。前端对应地有同名解析逻辑（`filenameFromDisposition`，见[第 10 章](10-前端交互层.md)）。

## 五、前端下载的「双面响应」难题

同一个下载 URL，成功返回二进制流、失败返回 JSON 错误包（甚至网关的 HTML 错误页）——前端 `api/download.ts` 的分流协议：

```mermaid
flowchart LR
    R["fetch blob 响应"] --> OK{"HTTP ok？"}
    OK -->|"是"| SAVE["按 Content-Type 校验后保存文件"]
    OK -->|"否"| P["parseBlobError：<br/>① JSON 错误 Envelope → ApiError<br/>② 非 JSON / 缺 code → 截断 200 字符转文本错误"]
    P --> SHOW["弹窗展示 code + trace_id"]
```

统一收口在业务语言接口 `downloadExportJob` 里，页面代码不接触 blob/状态码/header 细节。

## 六、验收清单

- `ExportFileServiceTest` 8 用例：exportRoot 提纯、`..` 穿越拒绝、符号链接拒绝、根组件拒绝等防腐矩阵；
- `ExportJobDownloadControllerTest` 7 用例：未完成不可下载、过期 410、路径污染 400、`EXPORT_FILE_MISSING` 语义、文件名编码；
- 发布/补偿路径在执行体集成测试中覆盖（[第 05 章](05-导出执行与Excel生成.md)）。

## 七、遗留与改进

- 无鉴权是最大边界（任务归属人校验缺位），上生产第一优先补齐；
- 本地盘 → 对象存储迁移时，`RootedPathGuard` 的职责将转为「对象 key 合法性校验」，双层思路依然适用；
- 大文件下载目前全量流式返回，未做 Range 分片（断点续传）。
