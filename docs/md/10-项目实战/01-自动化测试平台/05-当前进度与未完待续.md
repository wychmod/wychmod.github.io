## 一、当前已经有的东西

从代码能够直接确认的能力如下：

### 1. 工程骨架

- 根工程是 Maven 多模块项目。
- `cloud-common` 提供共享 DTO、请求对象、枚举和工具。
- `cloud-engine` 提供压测相关 Controller、Service、Mapper、模型和引擎类。
- `cloud-data` 提供报告模型、Mapper、Service 和报告保存接口。
- `cloud-gateway`、`cloud-account` 已在模块列表中，但当前主要还是工程骨架。

### 2. 测试数据管理

- 项目可以列表查询、新增、更新和删除。
- 环境可以按项目查询，并支持新增、更新和删除。
- 压测模块可以列表查询、查看详情、新增、更新和删除。
- 压测模块列表会尝试带出关联压测用例。
- 压测用例可以查询、新增、更新、删除，并有执行入口。

### 3. 报告初始化

压测用例执行时，Service 会先创建一条 `EXECUTING` 状态的报告请求，再通过 Feign 调用 `cloud-data`：

```text
engine-service
  -> ReportFeignService
  -> POST data-service/api/v1/report/save
  -> report 表 insert
  -> 返回 reportId
```

这一步已经形成了服务间调用的雏形。

### 4. JMeter 底座

- Maven 中引入了 JMeter 5.5 相关依赖。
- 运行资源放在 `cloud-engine/src/main/resources/jmeter`。
- `StressTestUtil` 已封装资源路径、属性加载、编码和本地化初始化。
- `BaseStressEngine` 已封装标准引擎和模板式执行流程。
- `EngineSampleCollector` 已能读取 `SampleEvent`，累计统计并封装结果。

## 四、下一阶段最自然的实现顺序

如果继续开发，建议严格沿着当前骨架向前推进：

1. 先完成 `StressSimpleEngine`：把 HTTP 请求和线程组 JSON 转成 `HashTree`。
2. 把 `EngineSampleCollector` 注册到测试计划，跑通一次本地最小请求。
3. 完成 `StressJmxEngine`：从 MinIO 获取 JMX，加载并执行。
4. 实现 `KafkaSenderService`，明确消息 topic、key 和序列化格式。
5. 在 `cloud-data` 消费并写入 `report_detail_stress`。
6. 在成功、失败、取消三条路径更新 `report.execute_state`、结束时间和摘要。
7. 再考虑异步任务、报告查询和权限隔离。

这个顺序的原则是：先让一条最小压测链路闭环，再扩展平台能力。不要先写大屏或复杂编排，因为当前最核心的执行分支还没有真正跑起来。

## 五、这套教程怎样跟着代码继续更新

后续每完成一个可验证阶段，就在本目录新增或更新一篇文章：

- 能从 `SIMPLE` 配置生成 `HashTree` 后，再写“在线测试计划”。
- 能从 `JMX` 文件加载并跑通后，再写“JMX 上传执行”。
- 能消费并持久化结果后，再写“报告明细与统计”。
- 能完成状态机和异常收尾后，再写“任务生命周期”。

这样文章和代码始终保持一致，读者可以边读边复刻，也能知道哪些地方需要自己继续完成。
