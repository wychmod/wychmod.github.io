## 一、为什么需要一个引擎基类

不管测试计划来自上传 JMX，还是未来由表单在线生成，它们都要经过类似流程：

```text
初始化 JMeter
    -> 组装测试计划
    -> 注册结果收集器
    -> configure
    -> run
    -> 清理临时资源
    -> 更新报告
```

如果把这些步骤复制到两个执行类里，后续加第三种来源时会重复很多代码。所以当前项目用 `BaseStressEngine` 固定流程，只把“测试计划怎么组装”留给子类。

这就是模板方法模式：父类控制顺序，子类实现变化点。

## 二、逐段读 `startStressTest`

当前基类的主入口是：

```java
public void startStressTest() {
    this.initStressEngine();
    this.assembleTestPlan();
    this.hashTree2Jmx();
    this.run();
    this.clearData();
    this.updateReport();
}
```

对应含义：

| 步骤 | 方法 | 当前情况 |
|---|---|---|
| 1 | `initStressEngine()` | 已调用 `StressTestUtil` 创建引擎 |
| 2 | `assembleTestPlan()` | 抽象方法，子类目前为空 |
| 3 | `hashTree2Jmx()` | 尝试把树保存成调试用 JMX |
| 4 | `run()` | 有 `testPlanHashTree` 才 configure/run |
| 5 | `clearData()` | 方法已预留，空实现 |
| 6 | `updateReport()` | 方法已预留，空实现 |

`hashTree2Jmx()` 的意义是把动态组装的树落成 JMX，方便调试和用 GUI 打开检查：

```java
SaveService.loadProperties();
String path = System.getProperty("user.dir")
        + File.separator + "static"
        + File.separator + IdUtil.simpleUUID() + ".jmx";
SaveService.saveTree(testPlanHashTree, new FileOutputStream(path));
```

这里要注意，当前代码没有先确保 `static` 目录存在，也没有把异常继续抛出，只记录了“保存本地 jmx 失败”。因此它是调试辅助能力，不应当被当成可靠的报告产物流程。

## 三、子类为什么暂时很短

两个具体类目前只有类声明和空的组装方法：

```java
public class StressSimpleEngine extends BaseStressEngine {
    @Override
    protected void assembleTestPlan() {
    }
}

public class StressJmxEngine extends BaseStressEngine {
    @Override
    protected void assembleTestPlan() {
    }
}
```

它们表达了架构意图，但还没有实现：

- `SIMPLE` 如何把 `path`、`method`、`header`、`body` 转成 `HTTPSamplerProxy`。
- `thread_group_config` 如何变成 `ThreadGroup` 和 `LoopController`。
- `assertion` 如何变成 JMeter Assertion。
- `JMX` 如何读取 `jmxUrl`，下载或读取文件，再调用 `SaveService.loadTree`。
- 结果收集器如何挂到测试计划树的正确节点。

因此当前文章讲的是“引擎骨架”，不是完整的 JMeter 生成器教程。

## 四、结果收集器是什么

JMeter 执行过程中，每个采样器完成一次请求，就会产生一个 `SampleEvent`。`EngineSampleCollector` 继承 `ResultCollector`，重写 `sampleOccurred`，于是可以在事件发生时处理结果。

```java
@Override
public void sampleOccurred(SampleEvent event) {
    super.sampleOccurred(event);
    SampleResult result = event.getResult();
    String sampleLabel = result.getSampleLabel();
    // 统计、封装、发送
}
```

父类调用要保留，因为 `ResultCollector` 自己也有结果收集行为。子类在此基础上增加平台需要的实时处理。

## 五、为什么按 `sampleLabel` 保存统计器

一个线程组可以放多个请求。比如“登录”和“查询商品”都是不同采样器，不能混成一份平均响应时间。

当前代码使用：

```java
private final Map<String, SamplingStatCalculator> calculatorMap
        = new HashMap<>();
```

收到事件后，以采样器标签作为 key：

```java
SamplingStatCalculator calculator = calculatorMap.get(sampleLabel);
if (calculator == null) {
    calculator = new SamplingStatCalculator(sampleLabel);
    calculatorMap.put(sampleLabel, calculator);
}
calculator.addSample(result);
```

这样每个标签都有自己的累计统计器，可以读取：

- 样本数量。
- 平均响应时间。
- 最小和最大响应时间。
- 错误数量和错误百分比。
- 请求速率。
- 接收和发送速率。

这是当前结果采集器已经实现的核心逻辑。

## 六、结果 DTO 装了什么

统计数据和原始请求响应数据会被放到 `StressSampleResultDTO`：

```java
stressSampleResultDTO.setReportId(reportDTO.getId());
stressSampleResultDTO.setSampleTime(result.getTimeStamp());
stressSampleResultDTO.setSampleLabel(result.getSampleLabel());
stressSampleResultDTO.setMeanTime(calculator.getMean());
stressSampleResultDTO.setMinTime(calculator.getMin().intValue());
stressSampleResultDTO.setMaxTime(calculator.getMax().intValue());
stressSampleResultDTO.setErrorCount(calculator.getErrorCount());
stressSampleResultDTO.setRequestRate(calculator.getRate());
```

还会补充：

- 请求地址、请求头和请求体。
- 响应码、响应头和响应数据。
- 断言名称及失败信息。

断言信息来自 `AssertionResult[]`，当前代码会遍历并拼成字符串：

```java
for (AssertionResult assertionResult : assertionResults) {
    assertMsg.append("name")
            .append(assertionResult.getName())
            .append(",msg=")
            .append(assertionResult.getFailureMessage())
            .append(",");
}
```

这个版本优先保证信息能传出去，后续可以改成结构化的断言 DTO，避免消费者再次解析字符串。

## 七、采集器如何把结果交给平台

当前采集器不会直接写数据库，而是：

```text
SampleEvent
   -> SamplingStatCalculator
   -> StressSampleResultDTO
   -> Fastjson JSON
   -> ResultSenderService.sendResult(...)
```

发送时还会携带用例信息：

```java
CaseInfoDTO caseInfoDTO = new CaseInfoDTO(
        stressCaseDO.getId(),
        stressCaseDO.getModuleId(),
        stressCaseDO.getName()
);
resultSenderService.sendResult(
        caseInfoDTO,
        TestTypeEnum.STRESS,
        resultJson
);
```

这里的接口设计是有价值的：采集器只依赖 `ResultSenderService`，不必知道消息组件的具体实现。当前 `KafkaSenderServiceImpl.sendResult()` 为空，所以“调用发送接口”已经存在，“结果真的进入 Kafka”还没有发生。

> 💡 补充：这也是当前实现最值得记住的一条分界线。采集器已经把“统计”和“发送”拆开了，但真正的消息消费、落库和页面展示还没有接上，所以本章只写到接口边界，不把后续能力算进已完成范围。

## 八、当前实现里需要保持警觉的地方

- `calculatorMap` 是 `HashMap`，如果一个引擎实例会被多个线程并发调用，需要重新确认线程安全。
- 结果 DTO 同时保存完整请求和响应，生产环境要控制敏感信息和响应体大小。
- `reportDTO`、`stressCaseDO`、`resultSenderService` 依赖构造时传入，调用引擎前必须保证它们不为空。
- `sampleCount` 在当前代码中先被设置为最大耗时，后又被设置为样本数，最终值是后一次赋值；阅读和维护时应避免这种重复赋值。
- `updateReport()` 和 `clearData()` 为空，异常路径也没有完成状态更新。
