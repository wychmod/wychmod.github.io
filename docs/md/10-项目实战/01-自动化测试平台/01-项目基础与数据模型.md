## 一、先创建一个多模块 Maven 工程

`cloud-meter/pom.xml` 是父工程，打包类型是 `pom`，下面挂了 5 个子模块：

```text
cloud-meter
├── cloud-common   # 公共 DTO、枚举、工具和依赖
├── cloud-gateway  # 网关工程骨架
├── cloud-data     # 报告数据服务
├── cloud-engine   # 压测业务和执行引擎
└── cloud-account  # 账号工程骨架
```

父 POM 统一管理 Java 17、Spring Boot 3.0.2、Spring Cloud 2022.0.0、MyBatis-Plus、JMeter 5.5、MinIO、Kafka、Rest Assured 和 Selenium 等版本。

这里有一个容易混淆的点：POM 中已经声明某个依赖，不等于业务代码已经完成。比如 `cloud-engine` 引入了 Rest Assured 和 Selenium，但当前代码没有形成接口自动化或 UI 自动化闭环，所以本系列暂不讲这两条线。

## 二、两个当前运行服务

当前配置表达的是两个服务：

| 服务 | Spring 应用名 | 端口 | 数据库 |
|---|---|---:|---|
| `cloud-data` | `data-service` | 8081 | `test_data` |
| `cloud-engine` | `engine-service` | 8082 | `test_engine` |

两个服务都开启了 Spring Boot、MyBatis Mapper 扫描、服务发现、Feign 和事务管理。

```java
@SpringBootApplication
@MapperScan("com.wychmod.mapper")
@EnableTransactionManagement
@EnableFeignClients
@EnableDiscoveryClient
public class EngineApplication {
    public static void main(String[] args) {
        SpringApplication.run(EngineApplication.class, args);
    }
}
```

`cloud-data` 的启动类采用同样的基础配置。工程目前依赖 Nacos 地址、MySQL 和 Redis 配置，因此“编译通过”和“完整启动成功”是两件不同的事。

## 三、为什么要拆这些表

把一次压测直接塞进一张大表，最开始看起来省事，但很快会遇到重复数据和归属混乱：同一个环境会被多个用例复用，同一类用例也需要分组管理。

当前模型可以先画成一棵树：

```text
项目 project
├── 环境 environment
└── 压测模块 stress_case_module
    └── 压测用例 stress_case
        └── 执行报告 report
            └── 压测明细 report_detail_stress
```

各表的职责如下：

| 表 | 表示什么 | 关键字段 |
|---|---|---|
| `project` | 测试项目空间 | `id`、`name`、`project_admin` |
| `environment` | 被测服务环境 | `project_id`、`protocol`、`domain`、`port` |
| `stress_case_module` | 压测用例分组 | `project_id`、`name` |
| `stress_case` | 一条压测用例 | `module_id`、`environment_id`、请求配置、压测来源 |
| `report` | 一次执行的总记录 | `case_id`、`execute_state`、开始结束时间 |
| `report_detail_stress` | 一条或一组压测统计明细 | `report_id`、响应时间、错误率、请求速率 |

## 四、压测用例为什么字段多

`StressCaseDO` 同时预留了两类来源：

1. `SIMPLE`：在线根据请求和线程组参数生成测试计划。
2. `JMX`：使用上传或保存的 JMX 脚本。

所以它既有通用关联字段，也有请求字段和脚本字段：

```java
@TableName("stress_case")
public class StressCaseDO {
    private Long projectId;
    private Long moduleId;
    private Long environmentId;
    private String name;
    private String assertion;
    private String relation;
    private String stressSourceType;
    private String jmxUrl;
    private String path;
    private String method;
    private String query;
    private String header;
    private String body;
    private String bodyType;
}
```

`assertion`、`relation` 和请求参数目前使用字符串保存，归档笔记建议它们承载 JSON。这样做的好处是扩展快，代价是数据库不会替你校验 JSON 结构，后续需要在请求层或领域层补校验。

线程组参数同样可以先约定一个 JSON 结构：

```json
{
  "threadGroupName": "登录接口",
  "numThreads": "20",
  "rampUp": "2",
  "loopCount": "10",
  "schedulerEnabled": false,
  "duration": 0,
  "delay": 0
}
```

这只是数据格式约定。当前 `StressSimpleEngine.assembleTestPlan()` 还是空方法，因此暂时不能宣称这些字段已经被转换成 JMeter 线程组。

## 五、报告为什么分主表和明细表

`report` 记录“这次执行是谁、什么时候开始、现在什么状态”；`report_detail_stress` 记录每个采样器的性能数据。

```text
report
├── id = 1001
├── case_id = 21
├── execute_state = EXECUTING
└── start_time = ...

report_detail_stress
├── report_id = 1001
├── sampler_label = HTTP请求
├── mean_time = 35.5
├── max_time = 90
├── error_percentage = 0
└── request_rate = ...
```

拆开后，报告列表不必携带每一次请求的完整响应体，详情页也可以按 `report_id` 查询。当前 `cloud-data` 已实现的是报告主表的保存入口：

```text
POST /api/v1/report/save
        |
        v
ReportController
        |
        v
ReportServiceImpl
        |
        v
ReportMapper.insert(reportDO)
```

报告明细 Mapper 和实体已经存在，但执行链路还没有把明细写入数据库。

## 六、数据库设计中的当前问题

教程应该把代码现状讲清楚，也要把容易踩坑的地方标出来：

- 业务表有 `project_id`，但部分查询只按自身 ID 查询，后续必须持续检查项目隔离条件。
- `stress_case_module.name` 在归档 SQL 中是唯一键，但如果未来允许不同项目使用同名模块，唯一约束应该改成 `(project_id, name)`。
- 删除模块时，当前服务会继续删除关联用例，但没有展示事务边界；真实环境应避免删除一半。
- `report_detail_stress.response_data` 在数据模型中是字符串，而采集 DTO 的 `responseDate` 是字节数组，落库前需要明确转换策略。
- 配置文件包含远程数据库、Redis 和 MinIO 凭据。教程只描述配置结构，实际项目应使用环境变量或密钥管理，不要把真实凭据提交到仓库。

这些问题不影响我们理解当前代码，但会影响后续把项目做成可长期运行的平台。
