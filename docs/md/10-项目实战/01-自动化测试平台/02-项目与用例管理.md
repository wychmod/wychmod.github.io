## 一、先理解这套分层

当前 `cloud-engine` 的管理接口基本遵循下面的调用链：

```text
HTTP 请求
   |
   v
Controller     接收参数、返回 JsonData
   |
   v
Service        组织业务逻辑、拼查询条件
   |
   v
Mapper         调用 MyBatis-Plus
   |
   v
MySQL
```

请求对象 `req`、数据库对象 `DO` 和返回对象 `DTO` 分开，是为了避免把数据库字段直接暴露成接口契约。

## 二、项目管理：最简单的 CRUD

项目入口是 `ProjectController`：

| 方法 | 路径 | 作用 |
|---|---|---|
| GET | `/api/v1/project/list` | 查询项目列表 |
| POST | `/api/v1/project/save` | 新增项目 |
| POST | `/api/v1/project/update` | 更新项目 |
| DELETE | `/api/v1/project/del` | 删除项目 |

Controller 不直接操作 Mapper，而是把动作交给 `ProjectService`：

```java
@GetMapping("/list")
public JsonData list() {
    return JsonData.buildSuccess(projectService.list());
}
```

Service 再完成 DO 与 DTO 的转换：

```java
List<ProjectDO> projectDOS = projectMapper.selectList(null);
return SpringBeanUtil.copyListProperties(projectDOS, ProjectDTO.class);
```

保存操作也是同样的思路：请求对象先转换成 `ProjectDO`，再调用 `insert`。这种写法简单，适合先把业务链路跑通。

## 三、环境管理：资源必须属于项目

环境接口是：

| 方法 | 路径 | 作用 |
|---|---|---|
| GET | `/api/v1/environment/list?projectId=1` | 查询项目环境 |
| POST | `/api/v1/environment/save` | 新增环境 |
| POST | `/api/v1/environment/update` | 更新环境 |
| POST | `/api/v1/environment/del` | 删除项目下环境 |

环境的保存会先查询项目是否存在：

```java
ProjectDO projectDO = projectMapper.selectById(req.getProjectId());
if (projectDO != null) {
    EnvironmentDO environmentDO = SpringBeanUtil.copyProperties(req, EnvironmentDO.class);
    return environmentMapper.insert(environmentDO);
}
return 0;
```

环境列表和删除都会带 `project_id` 条件，这体现了“环境不能脱离项目”的业务关系。

## 四、压测模块：把用例组织起来

压测模块接口是：

| 方法 | 路径 | 作用 |
|---|---|---|
| GET | `/api/v1/stress_case_module/list?projectId=1` | 查询模块及其用例 |
| GET | `/api/v1/stress_case_module/find?projectId=1&id=2` | 查询模块详情 |
| POST | `/api/v1/stress_case_module/save` | 新增模块 |
| POST | `/api/v1/stress_case_module/update` | 更新模块 |
| POST | `/api/v1/stress_case_module/del` | 删除模块 |

`list()` 先查模块，再逐个查询模块下的压测用例：

```text
查 module 列表
  -> 对每个 module 查 stress_case
  -> 转换 DTO
  -> module.setList(cases)
  -> 返回树形结果
```

它很容易理解，但也能看出当前实现是逐模块查询，模块很多时可能产生 N+1 查询。当前阶段先保留这个清晰版本，后面可以改成一次性查询后在内存分组。

删除模块时，代码先删除模块，再按 `module_id` 删除用例：

```java
int delete = stressCaseModuleMapper.delete(wrapper);
if (delete > 0) {
    LambdaQueryWrapper<StressCaseDO> queryWrapper = new LambdaQueryWrapper<>();
    queryWrapper.eq(StressCaseDO::getModuleId, id);
    stressCaseMapper.delete(queryWrapper);
}
```

这里应该补上事务，否则中途失败会留下孤儿数据。这是当前代码的改进点，不是已经完成的功能。

## 五、压测用例：保存“怎么压”

压测用例接口是：

| 方法 | 路径 | 作用 |
|---|---|---|
| GET | `/api/v1/stress_case/find?projectId=1&id=2` | 查询用例 |
| POST | `/api/v1/stress_case/save` | 保存用例 |
| POST | `/api/v1/stress_case/update` | 更新用例 |
| POST | `/api/v1/stress_case/del` | 删除用例 |
| GET | `/api/v1/stress_case/execute?projectId=1&id=2` | 执行入口 |

保存用例当前主要是对象转换和插入：

```java
StressCaseDO stressCaseDO =
        SpringBeanUtil.copyProperties(req, StressCaseDO.class);
return stressCaseMapper.insert(stressCaseDO);
```

查询和删除会同时使用 `projectId` 和 `caseId`，这是比只按主键查询更好的隔离习惯。

但是更新方法目前只按用例 ID 更新：

```java
wrapper.eq(StressCaseDO::getId, stressCaseDO.getId());
return stressCaseMapper.update(stressCaseDO, wrapper);
```

这意味着后续需要补项目归属校验，否则调用方可能更新不属于当前项目的用例。教程把它标出来，是因为从代码能直接确认这个风险。

## 六、执行入口现在做了什么

`StressCaseController.execute()` 只负责接收参数并调用 Service：

```java
@GetMapping("/execute")
public JsonData execute(Long projectId, Long caseId) {
    stressCaseService.execute(projectId, caseId);
    return JsonData.buildSuccess();
}
```

Service 的当前流程是：

```text
查询压测用例
   -> 创建 EXECUTING 状态的报告
   -> 调用 cloud-data 的 /api/v1/report/save
   -> 根据 stressSourceType 分派 SIMPLE 或 JMX
```

分派代码已经有了：

```java
if (StressSourceTypeEnum.SIMPLE.name().equalsIgnoreCase(type)) {
    runSimpleStressCase(stressCaseDO, reportDTO);
} else if (StressSourceTypeEnum.JMX.name().equalsIgnoreCase(type)) {
    runJmxStressCase(stressCaseDO, reportDTO);
} else {
    throw new BizException(BizCodeEnum.STRESS_UNSUPPORTED);
}
```

但两个 `run...` 方法现在为空。因此调用接口不等于已经完成压测，当前只能确认“执行编排入口和报告初始化”已经写出来。

## 七、返回值和校验的现实边界

当前大量接口返回 `JsonData.buildSuccess(...)`，保存、更新、删除通常返回数据库影响行数。它还没有统一处理以下问题：

- 请求参数是否为空或格式非法。
- 更新或删除的记录是否真的属于项目。
- 删除模块是否有报告引用。
- 执行接口是否应该同步等待，还是返回任务 ID。
- 报告初始化成功后，引擎失败怎样更新状态。

这些属于平台从“接口能调用”走向“线上可用”时必须补齐的业务规则，本系列只在当前代码触及的位置说明，不提前虚构实现。
