## 一、这篇补的是哪一段

其余 14 篇都建立在一个默认前提上：**你已经装好了，并且知道 DSH 是什么。**

这个前提对作者成立，对第一次读到的人不成立。所以那些文章里会出现这种句子：「看板要暴露 HTTP，就必须自己判断谁可以读」——但没说过看板在哪、HTTP 从哪来；或者「`tools.restrict({deny:['write','edit']})` 让模型看不见这两个工具」——但没说过工具是怎么注册的。

这一篇就是把这段补上。它不讲设计，只讲**怎么让它跑起来**。

## 二、前置知识：五件你必须先知道的事

不需要读完 DSH 文档，但这五个概念必须先有：

**① DSH（DeepSeek Harness）是一个 Agent 宿主。**
它提供会话、模型调用、工具执行、权限审批这一整套运行时。插件不是独立程序，是**挂在宿主进程里**的一段代码。

**② Session（会话）是一段有历史的对话。**
它会累积消息、保留上下文，侧边栏里能看见、能点开、能继续。**这是本插件最核心的依赖**——它派的「活」就是一个真实 Session，不是一次性子进程。

**③ Agent 是 Session 背后的模型实例。**
一个 Session 对应一个 Agent，Agent 有 `id`、有 `ctx`（作用域上下文）、有工具集。插件通过 `agent.ctx` 能只对某个会话做改动。

**④ 工具（tool）是模型能调用的函数。**
本插件注册了 10 个 `dispatch_*` 工具。注册在**插件根 ctx** 上 = 全局层，所有会话的模型都能看见；注册在 `agent.ctx` 上 = 只对该会话可见。

**⑤ 插件是一个 bundle，用 `apply(ctx, config)` 作为入口。**
没有构建步骤、没有编译产物，`main` 直接指向 `src/index.js`。配置写在 `cordis.patch.yml` 的 `config` 段，全部可选，默认值见 `src/constants.js` 的 `DEFAULTS`（47 项）。

> 这五条里有四条能在仓库的 `docs/api-contracts.md` 找到证据（§4 `sessionController.create` 的真实行为、§6 `ctx.tools.register` 的作用域语义）。如果只想跑起来，记住「会话 = 有历史的一段对话」「工具注册在全局层」这两条就够。

## 三、环境要求

| 项 | 要求 | 怎么查 |
|---|---|---|
| DSH | `>= 0.2.1-rc.2` | `package.json` 的 `engines.dsh`；DSH 里看「关于」 |
| Node | `^22.19.0 \|\| >= 24.0.0` | `node -v` |
| 运行时依赖 | **0 个** | `package.json` 的 `dependencies` 为空 |
| 构建步骤 | **无** | 没有 bundler、没有 `dist/` |
| 操作系统 | 任意（Windows 有专门的目录名处理，见 [03 篇](/md/10-项目实战/04-DSH任务派发插件/03-工作区模型.md) 第六节） | —— |

**为什么 `engines.dsh` 要写这么具体**：插件用到的 `connection.requestRejection`、`agent/pre-step` 的 `startsRequestSeries`、`conversation.chat.turnTail` 槽都是宿主后来才提供的。DSH 太旧时这些能力不存在，插件会走各自的降级路径（不是崩溃，是功能少一块）。0.10.4 起看板在拿不到 `connection` 时直接回 503，而不是静默放行。

## 四、安装：三种方式，选一种

### 方式一：图形界面（推荐，不用命令行）

1. 打开 DSH 的**插件页面**
2. 点右上角「**添加插件**」
3. 输入 `dsh-mini-superagent`，确认安装

不需要写 `target`，不需要 clone。

### 方式二：按包名安装（npm 已发布）

```text
plugin_manager(action="install_bundle", target="dsh-mini-superagent@0.10.4")
```

**版本号必须写 `0.10.4`。** 本系列里会反复出现 `0.8.1` / `0.9.0` / `0.10.3` 这些版本号，它们分别属于「内部里程碑」「CHANGELOG 段」「仓库里的提交」——**`0.9.0` 与 `0.10.3` 从未发布到 npm**，写成这两个会装不上。完整的三层口径对照见 [00 篇](/md/10-项目实战/04-DSH任务派发插件/00-项目全景与阅读地图.md) 第四节。

### 方式三：从仓库或本地目录安装（要改代码时用）

```text
git clone https://github.com/wychmod/dsh-mini-superagent.git
```

```text
plugin_manager(action="install_bundle", target="<仓库路径>/dsh-mini-superagent")
```

注意路径要指到**包目录**（含 `package.json` 那一层），不是仓库根。

### 装完之后必须做的一件事

**刷新一次 GUI 页面。**

这不是可选项。插件的宿主半边在进程里，浏览器半边（看板、输入框控件、会话卡片）是页面加载时才注册的。只装插件不刷新页面，症状是：工具能调、`dispatch_list` 有返回，但**侧边栏没有「派发工作台」、输入框没有派发目标控件**。这个「假故障」在 README 里出现了三次，是最高频的误判来源。

### 一条硬性禁止

**不要同时安装旧的 `dsh-dispatch`。** 两个包共有 8 个同名工具，同一全局层重复注册会直接抛错，整个插件起不来。要换就先把旧的卸载干净。

## 五、装完自检：三步确认它真的在工作

### 第一步：工具在不在

```text
dispatch_list()
```

预期返回：

```json
{"version":"0.10.4","total":0,"running":0,"max_workers":6,"tasks":[]}
```

三个字段各有含义：

| 字段 | 该对什么 | 对不上说明什么 |
|---|---|---|
| `version` | `0.10.4` | 装的是别的版本，或旧插件没卸干净 |
| `max_workers` | `6` | `cordis.patch.yml` 里的 `maxWorkers` 没生效 |
| `tasks` | `[]` | 非空但你还没派过任务 → `stateDir` 指到了别人的账本 |

### 第二步：浏览器半边在不在

打开侧边栏，找「**派发工作台**」。找不到就查：

```text
GET /dsh-mini-superagent/board/selfcheck
```

（同源地址，浏览器里能直接打开；远程 curl 会被 403，这是有意的。）

看三个字段：

| 字段 | 含义 | 值为 `false` / 缺失怎么办 |
|---|---|---|
| `client.inGraph` | 客户端模块进了启动图 | 重启宿主进程 |
| `client.ready` | 页面里真的跑起来了 | 刷新页面 |
| `client.ready.cards` | 卡片注册结论 | 见 [11 篇](/md/10-项目实战/04-DSH任务派发插件/11-会话里的卡片与分隔线.md) 的三态表 |

**`inGraph` 和 `ready` 是两件事**：前者是「模块被列进启动图」，后者是「它在页面里执行完了」。两个都过、还是没有面板，才轮到槽注册与渲染。

### 第三步：一次最小派发

```text
dispatch_launch({
  title: "最小验证",
  brief: "目标：在当前目录建一个 verify.txt，内容写 ok。\n约束：只做这一件事。\n验收：文件存在且内容为 ok。"
})
```

预期：立即返回一个 `task_id`（形如 `t-xxxxxx-1`），**不阻塞**。然后：

```text
dispatch_list()
```

应该看到这条任务 `running`（有空位）或 `queued`（并发位满）。几十秒到几分钟后，报告会作为一条**带来源标识的消息**出现在当前会话里，分四段：

```text
【任务】最小验证
【结果】verify.txt 已创建，内容为 ok
【说明】……
【细节】dispatch_inspect t-xxxxxx-1
```

看到这条消息，说明整条链路（派发 → 建会话 → 执行 → 回流）都通了。

## 六、第一次派发：一条完整可复制的例子

最小验证只证明链路通。真实任务的差别全在 **brief（简报）** 上——因为**子会话看不到主会话的历史**，这是设计而非缺陷（见 [01 篇](/md/10-项目实战/04-DSH任务派发插件/01-从单文件到最小闭环.md) 第三节）。

一条能用的简报有四段：

```text
dispatch_launch({
  title: "把 auth 拆成独立模块",
  brief: [
    "目标：把 src/auth.js 拆成 src/auth/{index,token,store}.js 三个文件。",
    "约束：不改任何公开 API；不引入新依赖；保持现有测试全绿。",
    "验收：npm test 全绿；src/auth.js 只剩 re-export。",
    "已知事实：入口在 src/auth.js（420 行）；测试在 test/auth.test.js；",
    "          refreshToken 目前在 index 里，被 6 处调用。"
  ].join("\n")
})
```

四段各解决一个失败模式：

| 段 | 不写会怎样 |
|---|---|
| **目标** | worker 不知道要做什么，只能猜 |
| **约束** | worker 用最省事的方式做（比如顺手改了 API） |
| **验收** | worker 说「做完了」，但你没法定量确认 |
| **已知事实** | worker 从零重建你对项目的认知，重复你已经查过的东西 |

**反例**：`brief: "修一下那个 bug"`。worker 不知道是哪个 bug、在哪个文件、什么算修好——它只能瞎猜，报告里全是假设。这类简报的成本不会消失，只是转移到了「你看完报告发现全错、重派一次」上。

## 七、起步阶段的六个坑

按出现频率排。每个都给出「怎么确认」而不是「可能是什么」。

### 坑 1 · 装完没图标

**先确认在装没装上，还是在页面没加载。** 查 `selfcheck` 的 `client.inGraph` 与 `client.ready`（见第五节第二步）。`inGraph: false` → 重启宿主；`ready` 缺失 → 刷新页面。

### 坑 2 · 工具调不了，报「只能在某个会话中调用」

`dispatch_*` 需要一个 Agent 作为调用者（要判「你是主会话还是 worker」）。在脚本或工具测试环境里没有 Agent，调不了。**从正常会话里调。**

### 坑 3 · 任务一直 `queued`

```text
dispatch_list()
```

看 `running` 是否已经等于 `max_workers`（默认 6）。等于就说明**并发位满了，在正常排队**——`queued` 代表「已派出去、在等空位」，不是「没派成」。这是本插件最常见的误读。

如果 `running < max_workers` 却仍有 `queued`，看是不是有任务卡在 `running` 占着位（用 `dispatch_inspect` 看它的 `last_worker_text`）。

### 坑 4 · 派完就结束本轮，但你以为它没回答

`dispatch_launch` 返回后本轮就可以结束了。**「结束本轮 ≠ 没回答」**——你在这一轮末尾说的那句「已派发，报告回来我汇总」就是回答。这个认知错位曾经导致主会话连续等 33 分钟、零产出（见 [06 篇](/md/10-项目实战/04-DSH任务派发插件/06-路由模式与提示词契约.md) 第三节）。

### 坑 5 · 选了「不派发」，它还是派发了

0.6.0 的实现有 bug：宿主的请求装配对变化的提示是**追加不是替换**，旧的强制段会留在会话面上。0.8.x 内部里程碑通过 `agent/pre-step` 返回 `startsRequestSeries: true` 修掉。**升级到 0.10.4 即解决。**

### 坑 6 · `dispatch_inspect` 一直报 `invalid output`

这是 0.10.3（仓库版本号）修的 `detail: undefined` 脏键问题。**`0.10.3` 没有发布到 npm**，装 `0.10.4` 即可，存量账本无需手工清洗（[12 篇](/md/10-项目实战/04-DSH任务派发插件/12-安全纵深与最后三修.md) 第四节有完整拆解）。
