## 一、一句话认识空气扑克

**「你下注的，是下一口空气。」**

空气扑克是一个把「数字构牌 + 受限信息 + 空气博弈」装进浏览器的单人策略游戏。你和对手各持五张私有数字牌，每轮用一张数字去构造一手五张实体牌；牌型决定摊牌强弱，而下注消耗的是同一种叫 AIR 的资源——它既是压上桌的筹码，也是你下一口的呼吸。

| 基本信息 | 说明 |
|---|---|
| 项目性质 | 非商用、爱好者技术实验，改编自漫画《噬谎者》「空气扑克」篇 |
| 运行形态 | 纯静态站点：原生 HTML / CSS / JavaScript，浏览器本地运行 |
| 运行时依赖 | **0**（无第三方游戏库、无编译步骤、无游戏后端、无账号） |
| 界面语言 | 中文与英文（文档另有日文版） |
| 自动化测试 | **202 个** `node:test` 用例 + 真实浏览器回归 |
| 许可 | MIT（仅覆盖作者编写的代码，原作素材不在其中） |

它不是一副扑克牌的电子版，而是一个**用扑克外壳包装的资源博弈系统**：数字、牌型、下注、呼吸、时间五件事彼此牵制，赢下底池不等于赢下整局。

## 二、它从哪来：漫画、考据与数字版改编

项目改编自迫稔雄漫画《噬谎者》（嘘喰い / Usogui）**第 40–43 卷「空气扑克」篇**。作者把它定位为非商用爱好者学习项目，尝试把原作里数字构牌、受限信息与空气下注的紧张感转化成可交互的浏览器体验。

真正让这个项目区别于普通「同人游戏」的，是它对**来源可信度**的诚实分层。项目文档把规则依据分成三层：

| 可信层级 | 内容 | 处理方式 |
|---|---|---|
| 一手资料 | 漫画单行本原文 | 精确时序、特殊判例回查单行本，不从德州扑克惯例补齐 |
| 二手公开整理 | Usogui Wiki、GOMISTATION（引用第 40 卷 62–63 页）、PHMPK 第 43 卷评述 | 交叉验证，只采用多来源支持的结论 |
| 数字版约定 | 单人合并上下层、自动换罐、60 秒构造、固定 10 秒缺氧宽限、双无解转耐息、快进 | 明确标注为「确定性改编」，不声称原作 1:1 复刻 |

这种「把自创机制明说成自创」的做法贯穿全项目。例如 2026-11-07 的「跟注即摊牌」改动，文档明确写着这是一次**规则变更而非 bug 修复**：原作二手整理记载的是「跟注后仍可继续加注、靠双方过牌收束」的旧行为，代码原本与之一致；只是作者出于体验考虑主动改了规则，并把原作依据、改动影响和保持不变的部分逐条记录。

> 这一层考据态度本身就是重要的可推荐价值——它示范了如何在「致敬原作」和「做可玩设计」之间划清边界，避免把自创机制说成原作规则。

## 三、项目想解决的三个问题

把漫画规则做成网页游戏，通常有三个坑。空气扑克逐一给出了答案。

**问题一：规则复杂，怎么让第一次玩的人看得懂？**
答案是八页渐进式界面 + 独立教学。首页 → 介绍 → 教学 → 对战 → 胜/负/平 → 复盘，每一步都用真实状态渲染，而不是拿带示例数据的整页图片冒充可操作界面。教学页把「选数字 / 整手锁定、支付、失败与灾厄、供气与宽限」拆成四项可重练的练习。

**问题二：单机游戏没有对手，怎么保证博弈有张力？**
答案是三档 AI + 严格的信息隔离。对手在你选牌**之前**就锁定自己的选择，只能凭自己的私有数字、公开数字、公共弃牌和下注历史决策，读不到你的未公开数字、构牌草稿或私牌。三档难度靠规划深度与公开信息利用区分，而不是靠作弊。

**问题三：资金和输赢怎么让人信服？**
答案是可核对的空气账本。每一罐 AIR 的转移都有逐笔记录，双方未开余额 + 未结算底池 + 累计已开呼吸罐 + 累计实际烧毁，恒等于初始的 50 罐。你可以展开全部轮次、构造尝试、事件时间线与账目，甚至导出 JSON 自己核对。

## 四、一分钟看懂核心玩法

| 要素 | 当前规则 |
|---|---|
| 开局资源 | 双方各 **25 罐 AIR**，各开 1 罐供气，剩 24 罐可下注 |
| 数字与成手 | 每轮消耗一张数字牌，构造 **5 张不同、未使用的实体牌**，点数和等于该数字；A=1，J/Q/K=11/12/13 |
| 共享牌库 | 双方从同一副 52 张牌的剩余牌库独立构牌，同轮可以重叠；有效成手中的牌用后进入公共弃牌 |
| 交替下注 | 过牌、跟注、加注、弃牌或合法全押；**跟注即摊牌**，只有加注才让对手继续回应 |
| 摊牌与灾厄 | 按标准五张牌型比较；双方成手有效、存在实体牌重叠且分出胜负时，败者额外烧毁空气 |
| 实时呼吸 | 每罐约供气 **300 秒**，用尽自动换罐；构造时限 **60 秒**，每次玩家下注 **30 秒** |
| 耐息终局 | 完成五轮或无法继续匹配底注时进入耐息，供气耗尽后有 **10 秒**缺氧宽限，按实际生存时间裁决胜负 |

一轮的节奏是：**选择数字 → 构造五张牌 → 锁定并投入底注 → 交替下注 → 摊牌结算**。

举个成手例子：本轮数字是 **17**，可以选择 A、2、3、4、7，因为 `A(1) + 2 + 3 + 4 + 7 = 17`。但点数和正确只是第一步——这五张还必须是真实存在、彼此不同、尚未用过的实体牌，最后仍要与其他有效成手比较牌型。**数字大不等于牌型强**。

## 七、三条推荐阅读路径

不同读者不必从头到尾读完，按需选路：

- **玩家 / 体验者**：00 → 01 → 07（玩法 + 界面），然后直接去在线试玩，边玩边对照规则。
- **前端 / 游戏开发者**：00 → 02 → 03 → 07 → 08，重点看架构分层、状态机与表现解耦、质量保障。
- **AI / 算法与工程研究者**：00 → 04 → 05 → 06，重点看受限信息决策、策略评估方法论与可审计账本。
- **产品 / 复盘读者**：00 → 10 → 06 → 08，重点看「为什么这么改」「账目怎么信」「怎么交付」。

如果你是技术选型者或团队负责人，只想快速判断「值不值得借鉴」，读 00 与 09 两篇即可；想看开发过程与弯路，加读 10。

## 八、核心讲解：为什么这个项目值得当教材

把前面所有信息收拢，这个项目的教学价值集中在四个「可迁移的模式」。

**第一，规则是纯函数，状态只有一个来源。** 牌型比较、下注合法性、供气计算、账目记录全部能脱离浏览器运行。这不只为测试方便，更是把「游戏规则」和「游戏怎么被展示」彻底分开——这是任何复杂交互系统都该遵守的第一原则。

**第二，隐私边界做在数据出口。** `getState()` 返回快照时会主动隐藏对手未出数字、摊牌前成手。界面拿不到隐私数据，就不可能「不小心」泄露。用数据结构本身来保证约束，比靠开发者自觉可靠得多。

**第三，时间基于绝对时长。** 引擎按绝对对局时间推进，后台一次恢复与分步推进得到的结果完全一致。切语言、看规则、关动效都不会延长真实截止时间。这解决了实时应用里最容易被忽视的一类 bug。

**第四，资金账目可连续重放。** 每笔 AIR 转移都保留前后五个账户，守恒式恒为 50。记录器只记事实，不参与决策——这让「复盘」成为对已发生事实的回放，而不是对历史的二次猜测。

> 这四条模式都不是空气扑克首创，但很少有一个体积这么小的项目把它们同时做到位、还配上 202 个测试与完整考据文档。这正是它适合当教材的原因。

## 九、使用建议与推荐结论

**怎么用这个系列：**

1. 第一次接触，先读本文和 01 篇建立玩法直觉，再决定深入方向。
2. 动手前把项目跑起来（08 篇有完整命令），边玩边读比纯读印象深刻得多。
3. 想借鉴某一种模式，直接跳到对应专题篇，每篇末尾都有「使用建议」。

**推荐结论：**

- **推荐谁读**：前端与游戏开发者（学架构与状态机）、AI 与算法爱好者（学受限信息决策与策略评估）、想做考据型项目的技术作者（学可信度分层）、需要向他人讲清复杂系统的工程师。
- **推荐读法**：把它当「小而全的工程样本」而非「游戏攻略」——它的价值在于把一个具体问题做到可验证、可审计、可解释。
- **不推荐期待什么**：它不是多人联机、不是原作 1:1 复刻、没有必胜 AI 或最高胜率算法、不模拟真实生理呼吸。这些边界作者在文档中均已明说，阅读时保持一致预期即可。
