## 一、一个「没有后端」的游戏怎么运转

空气扑克是一个纯静态站点：浏览器直接通过 HTTP 加载 ES modules，没有编译步骤，没有游戏后端，没有账号系统。开发工具和测试使用 Node.js，但 Acorn、Prettier、Playwright 都只是开发依赖，不进入站点产物。

这个选择带来三个直接后果：**打开 URL 就能玩**（无需注册、无需等服务端）、**对局逻辑全在本地**（规则即代码，可离线验证）、**部署极简**（把静态目录托管出去即可）。但它也带来一个工程挑战：没有后端帮你集中管理状态，所有「权威判断」必须在前端内部自己守住。

项目的回答是：**把游戏核心做成一个与浏览器完全隔离的纯逻辑模块**。这不只是目录习惯，而是写进检查器的硬约束。

## 二、三层分离：核心 / 平台 / 呈现

架构上分成三层，依赖方向单向向下：

```
app.js（入口 · 事件 · 页面 · 存储）
  ├── 呈现层：ui/*（牌桌 · 教学 · 复盘）+ i18n.js（双语文案）
  ├── 平台层：browser/*（行动时钟 · 对局时钟 · 归档 · 分享 · 统计）
  └── 核心层：game/*（状态机 · 规则 · 牌 · 发牌 · AI · 下注 · 呼吸 · 记录）
```

| 层 | 职责 | 关键特征 |
|---|---|---|
| `game/`（核心） | 牌型、共享牌库、发牌、对手决策、下注、呼吸、记录与权威状态机 | **不访问 DOM、网络、存储、平台计时器或 Node API**，可在纯 Node 环境导入 |
| `browser/`（平台适配） | 对局与行动时钟、最近完成局归档、场景动效、访问统计、分享转换 | 只负责时钟调度、平台读写与渲染调度 |
| `ui/`（呈现） | 页面、牌桌、自由构牌、教学、记录与复盘渲染 | 只消费公开快照与只读函数，不创建第二份对局状态 |
| `app.js` / `i18n.js` | 应用入口、事件协调 / 中英文文案 | 事件委托、对话框、真实时钟、教学状态、偏好存储 |

这套分层的核心思想是：**界面只消费快照，浏览器模块只提交时间和动作**。真正的牌力判断、资金变化、状态迁移，全部发生在纯逻辑核心里。

## 三、模块依赖矩阵

项目把依赖方向固化成一张矩阵（可执行版本在 `scripts/harness/config.js` 的 `LAYERS`）：

| 层 | 允许依赖 |
|---|---|
| data、rules、betting、breathing、records、contracts、difficulty、ai-observation | 无运行模块依赖（最底层） |
| cards | data、rules |
| deal | cards |
| ai-planning | cards、deal、difficulty |
| ai-betting | cards、deal、rules、ai-planning、difficulty、ai-observation |
| ai → opponents | 逐层向上组合 |
| engine | rules、cards、deal、ai、betting、breathing、records、ai-observation |
| archive（browser/record-store.js） | records；只负责归档平台读写 |
| ui | ui、share-ui、data、rules、cards、engine、breathing、i18n、contracts、difficulty |
| share-qr / share-ui / browser/share | 分别无依赖 / 依赖 records+share-qr / 无依赖 |
| app | engine、browser、archive、ui、share-ui、i18n、opponents、contracts、difficulty |

几个关键约束：

- **引擎是汇聚点**：只有 `engine` 能同时依赖规则、牌、发牌、AI、下注、呼吸、记录。它是唯一持有权威状态的地方。
- **ui 不能碰第二份状态**：ui 只读快照与只读函数，不自行下注结算。
- **share-qr 无运行依赖**：二维码矩阵直接内嵌，不请求远程生成服务。
- **i18n 独立**：文案层不依赖游戏逻辑。

> 新增模块必须明确职责并更新这张矩阵。检查器会解析静态 `import`、re-export 与字面量动态 `import`，拒绝计算出来的模块路径——因为动态拼接的路径无法静态验证边界。

## 四、createGame 的四个出口

`createGame()` 持有私有对局状态，只暴露四个入口，形成一条严格的「信息隧道」：

| 入口 | 作用 | 隐私处理 |
|---|---|---|
| `getState()` | 返回独立的深拷贝快照 | **隐藏**对手未出数字、来源证明、摊牌前成手；accounting 只保留当前五账户摘要 |
| `getRecord()` | 按需返回完整事件、轮次、逐笔账目与派生统计 | 进行中继续隐藏未揭示尝试的对手成手，不含未来对手数字 |
| `dispatch(action)` | 接受当前阶段的合法动作，成功返回 `true`，非法返回 `false` 且状态不变 | 重复确认、非法阶段、旧动作不会改变状态或重复扣款 |
| `reset()` | 开启新局 | 动作编号跨重开递增，`sessionId`/`attemptId`/`turnId` 同步递增 |

`createGame` 支持依赖注入：`random`、`dealRandom`、`opponent`、`swapSides`、`recordId`、`mode` 都可传入。默认使用 ai 的兼容基线；浏览器通过 `opponents` 工厂注入所选难度。这种注入能力让「固定种子整局模拟」「交换持牌对比」等评估手段成为可能（见 05 篇）。

**数组形式的无效成手提交是合法游戏动作**——它会被记录为成手失败；而错误类型的请求则被直接拒绝。这个区分保证「失败」也是可记录、可推理的游戏事实，而不是异常。

## 五、七条设计约束

README 把设计原则浓缩成七条，每一条都对应一类常见 bug：

1. **规则是纯函数，状态只有一个来源。** 牌型、下注、供气、账目都可脱离浏览器运行，测试不依赖页面。
2. **隐私边界做在数据出口。** `getState()` 不把隐私交给界面，表现层无法「猜牌」。这是模块边界，不是对本机调试者的加密保护。
3. **动作带身份，超时只生效一次。** `sessionId`、`attemptId`、`turnId` 隔离重开、重新构造与旧回调，防止重复确认与重复结算。
4. **时间基于绝对时长。** 后台恢复、暂停动效、切语言都不延长真实截止时间；一次长时间恢复与分步推进结果相同。
5. **资金账目可连续重放。** 每笔转移保留前后五账户，守恒式恒为 50；记录器只记事实，不参与决策或结算。
6. **静态站点也做结构约束。** 架构检查器解析静态导入、禁止计算模块路径、按层级拒绝越界依赖；发布走显式白名单。
7. **表现与对局解耦。** Canvas 动画只消费公开事件，动画完成不触发扣款或结算；隐藏页面时停止绘制，恢复后先同步引擎。

## 六、架构检查器：把约定变成可执行规则

「我们约定 game 不访问 DOM」和「检查器确保 game 不访问 DOM」是两回事。项目属于后者。

架构检查器（`scripts/harness/`）做三件事：解析静态 `import`/re-export/字面量动态 `import`；拒绝计算出来的模块路径；按 `LAYERS` 矩阵拒绝越界依赖。游戏层禁止的 API 名称（DOM、网络、存储、平台计时器、Node 平台 API）在配置里维护成名单，一旦被核心层引用就会报错。

配合检查的还有：
- **语法检查**：覆盖全部 JS 文件；
- **格式检查**：Prettier 管理受控源码与工程文档；
- **HTTP 资源检查**：不执行页面脚本，但覆盖当前 HTML 的 `src/href/poster`、CSS 的 `url/@import`、JS 模块导入以及静态图片/字体字符串；
- **测试**：`node:test` 覆盖规则、引擎、账目与检查器本身。

`npm run check` 把这些串成一条流水线：语法 → 架构 → 测试 → 格式 → 构建 → HTTP 资源，任一步失败即停止。

> 注意检查器的边界：它不能替代完整类型系统或安全审计。这是项目自己写明的限制——承认工具的能力边界，本身就是严谨的表现。

## 七、发布与资源边界

`npm run build` 只替换固定输出目录 `dist/site/`，从白名单复制：入口 HTML、JS、实际使用的 CSS、`assets/runtime/` 下的 WebP 与 `assets/share/` 下的封面/图标，并生成英文元信息入口 `en.html`。不复制开发依赖、测试、脚本、设计提案或参考素材；没有运行时代码打包或转换。

浏览器导入与本地资源使用**相对路径**，以兼容根路径和项目子路径（这对 GitHub Pages 子路径部署至关重要）。新增运行目录时要同步核对三处：发布与代码检查范围、本地开发服务的公开路径、真实浏览器的加载行为与资源递归检查。

发布产物约 **2.5 MB / 56 个文件**。此前经过专门优化，从约 58.96 MB 瘦身而来——具体数据与做法见 08 篇。

## 八、核心讲解：边界即正确性

这个项目最值得学的，不是某一个算法，而是**用边界设计来保证正确性**的思路。

传统做法把规则、状态、渲染混在一起，正确性靠测试和代码审查兜底。空气扑克反过来：先把「谁能依赖谁」「谁能看到什么」「谁能改什么」写成硬边界，再用检查器强制。边界一旦成立，很多 bug 不是「被修掉」，而是「根本无法被写出来」——

- ui 拿不到对手私牌，就不可能泄露对手私牌；
- game 访问不到计时器，就不可能依赖浏览器时钟做判断；
- 动作带 `attemptId`，旧回调就无从重复扣款；
- 发布走白名单，参考素材就进不了产物。

> 这种「让错误无法发生」的设计，比「让错误发生后能被发现」高一个层级。它也是为什么这个零依赖小项目能承载 202 个测试和三档 AI 而不失控。

## 九、使用建议与推荐结论

**使用建议：**

1. **想借鉴架构**：先照搬「核心层禁止 DOM/网络/存储/计时器」这条硬约束，收益最大、成本最低。
2. **做静态站点**：把发布白名单和资源检查器当成必备设施，尤其是要部署到子路径时。
3. **引入检查器时**：明确写清它不能替代什么（类型系统、安全审计），避免团队误以为「检查通过 = 绝对安全」。

**推荐结论：**

- 这套架构适合**规则复杂、需要高可信度、但又想保持零后端**的项目——博弈游戏、编辑器、模拟器、教学工具都适用。
- 对于真正需要多人联机、账号、服务端的场景，它不被设计成那种方案；应把它当「单机可信核心」模块嵌入更大的系统，而不是整体照搬。
- 依赖矩阵 + 自动检查器的组合，是它最可迁移的工程资产。即使不用 JavaScript，这套思路也能直接套用到其他语言的分层架构里。
