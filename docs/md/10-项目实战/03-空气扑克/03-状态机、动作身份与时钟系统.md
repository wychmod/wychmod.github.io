## 一、一局游戏的状态流转

引擎维护一个明确的状态机，每个阶段只接受特定动作。

```
正常流程：lower → upper → bet → showdown → lower
                                    ↓（五轮完成 / 无法匹配底注）
                              endurance → summary

双方成手失败：bet → upper（重做同数字、同底池）→ showdown
双方数学无解：退回底池 → endurance → summary
任意活动阶段：供气耗尽 + 缺氧宽限结束 → summary
```

| 阶段 | 做什么 | 谁能行动 |
|---|---|---|
| lower（下层） | 选择数字 | 先对手后玩家，对手在玩家选择前锁定 |
| upper（上层） | 60 秒内构造五张实体牌 | 玩家构牌；可主动放弃 |
| bet（下注） | 交替下注直至摊牌条件满足 | 首动方按规则交替 |
| showdown（摊牌） | 比较牌型、结算底池、判定灾厄 | 引擎自动 |
| endurance（耐息） | 时间推进至首次耗尽，可快进 | 引擎按供气公式模拟 |
| summary（终局） | 冻结结果、保存最近完成局 | 引擎冻结 |

关键细节：`completedRounds` **只在真正结算后递增**。双方重做、双无解未结算的轮次不计入完成数；耐息期间不补数字、不下注、不增加下注回合。这让「完成轮数」始终是一个可信的事实，而不是一个不断被猜测的计数。

## 二、动作身份：三道防重的闸门

实时交互里最隐蔽的 bug 是「同一个动作被处理两次」——后果可能是重复扣款、重复结算。项目用三个身份编号把这类问题从根上堵住。

| 身份编号 | 隔离什么 | 用在哪些动作 |
|---|---|---|
| `sessionId` | 区分不同对局（重开后递增） | 时间动作 `elapse`、终局快进 |
| `attemptId` | 区分同一对局内不同的构牌尝试 | `confirm-hand`、`submit-hand`、`fail-hand`、`upper-timeout` |
| `turnId` | 区分不同的下注回合 | 下注动作、对手动作、下注超时 |

规则很硬：上层的 `confirm-hand` 等动作**必须带当前 `attemptId`**；下注、对手与下注超时**必须带当前 `turnId`**。动作编号跨重开递增，重复时间、旧确认、旧回调都不能影响新局。

引擎还维护最近 64 个已接受下注的白名单观察：在动作接受前采集 session / round / attempt / turn 以及应跟额、加注上限，接受后加入实付和超时标识。非法、重复、过期动作不追加；`reset()` 清空。这份观察只用于困难档的**本局内适应**，不放进 `getState()`，也不从记录器反向读取。

> 这套设计解决的是一个通用难题：**异步回调的陈旧性**。只要界面可能比状态慢半拍，就需要让每个动作携带「我是哪一轮、哪一次尝试」的身份证，否则慢回调会打到新状态上。

## 三、elapse：把时间当动作提交

时间不是由界面自己推进的，而是作为一个动作提交给引擎。

`elapse` 动作携带 `sessionId` 和一个**递增的安全整数 `elapsedMs`**。引擎收到后，按绝对对局时间依次推进到三个边界：供气边界、60 秒构造截止、下注行动截止。一次长时间恢复与分步推进得到相同结果——因为引擎算的是「从起点到现在应该发生什么」，而不是「收到几次脉冲就走几步」。

这样做的好处是：**无论浏览器因为后台标签页、卡顿、切语言而丢失多少次脉冲，只要把最新的绝对时间交给引擎，状态就会收敛到正确位置。**

## 四、三套时钟各司其职

浏览器侧的时钟模块分工明确：

| 时钟 | 文件 | 职责 |
|---|---|---|
| 对局时钟 | `browser/match-clock.js` | 用单调时钟同步绝对时长，负责呼吸脉冲 |
| 行动时钟 | `browser/turn-clock.js` | 展示引擎截止时间，调度玩家 30 秒 / 对手 600 ms / 构造 60 秒 |
| 引擎时间轴 | `game/engine.js` | 权威地按顺序推进构造、下注、换罐边界 |

几条纪律保证时钟不「帮倒忙」：

- **交互前先同步时间**：`app` 在任何交互前先让引擎同步到当前绝对时间。
- **pageshow 先恢复呼吸再恢复行动**：从后台回来时，先处理供气边界，再处理行动截止。
- **普通呼吸脉冲只更新文字**：不重建加注输入——否则用户正在输入的数字会被一次呼吸脉冲清掉。只有阶段、行动或整罐余额变化才触发重绘。
- **语言与只读查看不重置**：切语言、看规则、看记录都不重置对局、截止时间或呼吸。

## 五、绝对时长：为什么恢复与步进结果一致

这是整个时钟系统最值得讲清楚的一点。

假设一罐 AIR 在第 300 秒耗尽。两种情形：

- **情形 A（分步）**：浏览器每秒提交一次 `elapse(1000)`、`elapse(2000)`……到第 300 秒时触发换罐。
- **情形 B（长时间恢复）**：标签页后台挂了 5 分钟，回来后一次性提交 `elapse(300000)`。

引擎的做法不是「数脉冲」，而是根据绝对时长**依次计算**中间发生了哪些边界事件（换罐、缺氧、构造截止、行动截止），并按顺序应用。所以 A 和 B 的终态一致。

> 这条性质在测试里是可验证的：同一组动作序列，用不同粒度的时间切片提交，结果必须相同。这也是项目敢说「时间基于绝对时长」的底气。

相对地，如果实现成「每次脉冲扣 1 秒」，后台恢复时就会少扣几百秒——玩家只要切到后台就能「暂停呼吸」，博弈瞬间失衡。

## 六、重开与归档的边界

**重开（reset）**：发出新数字、恢复 25 罐总资源并各开一罐，清空弃牌、轮数、耐息和旧时钟。`sessionId`、`attemptId`、`turnId` 跨重开递增，动作编号不回退。首页/介绍/教学阶段不创建引擎，空闲快照只有 `phase=idle` 与 `sessionId=0`；首次开始才 `createGame`，之后 `reset` 复用原实例以保持编号递增。

**归档**：只在每个 session **首次进入 summary 时保存一次**完整记录。归档模块只读写固定键 `air-poker-last-record-v1`，检查版本、基本结构和连续账目，重算派生统计；失败返回状态但不阻断游戏。新局不会覆盖此前完成局，下一局完成才替换；未完成对局不保存为正式战绩，也不恢复进度。

> 注意边界：这不是「存档读档」系统。它不提供对局恢复、导入执行或防篡改认证。刷新不会恢复未完成对局——这是明确的产品选择。

## 七、表现层的时钟纪律

场景动效（`browser/scene-motion.js`）无运行模块依赖，从前后公开快照识别已接受动作，用真实的 `betting.history.paid` 区分支付与呼吸开罐。几条纪律：

- 表现副本不含可交互入口；动画结束**不触发任何引擎动作**。
- Canvas 限制像素倍率（上限 2），隐藏时停止绘制，恢复后不补播过时事件。
- 统一受应用开关与系统 `prefers-reduced-motion` 双重控制。
- 终局约 2.9 秒的收尾序列不拦截指针，结束后自动移除。

## 八、核心讲解：确定性来自哪里

把三套机制合起来看，确定性来自三个「不」：

1. **不靠脉冲计数推进时间**：靠绝对时长计算边界，恢复与步进等价。
2. **不靠回调现场判断有效性**：靠动作携带的身份编号，旧回调自然失效。
3. **不靠表现层触发状态变化**：动画只是对已发生事实的回放，不参与结算。

> 这三条合起来，让「同一组输入 → 同一组输出」成立。而确定性正是可测试、可复盘、可评估的前提——05 篇的固定种子策略评估、06 篇的账目连续重放，都建立在这个基础之上。

## 九、使用建议与推荐结论

**使用建议：**

1. **做任何实时交互**，都值得引入 `sessionId + attemptId + turnId` 这类身份分层，成本很低、收益很大。
2. **处理后台恢复**时，用绝对时间 + 边界推进模型，不要用「每帧扣一点」的增量模型。
3. **区分「会动效」与「会结算」**：让动画只消费事实，可以极大降低状态机的复杂度。

**推荐结论：**

- 本篇的价值在于示范**如何把时间、身份、表现三件容易纠缠的事彻底解耦**。这套方法适用于任何有实时约束的前端应用，不限于游戏。
- 需要提醒的是：归档只保留最近一局、不恢复未完成对局，是产品取舍而非技术限制。若你的场景要存档读档，需要另行设计，不能指望复用这里的归档模块。

## 附录：一次下注动作的代码路径

> 对应源码：`game/betting.js` 的 `getBetOptions()`、`applyBetAction()`；`game/engine.js` 的 `resolveBet()`。

界面只负责把动作和 `turnId` 交出去，合法性、扣款和阶段迁移都在引擎里。

**1. `getBetOptions(state, actor)` 先算钱**

```
toCall       = max(0, 对手投入 − 我的投入)
matchedLimit = min(我的投入 + 我的未开储备, 对手投入 + 对手未开储备)
maxRaise     = max(0, min(⌊(底池 + toCall) / 2⌋, matchedLimit − 较高投入))
allInCost    = max(0, matchedLimit − 我的投入)
canCall      = 有应跟 且 应跟 ≤ 我的未开储备
canAllIn     = 全押成本 > 0 且 全押成本 − 应跟 ≤ maxRaise
```

最后一条保证**全押也不能绕过半池上限**。

**2. `applyBetAction()` 生成新状态**

- 过牌：应跟为 0 才合法，累计 `checks`；
- 跟注：付 `toCall`；
- 加注：付 `toCall + 增量`，其中增量必须落在 `1..maxRaise`；
- 全押：付 `allInCost`；
- 弃牌：付 0。

付款后写回 `air`、`bet`、`pot`，然后决定结局：

```js
const outcome =
  action === 'fold' ? 'fold'
  : action === 'call' || checks >= 2 || matchedAllIn ? 'showdown'
  : 'continue';
```

注意 `paid` 与 `raised` 是两个字段：加注时 `paid` 包含先跟齐的部分，`raised` 只是增量。无论哪种结局，`turnId` 都会 +1；终结时 `turn` 置空，但编号继续递增，旧按钮自然失效。

**3. `resolveBet()` 记账并分流**

```js
if (!isBetTurn(actor, turnId)) return false;
const options = getBetOptions(state, actor);
const result = applyBetAction(state, actor, action, amount);
if (!result) return false;
state = result.state;
// 记录观察、写 bet 事件、把 paid 从行动方转入底池
if (result.outcome !== 'continue') resolveRound(result.foldedBy);
```

如果动作后还有人要行动，重置截止时间：玩家 30 秒，对手 600 毫秒。超时由 `bet-timeout` 触发，规则是「有应跟则弃牌，无应跟则过牌」。

**4. 一手完整的数值变化**

初始双方各付 1 底注，底池 2：

| 步骤 | 行动 | 行动前应跟 | 最大加注 | 实付 | 底池 | 双方投入 |
|---|---|---|---|---|---|---|
| 1 | 玩家加 1 | 0 | 1 | 1 | 3 | 2 / 1 |
| 2 | 对手反加 2 | 1 | 2 | 3 | 6 | 2 / 4 |
| 3 | 玩家再加 4 | 2 | 4 | 6 | 12 | 8 / 4 |
| 4 | 对手跟注 | 4 | 8 | 4 | 16 | 8 / 8 |

第 4 步 `outcome = showdown`，双方各投 8，底池 16，剩余储备各 17。跟注不会再给对手反加机会——这是规则，不是遗漏。
