## 一、质量体系的三道门

项目把质量守门分成三层，逐层加严：

| 门 | 工具 | 守什么 |
|---|---|---|
| 静态门 | 语法检查、架构检查器、Prettier 格式检查 | 依赖边界、代码风格、语法正确性 |
| 逻辑门 | 202 个 `node:test` 用例 | 规则、引擎、账目、工程检查器本身；不依赖页面 |
| 真实门 | Playwright 浏览器回归、HTTP 资源检查 | 手机/桌面真实操作、资源加载、分享下载 |

`npm run check` 把静态门与逻辑门串成一条流水线：语法 → 架构 → 测试 → 格式 → 构建 → HTTP 资源，**任一步失败即停止**。涉及界面、计时器、存储、事件或导航的改动，还要补做浏览器验收清单里的相关场景。

完整检查报告写入 `output/harness/latest.json`，浏览器报告在 `output/e2e/report/`。

## 二、202 个测试与架构检查

测试数量随项目演进持续增长：早期 48 → 90 → 121 → 134 → 135 → 181 → 202 项。这个增长曲线与功能演进同步——每次加能力，都补上对应回归。

测试覆盖的重点正是项目最「较真」的部分：

- **规则**：牌型比较、点数和、A/JQK 取值、踢脚顺序；
- **引擎**：状态流转、动作身份防重、超时处理、跨重开编号；
- **账目**：50 罐守恒、逐笔重放、灾厄数学（净亏 2s 而非重复计算）、快进拆笔；
- **工程检查器本身**：越界依赖、计算路径、禁止 API 的反例测试。

架构检查覆盖了全部 JS 文件与浏览器模块（最新报告为 118 个语法文件、35 个模块 / 22 层）。测试里还包含**故障注入**：曾故意禁用「确认数字」按钮，确认测试退出码为 1；把首图扩到 300,001 bytes，确认预算检查退出码为 1——验证守门器真的会拦，而不是摆设。

## 三、真实浏览器回归

静态与逻辑测试再全，也代替不了真机。`npm run check:browser` 自动构建后在真实 Chromium 上跑手机与桌面回归：

- **视口矩阵**：phone-390-root、phone-320-subpath、desktop-subpath 三项目；根路径与子路径各跑一遍（子路径对 GitHub Pages 部署尤其重要）。
- **真实操作**：打开页面、构牌、下注、摊牌、终局、查看复盘、分享下载，全链路走通。
- **性能条件**：390×844、1.6 Mbit/s、150 ms 延迟、4× CPU 降速、冷缓存。
- **结果**：早期 64 通过 / 2 跳过；战报改版后 Chromium 81 通过 / 6 跳过。

浏览器回归还验证了分享战报的二维码：用 jsQR 从 4 张最终 PNG 解码链接，全部一致——确保导出的图片真的能被扫出正确地址。

## 四、构建白名单与 HTTP 资源检查

**构建**：`npm run build` 只替换固定输出 `dist/site/`，按白名单复制入口、JS、实际使用的 CSS、运行时 WebP 与分享素材，并生成英文入口 `en.html`。测试、开发依赖、工程文档、设计提案、参考素材都不进产物。

**HTTP 资源检查**：不执行页面脚本，但静态覆盖 HTML 的 `src/href/poster`、CSS 的 `url/@import`、JS 模块导入以及静态图片/字体字符串，已覆盖 56 个资源（早期 30+）。

**已知边界**：HTTP 资源检查不执行脚本，所以对交互的改动仍需按浏览器验收清单补做真机验证；新增 `srcset`、动态拼接资源路径等新加载方式时，必须先扩展检查器并补反例测试。

## 五、性能优化：从 58 MB 到 2 MB

项目做过一轮系统优化，涵盖六件事：手机构牌、发布资源、延后初始化、实操教学、浏览器 CI、分享传播。效果实测如下：

| 指标 | 优化前 | 优化后 |
|---|---|---|
| 发布目录总量 | 约 58.96 MB | 约 2.13 MB（2,125,892 bytes） |
| 运行插画总量 | 约 10.72 MB | 约 1.6 MB（1,616,658 bytes） |
| 模拟手机 LCP | 13,352 ms | 2,788 ms |
| 页面资源传输 | 2,408,481 bytes | 413,851 bytes |
| FCP | 约 2,792 ms | 2,788 ms（基本未变） |

**一个诚实的提醒**：FCP 基本没变，所以不能把「主图加速」说成「文字首屏加速」。项目明确区分了这两件事。测试环境为 Node.js 24.22.1、Playwright 1.62.1、Chromium 151。

## 六、发布流程与 CI

仓库提供两条 GitHub Actions 工作流：一条跑项目检查（CI 徽标），一条跑 GitHub Pages 发布（Pages 徽标）。发布前会执行完整 `npm run check` 与 `npm run check:browser`，通过后才产出站点。

本地开发流程简洁：`npm ci && npm start`，浏览器打开 `http://127.0.0.1:4180`（可用 `AIR_POKER_PORT` 改端口）。游戏通过 HTTP 加载 ES modules，所以必须经本地服务访问，不能直接双击 HTML 文件打开。

协作约定也服务于质量：规则改动必须带测试；不绕过架构检查；提交前跑完整校验；Pull Request 要写清「改了什么、为什么、跑了哪些检查、哪些还没验证」。项目接受 AI 辅助开发，但提交者仍需对改动、测试和事实准确性负责。

## 七、战报分享与降级智慧

终局页或「最近完成局」可点「分享战报」，生成中英预览、**1080×1440 PNG 下载**与试玩链接复制。

**隐私保护**：分享模型只保留公开完成局事实（结果、轮数、账目趋势、烧毁、时长），**不含牌面、未公开数字、动作历史、记录 ID**。二维码版本 4、纠错 Q、含四模块静区，以矢量路径写入 PNG，不请求远程生成服务。

**一个教科书级的降级案例**：桌面端**隐藏**系统分享按钮。原因是真实环境中 Windows 的 `ShellExperienceHost.exe` 会在点击后崩溃，`navigator.share` 假装「成功」但屏幕上什么都没有——这是静默失败，比报错更糟。项目的判断逻辑是：只有 `navigator.share` 存在且（命中粗指针设备或移动端 UA）才显示系统分享，否则保留「保存图片」路径。取消、权限失败、不支持文件分享时，都保留下载或链接回退。

## 八、宣传片：可验证的传播设计

项目还制作了 B 站宣传片，并且把传播也做成了可验证的工程。

**横版主片**《这局扑克，赌的是呼吸》：72 秒、1920×1080、30 fps、中文硬字幕；配色沿用纸白 #f2f0e9 / 墨黑 #151515 / 风险色 #8d2429；音频为原创算法音轨，120 BPM，响度目标 −14 LUFS、真峰值 ≤ −1.5 dBTP，双遍 loudnorm。制作分七步：来源哈希与规则验证 → 时间轴 → 逐帧渲染 → 预览 → 音频生成 → FFmpeg 合成 2160 帧 → 校验。

**竖版 V2**（30 秒）改为中文旁白主导、音乐退背景：旁白用 Edge `zh-CN-YunxiNeural` 云希男声，rate +8%、pitch −2 Hz；九段口播合计约 20.21 秒；音乐在人声期间降约 11.1 dB（侧链压缩），句首前 100 ms 退后、句尾留 60 ms、420 ms 恢复。

| 指标 | V1 音乐版 | V2 旁白版 |
|---|---|---|
| 时长 / 帧数 / 画幅 | 30 s / 900 / 1080×1920 | 相同，视频包 SHA-256 一致 |
| 响度 | −14.21 LUFS | −14.86 LUFS |
| 真峰值 | −3.38 dBTP | −2.13 dBTP |
| LRA | 10.70 LU | 3.40 LU |

**不作虚假宣传**是宣传片的硬约束：不声称多人联机、原作 1:1、必胜 AI、最高胜率或真实生理模拟。V1/V2 视频包哈希一致，保证两版对比是公平的「同画不同声」。

## 九、核心讲解：质量是一种可验证的承诺

把整个质量与传播体系收拢，核心是「可验证」三个字：

- **守门器要被验证会拦**（故障注入确认退出码为 1）；
- **性能数据要写清测试条件**（LCP 条件的网络、CPU、缓存）；
- **AI 强度要有置信区间**（05 篇）；
- **账目要有守恒式**（06 篇）；
- **宣传对比要哈希一致、不伪造数据**；
- **降级决策要基于真实故障**（桌面分享按钮的隐藏来自真实组件崩溃）。

> 这些做法共同指向一种价值观：不说「我们质量保证」，而是给出「在什么条件下、用什么方法、测出什么结果」。这让所有结论都能被复核、被质疑、被复用。

## 十、使用建议与推荐结论

**使用建议：**

1. **把检查串成一条命令**：`npm run check` 一步失败即停，比「记得跑一下」可靠得多。
2. **给守门器做故障注入**：故意造一个坏样本，确认检查真的会失败——否则你不知道守门器是不是摆设。
3. **报性能要带条件**：网络、CPU、缓存状态缺一不可；不同指标（LCP / FCP）不要混着说。
4. **分享功能要查真实降级**：静默失败比报错更伤体验，宁可隐藏功能也不要假装成功。

**推荐结论：**

- 这套质量体系适合**任何需要长期维护、多人协作、可被质疑的开源项目**。它的成本不高（都是标准工具的组合），但回报是一套能被信任的结论。
- 宣传片部分相对独立：如果你做的是「需要向外界讲清项目」的技术作品，它的「可验证传播 + 不伪造数据」思路非常值得学。
- 最值得推荐的一点是**把诚实当工程纪律**：无论是数据、性能还是宣传，项目都选择说清边界而非夸大结论——这是这套体系能被人信任的根本原因。
