## 一、为什么要给游戏做账本

大多数游戏只需要知道「谁赢了」，但空气扑克想让玩家相信「赢得明白」。当 A=1、灾厄烧毁、呼吸开罐、底池退款交织在一起时，玩家很容易怀疑：我的 25 罐到底去哪了？

项目给出六项功能要求（F1–F6），核心可以概括为：

| 要求 | 含义 |
|---|---|
| 完整记录 | 记录整局已接受的选牌、候选、构造尝试、下注与超时、失败重做、耐息、终局；单调序号 + 实际对局毫秒，不截断成 7 条短日志 |
| 逐轮明细 | 保存起止余额、目标、弃牌前后、每次成手与失败原因、真实下注、比较依据、实际收到与烧毁；作废轮不冒充完成 |
| 资金守恒 | 每笔底注、跟注、加注、退款、结算、开罐、灾厄都有唯一账目，能从初始各 25 罐重放到当前余额 |
| 只读可见 | 当前账目可读；未摊牌的对手成手继续隐藏；查询与导出不修改对局 |
| 最近归档 | 只保存最近一局完成局，重开不覆盖，刷新可查看；存储失败不阻断游戏 |
| 可导出 | 账目浮层、回合详情、完整时间线及 JSON 导出，中英同步 |

## 二、守恒式：恒等于 50 罐

整个账本建立在一条简单而强硬的等式上：

```
双方未开余额 + 未结算底池 + 累计已开呼吸罐 + 累计实际烧毁 = 50
```

初始双方各 25 罐，共 50。之后资金只会在这五个「账户」之间转移，或从系统中「 burned 」出去。只有两类事件会减少未开总额：**打开呼吸罐**（转为已开）与**实际灾厄烧毁**（退出系统）。普通结算是守恒的——底池在双方之间转移，不凭空增减。

这条守恒式是账本的「校验和」。任何一处记账错误都会让等式失衡，因此它既是设计约束，也是测试断言。

一个真实浏览器对局的账目证据：完成五轮后共 **44 笔账目**，最终账户为玩家 19、对手 0、底池 0、已开呼吸 25、烧毁 6，合计恰好 50。终局复盘保留 **77 个事件**。

## 三、记录器记什么

引擎在**已接受动作和实际资金写入点**通知记录器（`records`），而不是由记录器自己推测发生了什么。

| 记录维度 | 内容 |
|---|---|
| 事件 id | 单调递增，使用对局 `elapsedMs` 作为时间基准 |
| 轮外事件 | 呼吸与耐息归为 `round=null` |
| 轮次 rounds | 目标、先动方、每次成手及失败原因、下注、结算牌型与踢脚向量、实际收款与 burned、前后余额与弃牌 |
| 尝试 | 双方失败时保留每次尝试；数学无解轮记为 `void`；耗尽时未结束轮记为 `interrupted`；只有 `settled` 计入完成数 |
| 账目 ledger | 以同一 id 关联资金转移，保存 `from`/`to`/`amount`/`reason` 及 before/after 五账户，可连续重放到实际状态 |
| 快进拆笔 | 长时间快进按真实开罐时刻拆笔，不依赖浏览器脉冲频率 |

「按真实开罐时刻拆笔」这条细节很关键：如果快进时把 100 秒的呼吸记成一笔，账目就与实际时间脱节。项目让记录跟随**真实事件时刻**而非**调用频率**。

## 四、账目结构：逐笔可重放

账本的可信度来自「可连续重放」——从初始五账户出发，按顺序应用每一笔 `ledger` 记录，最终余额必须与游戏实际状态一致。

每一笔记录包含：

- **唯一 id**：与对应事件关联；
- **转移信息**：从哪个账户 `from` 到哪个账户 `to`，金额 `amount`，原因 `reason`（底注、追加、退款、底池收款、烧毁、开罐等）；
- **前后快照**：转移前的五账户 `before` 与转移后的五账户 `after`。

因为每笔都带前后快照，你可以抽查任意一笔、任意时刻的账户状态，而不必从头重放全部。这也是为什么「收款不等于净赚」能被清楚表达——账目里分别记录了收款与你的投入。

## 五、公开与隐藏的边界

复盘系统必须处理一个微妙问题：它展示历史，但不能泄露当时还不该知道的信息。

| 状态 | 处理 |
|---|---|
| 对局进行中 | `getRecord()` 隐藏未揭示尝试的对手成手，不包含未来对手数字 |
| 当前未摊牌对手成手 | 保持隐藏 |
| 对局结束后 | 公开实际锁定的尝试 |
| 未出的对手数字 | 始终不记录 |
| 完整记录 vs 短日志 | 完整记录不受牌桌七条短日志限制；双方失败保留每次尝试 |

显示层（`ui/record.js`）只渲染快照与翻译，外来字符串转义。这意味着即使记录数据来自导入或被篡改的来源，也不会造成注入问题（不过项目明确说明：**不提供防篡改认证**，这是能力边界）。

## 六、归档、导出与降级

**归档时机**：`app` 在每个 session 首次进入 `summary` 时保存一次完整记录。`archive`（`browser/record-store.js`）只读写固定键 `air-poker-last-record-v1`，检查版本、基本结构与连续账目，重算派生统计。

**保存策略**：本机只保存**最近一个完成局**，下一局完成后才替换。未完成对局不保存为正式战绩，也不恢复进度。刷新页面不会恢复未完成对局，但可以再次查看已保存的最近完成局。

**降级设计**：存储不可用、版本不支持或数据损坏时，返回状态但**不阻断游戏**；内存中的记录仍可导出 JSON。导出通过浏览器 Blob 下载，查看与导出使用打开时的快照，不暂停计时；刷新按钮主动读取最新状态。

> 这里有个容易被忽视的用户体验：查看记录**不暂停呼吸、不延长行动**。记录是只读窗口，不能变成「暂停游戏的作弊菜单」。

## 七、复盘界面：把事实摆出来

P08 复盘界面是全功能的集中展示：

- 全屏档案浮层，可展开全部轮次与构造尝试；
- 露出完整五张公开牌，给出牌型与踢脚依据；
- 逐笔事件时间线，可播放、暂停、定位；
- 五账户余额与趋势；
- JSON 导出，供玩家自行核对 50 罐去向。

牌桌上的短日志只保留最近 7 条，但复盘不受此限制——这体现了「实时界面求简洁、复盘界面求完整」的分工。

分享战报也建立在这份记录之上：终局页「分享战报」会生成 1080×1440 PNG，但**只保留公开完成局事实**（结果、轮数、账目趋势、烧毁、时长），不含牌面、未公开数字、动作历史或记录 ID（详见 08 篇）。

## 八、核心讲解：记录器只记事实

这一篇最值得带走的，是记录系统的角色定位：**记录器是事实的旁观者，不是决策的参与者。**

- 引擎在动作与资金写入点**通知**记录器，记录器不反推、不干预。
- 记录器不参与对手决策或结算；困难档的自适应观察是另一条独立通道，不从记录器读取。
- 复盘只消费 `getRecord()` 快照，**不重新运行 AI**——你看到的历史就是当时发生的历史。

> 这个定位带来两个好处：一是记录天然可信（没有二次加工），二是系统可解耦（记录失败不影响对局，对局逻辑不依赖记录格式）。相比之下，很多游戏的「回放」是重新模拟一遍，一旦规则改了，旧回放就会失真。

## 九、使用建议与推荐结论

**使用建议：**

1. **做涉及虚拟货币/资源的系统**，务必设计一条守恒式当校验和——它能在测试里第一时间抓出记账错误。
2. **记录要在事实发生点写入**，不要在展示层反推；否则「记录」和「真相」会随版本演进而分叉。
3. **只读查看不要暂停主流程**：把复盘、设置、帮助都设计成不干扰实时状态的窗口。
4. **存储失败要降级**：保留内存副本并允许导出，让「本地存储不可用」不毁掉一局游戏。

**推荐结论：**

- 这套账本是全系列中**最容易直接迁移**到业务系统的设计——任何需要审计、对账、可追溯流水的场景（支付、积分、库存、游戏经济）都能借鉴守恒式 + 逐笔前后快照的思路。
- 它的边界要记清：只存最近一局、不提供防篡改认证、不恢复未完成对局。若业务需要完整历史或合规审计，需要另做持久化与签名，不能照搬。
- 最值得的一句话是「收款不等于净赚」——把这一类容易混淆的概念在账本结构里显式区分，是让系统可信的关键。
