## 一、为什么需要分布式唯一 ID

> 💡 补充：以下是选型背景，归档原笔记未展开。

- 单库自增主键在分库分表、多实例部署下会重复，迁移扩容也困难。
- UUID 全局唯一，但 36 位太长且无序，作主键会导致 B+ 树频繁页分裂、索引膨胀。
- 业务要的 ID 应同时满足：**全局唯一、趋势递增、本地生成、高性能**。

**主流方案对比**：

| 方案 | 有序性 | 依赖 | 吞吐 | 典型问题 |
|---|---|---|---|---|
| UUID | 无序 | 无 | 高 | 太长、索引膨胀、页分裂 |
| 数据库号段 | 趋势递增 | DB | 中 | 强依赖 DB，扩容需协调 |
| Redis 自增 | 递增 | Redis | 高 | 强依赖中间件，持久化风险 |
| 雪花算法 | 趋势递增 | 无 | 极高 | 时钟回拨、workerId 分配 |

- 雪花算法四个目标都占，且不依赖第三方组件，是中小规模系统的默认选择。

## 二、起源与特点

雪花算法（Snowflake）最早是 Twitter 内部使用的分布式环境唯一 ID 生成算法，2010 年开源，开源版本由 Scala 编写。特点是：

- 能满足高并发分布式系统环境下 ID 不重复
- 基于时间戳，保证基本有序递增（有些业务场景对这个有要求）
- 不依赖第三方库或中间件
- 生成效率极高

## 三、结构与原理

算法生成一个 64 位 long 型整数：

| 分段 | 位数 | 说明 |
|---|---|---|
| 符号位 | 1 | 固定 0，保证 ID 为正数 |
| 毫秒时间戳 | 41 | 相对起始纪元计算，约 69 年不重复 |
| 机器标识 | 10 | 1024 节点；常拆成 5 位数据中心 + 5 位机器 |
| 序列号 | 12 | 单节点每毫秒 4096 个 |

```
1 bit    41 bit                   10 bit           12 bit
+------+------------------------+---------------+-----------+
|  0   |    毫秒时间戳（相对）    |    机器标识    |   序列号   |
+------+------------------------+---------------+-----------+
                     机器标识常拆为：5 bit 数据中心 + 5 bit 机器
```

**容量计算**：

- 41 位时间戳：`2^41 ms ≈ 69.7 年`，时间用完后需更换纪元或升级算法
- 10 位机器：`2^10 = 1024` 个节点
- 12 位序列：单节点每毫秒 4096 个，即约 409.6 万 QPS
- 高位是时间戳，所以 ID 整体**趋势递增**，作主键对 B+ 树友好

**生成流程**：

1. 取当前毫秒时间戳，与上次生成时间戳比较
2. 当前 < 上次（时钟回拨）→ 拒绝生成
3. 同一毫秒内 → 序列号自增；溢出（超过 4095）→ 自旋等待下一毫秒
4. 新毫秒 → 序列号归零
5. 四段各自左移后按位或拼接成 64 位 long

## 四、关键问题与应对

**时钟回拨**：

- 雪花算法强依赖机器时钟，NTP 校时或人工调整都会导致回拨，回拨期间可能生成重复 ID
- 最简单策略是原笔记代码的"直接抛异常拒绝生成"
- 常见兜底：小幅回拨自旋等待追平；大回拨报警并拒绝服务；美团 Leaf-snowflake 用 ZooKeeper 存历史最大时间戳做校验

**机器 ID 分配（10 位必须全局唯一，重复即 ID 冲突）**：

| 方式 | 做法 | 适用 |
|---|---|---|
| 手工配置 | 配置文件指定，上线前规划好 | 实例少、部署固定 |
| 数据库分配 | 启动时从 DB 取自增号 | 常见的默认做法 |
| ZooKeeper | 顺序节点编号 | 已有 ZK 的系统 |
| IP / 主机名推导 | 哈希取模映射 | 简单但有碰撞风险 |

**其他固有特点**：

- ID 含时间与机器信息，可反推生成时间和业务量，敏感业务要慎用
- 依赖时钟，是"弱有序"而非严格有序：跨节点无法保证全局有序

> 💡 补充：本节回拨策略与 workerId 分配方式为 AI 归纳的通用实践。

## 五、Java 实现

```java
package com.wychmod.wiki.util;

import org.springframework.stereotype.Component;

/**
 * Twitter的分布式自增ID雪花算法
 **/
@Component
public class SnowFlake {

    /** 起始的时间戳：2021-01-01 00:00:00 */
    private final static long START_STMP = 1609459200000L;

    /** 每一部分占用的位数 */
    private final static long SEQUENCE_BIT = 12; //序列号占用的位数
    private final static long MACHINE_BIT = 5;   //机器标识占用的位数
    private final static long DATACENTER_BIT = 5;//数据中心占用的位数

    /** 每一部分的最大值 */
    private final static long MAX_DATACENTER_NUM = -1L ^ (-1L << DATACENTER_BIT);
    private final static long MAX_MACHINE_NUM = -1L ^ (-1L << MACHINE_BIT);
    private final static long MAX_SEQUENCE = -1L ^ (-1L << SEQUENCE_BIT);

    /** 每一部分向左的位移 */
    private final static long MACHINE_LEFT = SEQUENCE_BIT;
    private final static long DATACENTER_LEFT = SEQUENCE_BIT + MACHINE_BIT;
    private final static long TIMESTMP_LEFT = DATACENTER_LEFT + DATACENTER_BIT;

    private long datacenterId = 1;  //数据中心
    private long machineId = 1;     //机器标识
    private long sequence = 0L;     //序列号
    private long lastStmp = -1L;    //上一次时间戳

    public SnowFlake() {
    }

    public SnowFlake(long datacenterId, long machineId) {
        if (datacenterId > MAX_DATACENTER_NUM || datacenterId < 0) {
            throw new IllegalArgumentException("datacenterId can't be greater than MAX_DATACENTER_NUM or less than 0");
        }
        if (machineId > MAX_MACHINE_NUM || machineId < 0) {
            throw new IllegalArgumentException("machineId can't be greater than MAX_MACHINE_NUM or less than 0");
        }
        this.datacenterId = datacenterId;
        this.machineId = machineId;
    }

    /**
     * 产生下一个ID
     */
    public synchronized long nextId() {
        long currStmp = getNewstmp();
        if (currStmp < lastStmp) {
            throw new RuntimeException("Clock moved backwards.  Refusing to generate id");
        }

        if (currStmp == lastStmp) {
            //相同毫秒内，序列号自增
            sequence = (sequence + 1) & MAX_SEQUENCE;
            //同一毫秒的序列数已经达到最大
            if (sequence == 0L) {
                currStmp = getNextMill();
            }
        } else {
            //不同毫秒内，序列号置为0
            sequence = 0L;
        }

        lastStmp = currStmp;

        return (currStmp - START_STMP) << TIMESTMP_LEFT //时间戳部分
                | datacenterId << DATACENTER_LEFT       //数据中心部分
                | machineId << MACHINE_LEFT             //机器标识部分
                | sequence;                             //序列号部分
    }

    private long getNextMill() {
        long mill = getNewstmp();
        while (mill <= lastStmp) {
            mill = getNewstmp();
        }
        return mill;
    }

    private long getNewstmp() {
        return System.currentTimeMillis();
    }
}
```

代码要点：

- `synchronized` 保证同一节点内的并发安全
- `-1L ^ (-1L << n)` 计算最大值：-1 是全 1，左移 n 位后低位补 0，异或得到低 n 位全 1
- `sequence == 0` 表示本毫秒 4096 个号已用尽，`getNextMill` 自旋到下一毫秒
- 回拨直接抛异常；生产环境可替换为等待追平或报警策略

## 六、在 Java 项目中落地

**方式一：自定义 Bean 注入使用**（原笔记即此方案，`@Component` 注册后直接注入）

```java
@Service
public class OrderService {

    @Resource
    private SnowFlake snowFlake;

    public Long createOrder() {
        long orderId = snowFlake.nextId();
        // ... 下单逻辑，orderId 直接作订单号/主键
        return orderId;
    }
}
```

**方式二：MyBatis-Plus 主键策略**（主流框架直接内置雪花）

```java
@TableId(type = IdType.ASSIGN_ID)   // 默认即 ASSIGN_ID，底层是雪花算法
private Long id;
```

- MP 内置 `IdentifierGenerator` 接口，可自定义 workerId / datacenterId 的取值逻辑
- 主键策略与全局配置详见 [Spring 生态](/md/01-计算机基础/50-Spring生态.md)

**方式三：Hutool 工具类**

```java
long id = IdUtil.getSnowflakeNextId();          // 默认 workerId / datacenterId
long id2 = IdUtil.getSnowflake(1, 1).nextId();  // 手动指定机器
```

> 💡 来自项目笔记：抽奖系统使用 hutool 封装的雪花工具类生成订单号；实际使用雪花算法时常需做优化处理，比如支持时间回拨、手工指定、简短生成长度、提升生成速度等。

**落地注意事项**：

- **前端精度丢失**：64 位 long 超出 JS Number 安全整数范围（2^53 - 1），返回前端必须转 String，详见 [Spring 生态](/md/01-计算机基础/50-Spring生态.md)
- **数据库字段**：对应 MySQL `BIGINT`，排序即按生成顺序
- **workerId 外部化**：容器多副本部署不能写死机器 ID，应从环境变量、配置中心或 DB 分配，否则副本冲突会产生重复 ID

## 七、小结

- 单节点约 409.6 万 QPS，无需中间件，ID 趋势递增，是中小规模系统生成分布式 ID 的默认选择
- 核心风险只有两个：**时钟回拨**与 **workerId 冲突**，落地时优先解决
- 更大规模或有特殊诉求可看增强方案：美团 Leaf（snowflake + 号段模式）、百度 UidGenerator
