# AI 应用从零开发实战

> 预计阅读：约 30 分钟
> 前置阅读：[AI 编程三件套方法论](/md/05-AI与Agent/00-AI编程三件套方法论.md)

## 一、核心概述

这篇文档把三件套落到一个具体场景：从零设计并开发一个简化版 AI Agent 平台 Hify。重点不是 Hify 本身，而是这套流程：

1. 先明确产品边界。
2. 再做功能取舍和技术选型。
3. 把架构、接口、数据库、部署和编码规范写进项目上下文。
4. 最后让 AI 在可验证的任务循环里实现。

## 二、架构师与工程团队

AI 辅助开发里，人是架构师，AI 是工程团队。

| 层级 | 内容 | 处理方式 |
|---|---|---|
| 第一层 | 产品边界、架构决策、技术取舍、跨模块一致性 | 人必须拍板，AI 只做方案对比 |
| 第二层 | 业务代码、接口、前端页面、测试、文档 | AI 生成，人验收 |
| 第三层 | 格式化、样板代码、启动脚本、Makefile | AI 可全权处理，人快速确认 |

三步检查法：

1. 查意图：是不是在解决正确问题？
2. 查质量：代码、测试、文档是否合格？
3. 查边界：有没有越权改动或破坏旧行为？

## 三、从零开发流程

以 Hify 为例，完整流程如下：

| 步骤 | 做什么 | 关键动作 |
|---|---|---|
| 1. 标杆调研 | 梳理 Dify 等产品的核心功能模块 | AI 给的信息不能直接信，要验证 |
| 2. 功能取舍 | 三问裁剪法 + MoSCoW 分层 | 明确做什么、不做什么 |
| 3. 技术选型 | 对比候选方案 | 看开发效率、生态成熟度、SDK 支持、运维复杂度 |
| 4. 应用架构 | 模块化单体 vs 微服务 | 追问依赖关系、循环依赖、维护成本 |
| 5. 代码组织 | 定义分层结构和职责边界 | 具体到 AI 能直接执行 |
| 6. 外部调用 | 设计 LLM 调用容错方案 | 按"慢且不稳定"设计 |
| 7. 部署架构 | 明确组件、流量路径和职责 | 先满足当前规模 |
| 8. 性能瓶颈 | 按严重程度排序 | 只处理一期必须处理的问题 |
| 9. 扩展路径 | 定义后续演进触发条件 | 条件不到不提前复杂化 |
| 10. 数据模型 | 梳理核心表和关系 | 先表名和关系，再展开字段 |
| 11. 数据库规范 | 索引、分页、通用字段 | 建表时一次性写好 |
| 12. 接口规范 | 路径、响应、错误码 | 统一给 AI 执行 |
| 13. 整合上下文 | 生成 `CLAUDE.md` / `AGENTS.md` | 所有决策沉淀为项目规范 |

每一步都是：**先写清楚（SDD），再沉淀进项目上下文（Harness），最后交给任务循环执行（Loop）。**

## 四、Hify 项目边界

Hify 是一个参考 Dify 的简化版内部 AI Agent 平台，目标是一个人开发、本地部署、服务团队内部 20-50 人。

### 4.1 做什么

- 多模型管理：OpenAI、Claude、Gemini、Ollama 等 provider 配置和连通性测试。
- Agent 配置：名称、系统提示词、绑定模型、知识库和 MCP 工具。
- 对话引擎：多轮对话、历史记录、SSE 流式响应。
- 知识库 RAG：文档上传、向量化、相似度检索、上下文注入。
- 简版工作流：开始、LLM、条件分支、工具调用、结束。
- MCP 工具接入：让 Agent 和工作流调用外部工具。

### 4.2 不做什么

- 多租户。
- 自定义插件市场。
- 实时协作。
- 企业 SSO。
- 精细化权限控制。
- 数据集版本管理。

这类功能有价值，但不适合一个人开发的 MVP 第一阶段。

## 五、技术与架构选型

推荐基线：

| 维度 | 选择 |
|---|---|
| 后端 | Spring Boot |
| 前端 | Vue + TypeScript |
| 主数据 | MySQL |
| 缓存 | Redis |
| 向量检索 | PostgreSQL + pgvector |
| 部署 | Docker，生产可上 Kubernetes |
| 架构模式 | 模块化单体，边界清晰，后续可拆微服务 |

模块化单体比一开始上微服务更适合小团队：部署简单、调试方便、事务边界清晰。关键是把模块边界写严，避免单体变成泥球。

## 六、代码组织规范

推荐模块：

```text
com.hify
├── common/
│   ├── config/
│   ├── exception/
│   ├── web/
│   └── util/
├── modules/
│   ├── model/
│   ├── agent/
│   ├── conversation/
│   ├── knowledge/
│   ├── workflow/
│   └── mcp/
└── HifyApplication.java
```

每个业务模块内部统一四层：

```text
modules/{module}/
├── api/       # 对外暴露的接口和 DTO
├── domain/    # 业务逻辑、领域对象、事务边界
├── infra/     # Mapper、RepositoryImpl、外部 API 客户端
└── web/       # Controller，只处理 HTTP 层
```

| 层 | 职责 | 禁止 |
|---|---|---|
| `web/` | 接收请求、参数校验、调用本模块 `api/`、返回统一响应 | 直接调用其他模块 `domain/`，直接操作数据库 |
| `api/` | 定义跨模块调用 interface 和 DTO | 包含业务逻辑实现 |
| `domain/` | 业务逻辑、领域对象、事务边界 | 依赖 web 层 |
| `infra/` | Mapper、RepositoryImpl、外部 API 客户端 | 包含业务逻辑 |

跨模块调用规则：

- 只能通过目标模块的 `api/` 接口调用。
- 跨模块传递使用 `api/` 下定义的 DTO。
- 禁止传 PO 或领域对象。
- 循环依赖视为架构错误，立即重构。

## 七、LLM 调用规范

外部 LLM API 要按"慢且不稳定"设计。

### 7.1 线程隔离

- 非流式调用使用独立 `llmExecutor`。
- 流式 SSE 调用使用独立 `llmStreamExecutor`。
- `CompletableFuture` 必须显式指定线程池，禁止默认 `ForkJoinPool.commonPool()`。

### 7.2 超时层次

| 层级 | 建议 |
|---|---|
| TCP 连接 | connectTimeout 5s |
| 非流式读取 | readTimeout 120s |
| 流式读取 | readTimeout 设为 0，避免 SSE 被读超时切断 |
| 总体兜底 | `CompletableFuture.get(90s)` |

### 7.3 重试、熔断和 fallback

- 普通 LLM 最多 3 次指数退避，Ollama 可适当放宽。
- 只对网络异常和 5xx 重试，4xx 不重试。
- 失败率或慢调用比例过高时触发熔断。
- provider 异常时按配置 fallback，fallback 也失败再抛业务异常。

```yaml
hify.llm.fallback:
  openai: ollama
  claude: openai
  gemini: ollama
```

LLM 调用日志至少记录 provider、model、耗时、token 数、是否命中缓存。

## 八、部署与数据库规范

### 8.1 部署架构

```text
用户浏览器
  ↓
Ingress Nginx（L7 负载均衡 + SSL 终止 + SSE 支持）
  ├── hify-frontend（Vue SPA，Nginx 静态文件服务）
  └── hify-backend（Spring Boot）
        ├── MySQL 8.x
        ├── Redis
        └── PostgreSQL + pgvector
```

SSE 场景下，Ingress 必须关闭缓冲并放宽读取超时：

```yaml
nginx.ingress.kubernetes.io/proxy-read-timeout: "300"
nginx.ingress.kubernetes.io/proxy-buffering: "off"
nginx.ingress.kubernetes.io/limit-rps: "20"
```

### 8.2 MySQL 通用字段

每张表默认包含：

```sql
id          BIGINT      NOT NULL AUTO_INCREMENT,
created_at  DATETIME(3) NOT NULL DEFAULT CURRENT_TIMESTAMP(3),
updated_at  DATETIME(3) NOT NULL DEFAULT CURRENT_TIMESTAMP(3) ON UPDATE CURRENT_TIMESTAMP(3),
deleted     TINYINT(1)  NOT NULL DEFAULT 0,
PRIMARY KEY (id)
```

约定：

- 字符集 `utf8mb4`，排序规则 `utf8mb4_unicode_ci`。
- 金额用 `DECIMAL(19,4)`，不用 `FLOAT` / `DOUBLE`。
- 布尔值用 `TINYINT(1)`。
- `TEXT/BLOB` 字段不建普通索引，需要时用前缀索引或全文索引。

### 8.3 索引与分页

- 区分度低的字段不要单独建索引，应与高区分度字段组合。
- 组合索引遵循最左前缀，等值字段在左，范围字段在右。
- 查询条件中常带 `deleted` 时，应纳入组合索引。
- 对话记录等时间线数据使用游标分页，避免深分页。

```sql
SELECT id, role, content, created_at
FROM t_message
WHERE conversation_id = ?
  AND deleted = 0
  AND (created_at < ? OR (created_at = ? AND id < ?))
ORDER BY created_at DESC, id DESC
LIMIT 20;
```

### 8.4 pgvector

向量表要提前建相似度索引，避免全表扫描：

```sql
CREATE INDEX idx_embedding_ivfflat
ON knowledge_embedding
USING ivfflat (embedding vector_cosine_ops)
WITH (lists = 100);
```

> 💡 补充：归档原文使用 ivfflat 作为示例。实际项目可按数据量、召回率和写入频率评估 HNSW / ivfflat 的取舍。

## 九、接口与编码规范

接口层建议统一：

- 路径使用 RESTful 风格。
- 响应用 `Result<T>` / `PageResult<T>` 包装。
- 分页参数统一命名。
- 空集合返回 `[]`，不要返回 `null`。
- 业务异常统一错误码。

编码纪律：

- Service 接口不加 `I` 前缀，实现类加 `Impl`。
- 表名使用 `t_` 前缀，列名使用 snake_case。
- 业务异常统一抛 `BizException(ErrorCode)`。
- 禁止空 catch、`e.printStackTrace()` 和 `System.out.println`。
- 线程池显式创建，禁止 `Executors.newFixedThreadPool` 这类容易引入无界队列的快捷方法。
- `ThreadLocal` 用完必须 `remove()`。

## 十、性能瓶颈优先级

| 级别 | 瓶颈 | 一期处理方式 |
|---|---|---|
| P0 | LLM API 延迟高（3-30s） | 线程隔离 + 熔断 + fallback |
| P0 | 向量检索无索引全表扫描 | 建向量索引 |
| P1 | 对话消息深分页 | 游标分页 |
| P1 | N+1 查询 | 批量查询，禁止循环单查 |
| P2 | 连接池耗尽 | HikariCP 配置连接上限与等待超时 |

## 十一、开发环境与版本控制纪律

再好的 AI 流程也依赖可回滚的工程环境。

### 11.1 Node 版本管理

- 用 nvm、nvm-windows 或 fnm 管理 Node 版本。
- 项目根目录放 `.nvmrc` 或 `.node-version`。
- 切换项目时先 `nvm use`，避免全局 npm 包和 Node 版本冲突。

### 11.2 每次修改先看 diff

- AI 或自己改完代码后，先看 `git diff`。
- 功能和实验走独立分支。
- 熟悉 `git revert`、`git stash` 等可回滚手段。
- 提交前确认：改了什么、为什么改、能不能回滚。
