# AI 前端设计工程化

> **资料来源**：[讲义：聊聊 AI 时代，前端能联动设计一起做些什么](https://sour-steel-ce8.notion.site/AI-3bdaccc3a5fb80b78270e85c40c05fe9)

---

## 一、核心概述

这份讲义讨论的不是“AI 会不会写前端”，而是更现实的问题：**AI 写出来的页面看起来像，但不一定符合团队真实的组件库、设计规范和验收标准**。

过去，前端拿设计稿写页面，设计师在交付和 Review 中兜底。AI 时代以后，产品、前端或 Agent 可能直接在代码仓库里生成页面，设计师不一定每次都参与。这时如果组件用法、设计规则、验收标准仍然只存在于人的脑子里，AI 就只能凭记忆猜，结果就是“编译通过，页面不对”。

讲义的核心结论可以压缩成一句话：

> **前端和设计要一起做的，不是把规范文档写得更长，而是把人的判断变成 AI 能读、能查、能验的数据。**

## 二、研发链路变了什么

### 2.1 旧链路：设计稿是唯一交接物

传统流程大致是：

```text
产品需求 → 设计师出设计稿 → 前端照稿开发 → 设计/研发 Review → 测试 → 上线
```

这条链路里，设计稿是前端最重要的输入。页面细节如果没写清楚，前端可以问设计师；颜色、间距、字体不对，设计师也能在 Review 时一眼看出来。

### 2.2 新链路：AI 可以直接生成页面

AI 时代的流程可能变成：

```text
产品需求 → AI 在代码仓库生成 UI 分支 → 前端接手/护航 → 测试 → 上线
```

甚至在 PDE 模式里，产品可以直接用 AI 生成 React 页面代码，前端只在后面做护航。

> 💡 补充：**React** 是一个常见前端框架，用来构建网页界面。可以简单理解为“用组件拼页面”的工具。

> 💡 补充：**UI 分支** 是代码仓库里为某个页面或功能单独开的开发线。AI 直接在分支里写代码，后续可以提交 PR 给研发审核。

### 2.3 新问题：AI 会写出“像但不对”的代码

讲义举了一个非常典型的例子：

```jsx
<Button mode="primary" size="large">
```

这段代码看起来像一个按钮，但如果公司内部组件库真实写法是：

```jsx
<Button variant="primary" size="lg">
```

那么 AI 写的 `mode` 和 `large` 就是错的。更麻烦的是，这种错误不一定会被编译器、ESLint 或构建流程拦住。页面能跑，但规范错了。

> 💡 补充：**组件库** 是团队提前封装好的按钮、输入框、弹窗、表格等 UI 零件。前端开发时不应该每次手写一个按钮，而应该使用组件库里的标准按钮。

> 💡 补充：**Props** 是组件的参数。比如按钮的类型、大小、是否禁用，都可以通过 props 控制。

> 💡 补充：**编译通过** 只说明代码语法和类型大体没问题，不代表页面符合设计规范。

## 三、有设计稿时：D2C 怎么做

### 3.1 D2C 是什么

D2C 是 **Design to Code**，意思是“从设计稿生成代码”。以前 D2C 常靠规则引擎或插件，现在 AI 可以辅助理解设计稿并生成页面。

但讲义强调：AI 并不是魔法。**规则引擎解析不了的混乱设计稿，AI 也很难真正解析对**。它只是失败得更像人写的页面，问题更隐蔽。

### 3.2 设计稿要让 AI 看得懂

AI 友好的设计稿要满足三件事：

| 要点 | 通俗解释 | 为什么重要 |
|---|---|---|
| 工程化分组 | 同一块内容要放进同一个容器 | AI 才知道哪些元素属于一组 |
| 结构化布局 | 明确横排、竖排、网格和伸缩规则 | AI 才能生成响应式布局 |
| 合理样式赋值 | 背景、描边、圆角、阴影挂在正确节点上 | AI 才不会拆出一堆奇怪层级 |

比如一个卡片，应该是“一个卡片容器里面有标题、内容、按钮”，而不是很多零散图层漂在画布上。否则 AI 只能按坐标猜，最后容易生成大量绝对定位。

> 💡 补充：**容器** 可以理解为页面上的盒子。网页布局本质上就是大盒子套小盒子。

> 💡 补充：**绝对定位** 是把元素钉死在某个坐标上。它短期看起来能对齐，但屏幕尺寸一变就容易乱。

> 💡 补充：**响应式** 是指页面能适配不同屏幕，比如电脑、平板和手机。

### 3.3 组件库信息要从源码实时查

讲义认为，AI 编造组件属性的根因是：组件真实信息只在源码里，文档、MCP 快照、人的记忆、模型训练数据都可能过期。

更可靠的做法是：

```text
组件源码 index.tsx / styles.ts / demo
        ↓
AST 解析
        ↓
生成组件 JSON 数据
        ↓
同时提供 CLI 和 MCP 给 AI 查询
```

也就是说，AI 生成页面前，不应该凭记忆写组件，而应该像查字典一样查当前仓库真实的组件属性、默认值、子组件和 demo。

> 💡 补充：**CLI** 是命令行工具。这里可以理解为“给 AI 查组件库用的字典命令”。

> 💡 补充：**MCP** 是 Model Context Protocol，模型上下文协议。它能让 AI 以统一方式连接外部工具和数据源。

> 💡 补充：**AST** 是代码被解析后的结构树。用 AST 抽取组件参数，比人工维护文档更可靠。

## 四、无设计稿时：PDE 怎么落地

### 4.1 PDE 不是少一个设计师，而是少一道判断防线

PDE 可以理解为 **Product、Design、Engineering 合流**。在这种模式下，产品同学可能不再等设计师逐迭代出图，而是直接在研发仓库中让 AI 生成前端页面。

问题是：设计师原来用眼睛兜住的风格一致性，现在没有人实时兜底了。

AI 能把页面布局模仿得七八分像，但它不一定知道：

- 公司品牌色到底是哪一个；
- 表格分页应该居中还是右对齐；
- 指标卡的大数字应该用什么字号；
- 哪些场景必须用内部组件，哪些地方可以自绘；
- 管理页、分析页、录入页的布局风格有什么区别。

因此 PDE 能不能落地，取决于设计师的判断能不能提前沉淀成 AI 可查询的规则。

### 4.2 Design Skill 是 AI 的设计手册

讲义把这套规则称为 **Design Skill**。它不是简单的一份设计规范 PDF，而是一组 AI 运行时会读取和执行的材料。

一个完整的 Design Skill 通常包括三类东西：

| 类型 | 作用 | 例子 |
|---|---|---|
| 工作流 | 告诉 AI 先做什么、后做什么 | 先拆页面区域，再匹配配方，最后写代码 |
| 设计规则库 | 告诉 AI 什么场景该长什么样 | 管理列表页、分析页、表单页的布局规则 |
| 组件查询通道 | 告诉 AI 真实组件怎么用 | 用 CLI 查询 Button、Form、Table 的 props |

最重要的规则是：**先路由，再编码**。

也就是 AI 不能拿到需求就直接写整页，而应该先把页面拆成“模板 + 区域”：

```text
页面需求
  ↓
判断页型：管理列表页 / 分析页 / 表单页
  ↓
拆分区域：筛选区 / 表格区 / 分页区 / 操作区
  ↓
每个区域命中唯一设计配方
  ↓
查询组件库
  ↓
生成代码
```

如果某个区域没有命中配方，应该停下来补规则，而不是让 AI 硬写。

> 💡 补充：**Skill** 可以理解为 AI 的专业操作手册。它把“遇到什么情况该怎么做”写成机器能执行的流程。

> 💡 补充：**配方** 是讲义里的比喻，指某类页面或区域的标准做法。比如“带搜索条件和表格的管理列表页”就是一种配方。

## 五、Design Skill 怎么沉淀

### 5.1 先审计真实页面

讲义建议从真实设计稿或真实页面中提取设计值。每个值必须记录三个键：

```yaml
brand-yellow:
  value: "#ffdd00"
  rule: "品牌主色"
  applications:
    - 激活 Tab 的边框
    - 重要指标卡的高亮边框
    - 视图切换激活项的容器背景
```

这三个键分别回答：

| 字段 | 含义 |
|---|---|
| value | 精确数值是多少 |
| rule | 这个值代表什么语义 |
| applications | 它在真实页面哪些地方用过 |

只有颜色值本身是不够的。AI 看到 `#ffdd00`，并不知道它该用在品牌按钮、警告状态，还是指标高亮。必须把“什么时候用”也记录下来。

> 💡 补充：**Token** 是设计系统里的标准值，比如品牌色、主文本色、间距 8px、圆角 4px。可以把它理解成“设计变量”。

### 5.2 不确定的值不要硬归类

讲义强调，审计时最怕的不是漏记，而是乱猜语义。

如果某个颜色只出现过一次，或者暂时不知道它代表什么，就应该放进 `non_token_list` 观察，不要硬说它是“次级背景色”。因为一旦写进规则库，AI 后面会把它当事实使用，错一路。

这和写代码很像：不确定的抽象不要提前抽，先保留证据。

### 5.3 规则库分层，而不是把所有资料丢给 AI

讲义否定了两个看似省事的办法：

- 把组件文档全部灌进 RAG；
- 把所有场景记录一次性塞给 AI。

原因是：组件文档会过时，应该实时查源码；场景记录太多，而且只说明“这一页用了什么”，不说明“什么场景应该用什么”。

更好的做法是把规则库拆成层级：

| 层级 | 回答的问题 | 例子 |
|---|---|---|
| global | 全局基础规则 | 颜色档位、字体、间距 |
| micro | 小元素规则 | 标签、状态点、分隔线 |
| organism | 区域规则 | 筛选区、表格区、指标卡 |
| template | 页面模板 | 管理列表页、分析页、录入页 |
| blueprint | 本次页面蓝图 | 当前需求拆出来的页面结构 |

组件本身不放进这栋规则库，而是通过 CLI 实时查。这样可以避免“设计规则是静态的、组件属性是动态的”混在一起。

> 💡 补充：**RAG** 是 Retrieval-Augmented Generation，检索增强生成。简单说，就是让 AI 先去资料库搜索，再根据搜到的资料回答。

## 六、生成后怎么验收

### 6.1 Lint 只能抓一部分问题

最基础的检查可以用 lint 完成，比如：

- 代码里不能裸写 `#ffdd00`，必须使用设计 token；
- Button 的 `variant` 只能是允许的值；
- 禁止绕过组件库手写已有组件。

但 lint 只能检查“代码里写没写错”，不能判断“这个地方该不该用这个设计值”。

> 💡 补充：**Lint** 是代码规则检查工具。它像自动阅卷机，能抓明确规则，但抓不了所有设计判断。

### 6.2 自动视觉验收不是截图找不同

很多人以为视觉验收就是截图 diff：把设计稿截图和页面截图叠起来，看像素差多少。

讲义说这不够准确。因为真实页面的数据可能不同，不能只按像素比。

更可靠的方式是：

```text
AI 负责认角色
程序负责算数值
```

例如：

```text
AI 判断：这几个节点是一组“评分标签”
程序测量：两个标签之间当前距离是 6pt
规则要求：评分标签横向间距应该是 8pt
验收结果：差 2pt，超过容差，FAIL
```

这样输出的不是“这里有点挤”，而是可以定位、可以修复、可以复检的问题。

> 💡 补充：**截图 diff** 是逐像素比较两张图。它适合静态页面，但遇到真实业务数据、动态内容时容易误判。

> 💡 补充：**语义节点** 是页面上有业务含义的元素，比如“评分标签”“指标卡”“筛选按钮”。

> 💡 补充：**几何测量** 是程序测量元素的位置、宽度、高度和间距。

### 6.3 AI 不能自己改标准答案

讲义还提到一个很关键的工程约束：AI 可以修页面，但不能为了让报告变绿去改验收标准。

换句话说：

- 把页面代码里的错误颜色改成规范颜色，这是改答卷；
- 把规范里的目标颜色改成当前错误颜色，这是改标准答案。

后者必须被禁止。

## 七、术语速查

| 术语 | 通俗解释 |
|---|---|
| React | 用组件构建网页界面的前端库 |
| JSX | React 里像 HTML 一样写页面结构的语法 |
| 组件库 | 团队封装好的按钮、表格、表单等 UI 零件库 |
| Props | 传给组件的参数，比如大小、颜色、类型 |
| D2C | Design to Code，从设计稿生成代码 |
| PDE | Product、Design、Engineering 合流，产品/设计/研发边界变得更融合 |
| CLI | 命令行工具，这里用于查询真实组件信息 |
| MCP | 让 AI 连接外部工具和数据源的协议 |
| Skill | 给 AI 使用的一套专业规则和工作流 |
| Token | 设计系统里的标准变量，比如品牌色、字号、间距 |
| RAG | AI 先检索资料，再基于资料生成答案 |
| AST | 代码被解析后的结构树，适合从源码提取真实信息 |
| Lint | 自动代码规则检查 |
| 视觉验收 | 检查页面是否符合设计规范 |
| 幻觉 | AI 一本正经编出不存在或不准确的信息 |

## 八、学习总结

这篇讲义对个人学习的价值在于：它把“AI 写前端”从工具技巧提升到了工程体系。

如果只把 AI 当成页面生成器，最终会反复遇到三类问题：

1. 组件属性写错；
2. 设计风格漂移；
3. 页面生成后没人能稳定判断对错。

真正可持续的做法是：

```text
输入能解析：设计稿结构化
规则能查询：组件库 CLI + Design Skill
结果能测量：lint + 视觉验收
```

缺任何一环，AI 都会退回“看起来很像，但不一定对”的状态。

对不熟前端的人来说，可以先记住这句话：

> **AI 前端工程化的关键不是让 AI 多写代码，而是让 AI 少猜。**
