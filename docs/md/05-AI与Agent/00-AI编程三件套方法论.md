# AI 编程三件套方法论

> 预计阅读：约 15 分钟
> 阅读建议：先读本文建立框架；工具链细节看 [AI 编程工具链与上下文工程](/md/05-AI与Agent/05-AI编程工具链与上下文工程.md)，从零开发流程看 [AI 应用从零开发实战](/md/05-AI与Agent/06-AI应用从零开发实战.md)。

## 一、核心结论

AI 时代程序员的核心竞争力，不再是手速或语法记忆，而是**判断力 + 驾驭 AI** 的能力。三件套方法论把这套能力拆成三个工程问题：

| 方法 | 解决的问题 | 关键产物 |
|---|---|---|
| SDD（Spec-Driven Development） | 想清楚 | spec、边界、验收标准 |
| Harness Engineering | 做对 | 指令、工具、上下文、子代理 |
| Loop Engineering | 自动做 | 计划、执行、观察、验证循环 |

一句话理解：**SDD 负责定义目标，Harness 负责限制行为，Loop 负责持续推进。**

## 二、为什么需要三件套

代码生成的边际成本正在下降，但工程本质没有变。真正难的仍然是业务理解、系统设计、架构权衡、复杂调试和技术选型。

大项目里直接让 AI 写代码，经常卡在三个问题上：

1. **上下文断裂**：代码太多，AI 记不住全局，容易改坏相邻模块。
2. **需求表达失真**：一句"做一个登录功能"，不足以约束安全策略、接口风格和数据边界。
3. **缺少增量验证**：大功能不能一次写完，每一步没有验证，错误会持续累积。

> 💡 补充：这三个问题不是"换更好的模型"就能解决的。模型能力越强，越需要清晰的规格、上下文和验证回路。

## 三、三件套分工

### 3.1 SDD：先把需求写成可执行规格

SDD 的核心是把"想清楚"变成 AI 能读懂、能执行、能验收的格式。

一份可用的 spec 至少要写清：

- 要解决的问题和目标用户。
- 功能范围：做什么、不做什么。
- 输入、输出、接口和数据约束。
- 边界条件、异常路径和验收标准。
- 依赖、兼容性、安全和性能要求。

SDD 与 TDD 的关系：

| 方法 | 先写什么 | 解决什么问题 | 适用阶段 |
|---|---|---|---|
| SDD | 要做什么、为什么、边界是什么 | AI 到底该做什么 | 0 -> 1 |
| TDD | 什么结果才算正确 | AI 做得对不对 | 1 -> 2/3 |

实战中可以先用"三问裁剪法"收敛范围：

1. 没有它，产品还成立吗？
2. 做到什么程度就够用？
3. 能不能一句话说清楚？

再用 MoSCoW 分层落地：

| 层级 | 含义 | 处理方式 |
|---|---|---|
| Must 必须做 | 没有它产品不成立 | MVP 第一版必须有 |
| Should 应该做 | 重要，但可以简化 | 第一版做轻量版，或第二版做 |
| Could 可选做 | 有价值但不紧急 | 有余力再做 |
| Cut 先砍掉 | 对当前约束不划算 | 不进入 MVP |

### 3.2 Harness Engineering：给 AI 搭可靠工作环境

Harness 解决"做对"的问题。它不是单个提示词，而是让 AI 在一个受约束的工程环境里工作。

| 支柱 | 作用 | 落地形式 |
|---|---|---|
| System Prompt | 行为规范 | 编码风格、技术栈、安全规则 |
| Tools | 能力边界 | 文件、命令、数据库、浏览器、MCP |
| Context | 上下文管理 | `AGENTS.md` / `CLAUDE.md`、设计文档、任务记录 |
| Subagents | 并行分治 | 复杂任务拆给独立子代理处理 |

`AGENTS.md` / `CLAUDE.md` 是最常见的 Harness 载体。它应该具体到 AI 能执行，例如：

- Controller 只做参数校验和调用 Service，不写业务逻辑。
- Service 处理事务、业务规则和数据校验。
- Mapper 只做数据库操作，不在 XML 里写复杂业务判断。
- 跨模块调用只能走目标模块的 `api/` 接口，禁止直接 import 其他模块的 `domain/` 或 `infra/`。

工具、记忆、规则文件、Skill、Plugin、Headless 等细节见：[AI 编程工具链与上下文工程](/md/05-AI与Agent/05-AI编程工具链与上下文工程.md)。

### 3.3 Loop Engineering：控制 AI 的执行循环

Loop Engineering 的核心是设计并控制 ReAct 循环：

```text
Thought -> Action -> Observation
        -> 循环直到任务完成
```

关键机制：

- **Plan Mode**：先规划，后执行。适合架构调整、批量改动和有风险的操作。
- **Hooks**：在执行前后插入检查、日志、格式化、测试或拦截。
- **Headless Mode**：把重复任务放到脚本或 CI 中无人值守运行。
- **增量验证**：每一步都能跑测试、查 diff、回滚或继续。

Loop 不是让 AI 不受控制地跑，而是让它在明确目标、可观测结果和验证门禁里持续推进。

## 四、推荐工作流

一个完整的 AI 辅助开发流程可以这样组织：

| 阶段 | 主要动作 | 三件套角色 |
|---|---|---|
| 需求澄清 | 写 spec、问边界、定验收标准 | SDD |
| 任务拆分 | 把大需求拆成可验证任务 | SDD + Loop |
| 上下文准备 | 更新 `AGENTS.md` / `CLAUDE.md`、补设计文档 | Harness |
| 执行实现 | 按任务改代码、生成测试、更新文档 | Loop |
| 验证收敛 | 跑测试、查 diff、修边界、追加记录 | Harness + Loop |

拿到 AI 输出后，按这个顺序检查：

1. **意图**：它是不是在解决正确的问题？
2. **质量**：代码、测试、文档是否达到项目标准？
3. **边界**：有没有越权改动、破坏旧行为或引入隐性依赖？

## 五、角色分工

AI 辅助开发里，人更像架构师，AI 更像工程团队。分工可以按三层看：

| 层级 | 内容 | 人的参与 |
|---|---|---|
| 第一层 | 产品边界、架构决策、技术取舍、跨模块一致性 | 必须人拍板，AI 只给方案对比 |
| 第二层 | 业务代码、接口、页面、测试、文档 | AI 做，人验收 |
| 第三层 | 格式化、样板代码、简单重构、启动脚本 | AI 可全权处理，人快速扫一眼 |

硬标准：**任何一行进入主分支的代码，都要能说清楚它在干什么。**

## 六、常见坑

1. **把 AI 当搜索引擎用**

   AI 给的信息不能直接信。技术选型、竞品分析、第三方 API 行为都要验证。

2. **需求描述过短**

   "做一个登录功能"不够。要写清认证方式、权限模型、token 过期、失败锁定、接口返回和审计日志。

3. **让 AI 一次做完整个大功能**

   大功能必须拆任务，每一步都能验证。没有验收点，Loop 只会放大错误。

4. **不沉淀项目上下文**

   每次对话都重新解释项目，AI 会反复忘。项目规则、架构约定和验证脚本应写进仓库。

5. **忽视外部 LLM 的不稳定性**

   LLM API 慢、贵、会失败。生产系统要做线程隔离、超时、重试、熔断和 fallback。
