# AI 编程三件套方法论

> 预计阅读：约 96 分钟（正文约 30543 字）
> 阅读建议：建议分两次阅读：先看概览、结论和关键表格，再按需翻文末原文归档。

## 一、核心主题概述

AI 时代程序员的核心竞争力，不再是手速或语法记忆，而是**判断力 + 驾驭 AI** 的能力。三件套方法论把这套能力工程化落地：

- **SDD（Spec-Driven Development）**：先把需求想清楚、写清楚，再让 AI 执行。
- **Harness Engineering**：给 AI 搭一个可靠的工作环境，让它不乱、不断、不出轨。
- **Loop Engineering**：让 AI 自主跑起来，最小化人工干预。

三者分别解决 **"想清楚""做对""AI 自动做"** 的问题。本文档同时融合了项目实战中的落地经验，包括如何用 `CLAUDE.md` 沉淀规范、如何组织模块化单体、如何处理 LLM 外部调用等。

## 二、时代背景：AI 改变了什么

### 2.1 软件工程的变化

| 工作 | 之前 | 之后 |
|---|---|---|
| 写一个 CRUD API | 2-3 小时 | 描述清楚，AI 10 分钟完成 |
| 写单元测试 | 1-2 小时 | Harness + AI，15 分钟 80% 覆盖率 |
| 从零搭框架 | 1-2 天 | Spec Kit，当天跑通 |
| 文档整理 | 半天 | AI 读代码自动生成，30 分钟 |
| Code Review | 看语法风格 | AI 做，人专注逻辑和架构 |

代码生成的边际成本趋近于零，但变化的是**执行方式**，不是**工程本质**。

### 2.2 没变的东西——这些才是判断力所在

- **系统设计**：模块划分、接口定义、数据流向，仍由人决策。
- **架构权衡**：一致性 vs 可用性、耦合 vs 扩展性，没有标准答案。
- **业务理解**：知道要解决什么问题，比知道怎么解决更难。
- **调试复杂问题**：分布式竞态、内存泄漏、边界 bug，AI 猜，人验证。
- **技术选型**：Spring Boot vs Quarkus、Kafka vs RocketMQ，懂底层才能选对。

> 💡 补充：AI 工具进化的速度，远快于这些判断能力被替代的速度。投资判断力比投资快捷键更保值。

### 2.3 三种程序员，三种结局

- **60% 原地踏步**：用了 AI 但没改变工作方式，效率提升 10-20%。
- **30% 工具依赖**：熟练用 AI 工具，能做小项目，遇到企业级复杂度就卡。
- **10% 能力跃迁**：改变思维和工作方式，把 AI 用在设计 + 执行双层，能主导复杂项目。

差异不在于用了什么工具，而在于**改没改变思维方式和工作方式**。

### 2.4 大项目用 AI 抓瞎的根因

不是 AI 不够强，是三个问题没解决：

1. **上下文断裂**：代码太多，AI 记不住全局。改了 A 模块，不知道 B 模块的依赖。
2. **需求表达失真**："做一个登录功能" 写出来不符合你的架构规范和安全策略。
3. **无法增量验证**：大项目不能一次写完。每步没有验证机制，错误累积，越到后面越难纠。

> 💡 补充：这三个问题不是"换更好的 AI"能解决的，需要方法论。

### 2.5 程序员的路径变化

| 维度 | 之前 | 之后 |
|---|---|---|
| 执行 | 手撸代码 | 驾驭 AI |
| 工作量度量 | 代码量 | 思考质量 |
| 能力判定 | 会写 | 会驾驭 |

**目的没变**：比别人更快更好地实现功能；从业务需求出发设计系统；在复杂大项目中发挥判断力。**到达路径变了**：从手撸代码执行，变成驾驭 AI 执行。

## 三、三件套方法论

### 3.1 SDD（Spec-Driven Development）

**核心**：先把要做的事写清楚，再让 AI 做。不是多一个步骤，是把"想清楚"变成 AI 能读懂的格式。

**流程**：

1. **先写 spec**：接口定义、约束、边界。
2. **Clarify**：AI 主动找模糊点，你回答，spec 更新。
3. **`/tasks → /implement`**：逐任务执行，每步可验证，错误不累积。

**与 TDD 的关系**：

| 方法 | 先写什么 | 解决什么问题 | 适用阶段 |
|---|---|---|---|
| SDD | 要做什么、为什么、边界 | AI 到底该做什么 | 0→1 |
| TDD | 什么结果才算正确 | AI 做得对不对 | 1→2/3 |

最好的流程是**用 SDD 收敛需求，用 TDD 锁住行为**。

**反例（没有 SDD）**：

```
"帮我做一个 Agent 模块"   → 写了，接口不对
"要能接 Spring 的"        → 改了，和数据库层冲突
"算了我自己改吧"         → 改完，AI 下次还是不记得
```

> 💡 补充：实战中的"三问裁剪法"可以帮助写 spec 前先做功能取舍：没有它产品还成立吗？做到什么程度够用？能不能一句话说清楚？

功能取舍可配合 **MoSCoW 分层**落地：

| 层级 | 含义 | 应该怎么做 |
|---|---|---|
| **Must 必须做** | 没有它产品不成立 | MVP 第一版必须有 |
| **Should 应该做** | 重要，但可以简化 | 第一版做轻量版，或第二版做 |
| **Could 可选做** | 有价值但不紧急 | 有余力再做 |
| **Cut 先砍掉** | 对当前约束不划算 | 不进入 MVP |

### 3.2 Harness Engineering

**核心**：给 AI 搭建可靠的工作环境，由四个支柱组成：

| 支柱 | 作用 | 落地形式 |
|---|---|---|
| **System Prompt** | 行为规范 | 项目级约定：编码风格、技术栈、安全规则 |
| **Tools** | 能力边界 | MCP 协议 + 自定义工具（文件、DB、API 调用） |
| **Context** | 上下文管理 | CLAUDE.md / AGENTS.md，让 AI 始终知道项目结构、依赖、进度 |
| **Subagents** | 并行分治 | 复杂任务拆子任务，多 Subagent 并行，主 Agent 协调 |

**CLAUDE.md 是 Harness 的核心落地载体**。一份完整的项目级上下文通常包含：

```markdown
## 项目概述
- 做什么、不做什么
- 团队规模、部署方式
- 技术栈

## 架构设计
- 应用架构（模块化单体 / 微服务）
- 代码组织规范
- 外部调用处理
- 部署与运维预期
- 缓存策略

## 数据库规范
- 通用字段、索引规则、分页规则
- 大表预判、pgvector 规范

## 接口规范
- RESTful 路径、统一响应、分页、错误码

## 行为指令
- 写代码时、改代码时、不确定时
```

代码组织要具体到 AI 能直接执行。例如分层规则：

- **Controller** 只做事：参数校验和调用 Service，不写业务逻辑、不做数据查询、不处理事务。
- **Service** 处理所有业务逻辑，包括事务管理、数据校验、业务规则。
- **Mapper** 只做数据库操作，不在 XML 里写复杂业务判断。
- **Entity** 和数据库表一一对应；**DTO** 控制暴露字段，不要把 Entity 直接返回给前端。

> 💡 补充：跨模块调用只能走目标模块的 `api/` 接口，禁止直接 import 其他模块的 `domain/` 或 `infra/` 类，循环依赖视为架构错误。

### 3.3 Loop Engineering

**核心**：让 AI 自主跑起来，最小化人工干预。本质是**设计并控制 ReAct 循环**的工程方法。

**ReAct 循环**：

```
Thought → Action → Observation
        ↻ 循环直到任务完成
```

**三个关键机制**：

- **Hooks**：在循环每步前后插入验证、日志、条件判断（pre / post 钩子）。
- **Plan Mode**：AI 先规划再执行，人工审批计划。
- **Headless Mode**：无人值守运行，接入 CI/CD pipeline。

**Claude Code 工具地图**：

| 工具 | 用途 |
|---|---|
| **CLAUDE.md / AGENTS.md** | 项目级 AI 行为规范，所有 session 共享 |
| **Skills / Slash Commands** | 可复用工作流，团队统一操作路径 |
| **Subagents** | 并行子任务执行，复杂项目分治 |
| **Hooks** | 事件驱动的自定义处理，pre / post 钩子 |
| **Plan Mode / Permission** | AI 先规划后执行，人工审批 |
| **MCP** | 外部工具接入：数据库、浏览器、第三方服务 |
| **Worktrees / Headless** | 多分支并行开发，无人值守模式接入 CI/CD |

> 💡 补充：这些不是可选项，是 Loop Engineering 的执行层。

### 3.4 Claude Code / Codex 配置分层

这套配置体系，本质上是在讲两条线：**机器可执行的配置**，以及**写给 AI 看的项目说明**。最容易记的方式是按这四个层级看：`User` = 个人默认，`Project` = 团队共享，`Local` = 这个仓库的个人覆盖，`Session` = 当前这次临时试验。

| 内容 | Claude Code 的位置 | 该放级别 | 一句话理解 |
|---|---|---|---|
| 常规设置 / 权限 / Hooks / env | `~/.claude/settings.json`、`.claude/settings.json`、`.claude/settings.local.json` | User / Project / Local | 这是机器直接执行的配置 |
| MCP 服务器 | `~/.claude.json`、`.mcp.json` | User / Project | 个人状态和本地 MCP 常在 `~/.claude.json`，团队共享 MCP 放 `.mcp.json` |
| 记忆与项目约定 | `~/.claude/CLAUDE.md`、`CLAUDE.md` / `.claude/CLAUDE.md`、`CLAUDE.local.md` | User / Project / Local | 这是写给 Claude 看的说明，不是硬限制 |
| Subagents | `~/.claude/agents/`、`.claude/agents/` | User / Project | 可复用的子代理 |
| 会话级临时项 | `claude --model`、`/model`、`/config key=value`、`outputStyle` | Session / CLI | 只对当前会话最重要 |

**两个小规则：**

- `CLAUDE.md` 是软指令，不是强制开关。
- `model` 和 `outputStyle` 更接近会话级，`outputStyle` 改完通常要 `/clear` 或新开会话。

**Codex 里有没有类似设计？** 有，而且更清楚地拆成两块：

| Codex 里的对应 | 位置 | 级别 |
|---|---|---|
| 配置 | `~/.codex/config.toml`、`.codex/config.toml`、CLI flags、profile | CLI flags > project > profile > user > system > defaults |
| 指令 | `~/.codex/AGENTS.md`、仓库 `AGENTS.md`、`AGENTS.override.md` | global / project / local override |
| 能力扩展 | skills / plugins / hooks / MCP / subagents | 独立能力层 |

> 💡 补充：Codex 的项目级 `.codex/config.toml` 只在 trusted 项目里生效；`AGENTS.md` 更像 Claude Code 的 `CLAUDE.md`，负责约定怎么做事。

### 3.5 Claude Code 自动记忆（Auto-memory）

> 内容基于 Claude Code 官方记忆文档（code.claude.com/docs/en/memory，2026-08 查阅）与本机 v2.1.126 二进制实现核对。

上一节 3.4 里的「记忆与项目约定」讲的是 `CLAUDE.md`——**你写给 Claude 看的说明**。本节讲的是它的另一半：**Auto-memory**——Claude 自己写的笔记，跨会话积累你的纠正与偏好，不需要你手动维护。

| 对比维度 | CLAUDE.md | Auto-memory |
|---|---|---|
| 谁写 | 你 | Claude 自己 |
| 内容 | 指令与规则 | 学到的经验与偏好 |
| 作用域 | 项目 / 用户 / 组织 | 每个仓库一份 |
| 何时加载 | 每次会话 | 每次会话（MEMORY.md 前 200 行或 25KB） |

两者互补：CLAUDE.md 管「该怎么做」，auto-memory 管「我学到的东西」。

**存储位置与加载机制**

- 每个仓库一份：`~/.claude/projects/<项目>/memory/`，git 仓库下所有 worktree / 子目录共享。
- 目录内是 `MEMORY.md`（索引）+ 若干主题文件（如 `debugging.md`）。每次会话只加载 `MEMORY.md` 前 200 行或前 25KB（先到者），主题文件按需读取。
- 记忆**仅本机**，不跨机器/云端同步；不受 `cleanupPeriodDays` 会话清理影响，除非主动删改。

**开启与关闭**

| 操作 | 方式 |
|---|---|
| 查看/管理 | 会话内 `/memory`（含开关 auto-memory、打开记忆文件夹、直接编辑文件） |
| 会话内开关 | `/toggle-memory` |
| 永久关闭 | 用户或项目 settings 设 `"autoMemoryEnabled": false` |
| 环境变量关闭 | `CLAUDE_CODE_DISABLE_AUTO_MEMORY=1` |
| 自定义目录 | settings 键 `autoMemoryDirectory`（支持 `~/` 前缀） |

> 💡 补充：官方文档的自定义目录键是 `autoMemoryDirectory`（不是 `memoryPath`——后者只是内部实现属性）；`autoMemoryDirectory` 放项目 `.claude/settings.json` 时按 workspace trust 规则处理。

**什么时候会写入**

没有固定规则，Claude 按四类记忆自行判断「值不值得记」：

| type | 写入时机 |
|---|---|
| `user` | 得知你的角色、专长、工作偏好 |
| `feedback` | 你纠正了做法，或确认了某个非显然的做法有效（确认类更隐蔽，同样值得记） |
| `project` | 谁在做什么、为什么、截止时间——无法从代码/git 推导的信息；相对日期转绝对日期 |
| `reference` | 外部系统信息的位置（issue 跟踪、dashboard、频道等指针） |

**不写入**：代码结构/约定/文件路径（读代码即得）、git 历史（`git log` 是权威）、调试修复配方、CLAUDE.md 已记录内容、临时任务细节。写入前查重：已有文件覆盖同一事实就更新而非新建，记错就删。

**排查与坑**

- `/context` 查看实际加载进当前会话的记忆文件清单。
- 界面出现 "Saved / Recalled N memories" 即 Claude 正在读写记忆。
- `MEMORY.md` 接近 200 行/25KB 上限时会被提醒精简；超限写入报错，超出的部分下次加载会被丢弃。
- 记忆是「当时为真」的快照：记忆里命名的文件/函数可能已改名或删除，推荐前要验证，冲突时以现状为准并更新过期记忆。
- 子代理（subagent）有独立记忆目录，不加载主对话记忆；fork 会继承。

### 3.6 Claude Code 规则文件与路径作用域（Rules & paths）

> 内容基于 Claude Code 官方记忆文档（code.claude.com/docs/en/memory，2026-08 查阅）；本机 v2.1.126 版本较旧，部分边界行为以新版本为准。

3.4 讲 CLAUDE.md、3.5 讲 Auto-memory，本节是第三个记忆载体：**`.claude/rules/*.md` 规则文件**。它把「写给 AI 的说明」拆成多个主题文件，并可用 `paths` 字段**按文件范围懒加载**——只处理匹配文件时才进上下文，省 token。

| 对比维度 | 无条件规则 | 路径作用域规则（带 `paths`） | Skill |
|---|---|---|---|
| 位置 | `.claude/rules/*.md`（无 `paths`） | `.claude/rules/*.md` | `.claude/skills/<name>/SKILL.md` |
| 何时加载 | 每次会话启动 | 读取到匹配文件时 | 显式调用或判定相关时 |
| 适用 | 全局约定、风格、安全红线 | 只对某类文件/目录有意义的约定 | 任务型工作流、发布清单、参考手册 |

**触发规则：**

- 带 `paths` 的规则仅在 Claude **读取**（不是每次工具调用）匹配 glob 的文件时加载；触发后本次会话常驻。
- glob 按文件相对路径比对，支持 `**`、`*`、`{a,b}` 大括号展开。
- 与根 CLAUDE.md 的关键差异：`/compact` 后根 CLAUDE.md 会从磁盘重读，带 `paths` 的规则和子目录 CLAUDE.md **不会自动重新注入**，需等下次读到匹配文件。

| glob 模式 | 匹配 |
|---|---|
| `**/*.ts` | 任意目录下所有 .ts |
| `src/**/*` | src/ 下所有文件 |
| `*.md` | 项目根目录的 .md |
| `src/components/*.tsx` | 特定目录下的组件 |

**用法判断：** 「只在碰这类文件时需要」→ 带 `paths` 的规则；「任何会话都该知道」→ 根 CLAUDE.md 或无条件规则；「偶尔查一下的任务型流程」→ skill（按调用加载，最省）。

**大需求记忆场景**：把某个大型需求/功能的「设计决策、踩坑、约定」做成带 `paths` 的规则，限定到该需求的文件范围——不迭代它时零成本，一读相关文件就自动加载。注意：触发靠「读文件」而非「话题提到」；超长需求规格建议规则里只放指针、正文指向真正的需求文档。

> 💡 补充：`paths` 整个列表共享 1000 个展开模式 / 4 MiB 预算；无效 `[` 模式匹配不到任何文件（v2.1.207 前会导致 Read 失败）；符号链接路径匹配需 v2.1.198+。这些边缘行为在旧版本（如本机 2.1.126）上可能不一致。

### 3.7 Claude Code 扩展机制速查（五大件）

> 一句话记忆：**Subagent 解决上下文限制问题，Skill 解决同一段话反复粘贴，Hook 解决模型不听话，MCP 解决 Agent 调用外部系统能力，Plugin 解决团队配置问题。**

| 机制 | 解决什么 | 一句话理解 | 位置 | 何时生效 |
|---|---|---|---|---|
| Subagent | 上下文限制 | 大任务拆给独立子代理，各占独立上下文，避免主对话被撑爆 | `~/.claude/agents/`、`.claude/agents/` | 按需委派（可并行） |
| Skill | 同一段话反复粘贴 | 把固定流程/知识打包成按需加载的指令文件，不再手动重复输入 | `.claude/skills/`、`~/.claude/skills/` | 显式调用或判定相关时 |
| Hook | 模型不听话 | 在固定生命周期事件强制执行脚本，是硬约束，软指令失效时的兜底 | settings 的 `hooks` 键 | 事件触发（如 PreToolUse） |
| MCP | Agent 调用外部系统 | 接入外部工具/服务，扩展 Tools 能力 | `.mcp.json`、`~/.claude.json` | 工具调用 |
| Plugin | 团队配置问题 | 把技能/命令/MCP 打包分发，团队一键启用同一套扩展 | 插件市场 | 启用即生效 |

> 💡 补充：这条口诀是 §3.2 Harness 四支柱落到 Claude Code 具体机制后的记忆锚点——Skill 与 Hook 都是「写给 AI 的说明」，区别在 Skill 是软指令（按需加载），Hook 是硬执行（强制生效）；MCP 是 Tools 的外部扩展；Subagent 是 Context 的隔离手段；Plugin 是把以上能力打包分发的载体。

### 3.8 Skill 与 Plugin：能力 vs 打包分发单位

> 一句话记忆：**Skill 是一种「能力」（内容），Plugin 是「打包 + 分发单位」（容器）。** Plugin 可以装多个 skill，但 skill 只是 Plugin 可能装的东西之一——Plugin 还能带命令（commands）、hooks、MCP 配置、subagents。

| 维度 | Skill（技能） | Plugin（插件） |
|---|---|---|
| 本质 | 单个可复用能力 | 打包分发单位 |
| 组成 | `SKILL.md` + 辅助文件 | manifest + **多个 skill + 命令 + hooks + MCP + subagents** |
| 安装方式 | 放进 `.claude/skills/` 就可用 | 通过 `/plugin` + marketplace 安装 |
| 分发方式 | 复制文件夹 / git / 软链（手动） | marketplace / 插件仓库（托管、带版本） |
| 启用 | 放进去即生效（`skillOverrides` 可关） | `enabledPlugins` 一键启用整包 |
| 团队共享 | 每人手动复制 | 团队 settings 一条配置，全员统一 |
| 加载 | 按需加载（调用或判定相关时） | 启用后，其内部 skill/命令各自按需加载 |

**关键差别不只是「分发」，而是「打包了什么」：**

- Skill 只能装「技能」：一个 `SKILL.md` + 参考文件/脚本，分享一个 skill = 得到「一个能力」。
- Plugin 能装「一整套」：如一个「前端评审插件」可同时带 3 个 skill + 2 个命令 + 1 个 hook + 1 个 MCP 配置。这些东西只能靠 Plugin 一起分发。

**选型规则：**

- 分发单个能力、自用为主 → skill，直接分享文件夹 / git / 软链。
- 分发一整套工具集（含命令 / hooks / MCP / 多 skill），需要团队一键启用、带版本管理 → plugin。

> 💡 补充：对应 §3.7 口诀「Plugin 解决团队配置问题」——Plugin 是把 subagent / skill / hook / MCP 打包成一份、统一分发启用的载体；单个 skill 是给人用的能力，Plugin 是给团队发的一整箱装备。

### 3.9 非交互调用（Headless）与 Agent SDK

> 一句话记忆：**交互模式是聊天窗口，非交互（`claude -p`）是函数调用；SDK 不是另一种功能，是同一引擎的编程语言封装。**

**非交互调用（headless，无头模式）**：不开对话界面，把 Claude Code 当命令执行--传入任务，自己跑完，输出结果后退出：

```bash
claude -p "分析这个仓库的性能瓶颈，输出一份报告"
```

特点：一次任务一个生命周期，跑完即退；没人点「允许」，权限要预先给好（`--allowedTools`）；输出给程序看（`--output-format json` 可拿到结构化结果：改了哪些文件、用了什么工具、花了多少 token）。

典型场景：CI 里每次 PR 自动审查代码、git hook 提交前检查、脚本里批量处理文件。

**与 Agent SDK 的关系**：不是两种功能。底层引擎只有一个，SDK（TypeScript / Python）是把 headless 的启动、传参、事件流、会话恢复包装成可 import 的库，用于在自己的应用里嵌入 agent：

```python
from claude_agent_sdk import query

async for message in query(prompt="重构这个模块", allowed_tools=["Edit", "Bash"]):
    ...  # 逐条拿到 agent 的每一步动作和输出
```

| 维度 | `claude -p`（CLI headless） | Agent SDK |
|---|---|---|
| 本质 | 同一个引擎 | 同一个引擎的库封装 |
| 调用方式 | shell 命令 / 子进程 | 代码里 import 后调用 |
| 适合场景 | 脚本、CI、一次性任务 | 构建自己的应用（机器人、编排系统、多 agent 平台） |
| 事件处理 | 文本 / JSON 流，自己解析 | 类型化的事件回调，直接写业务逻辑 |
| 多轮控制 | `--resume` 恢复会话 | 程序里原生管理会话状态 |

**选型规则**：写个脚本让 AI 干活 -> `claude -p`；写一个「里面包含 AI agent」的产品 -> SDK。

**别混淆 Anthropic API**：API 调用的是**模型本身**（只有大脑，没有手脚）；Claude Code / Agent SDK 调用的是**完整 agent**（自带读写文件、跑命令、搜索、权限管理的工具循环）。对应 §3.3 的「Worktrees / Headless 无人值守接入 CI/CD」，说的就是这套东西。

### 3.10 从零开发一个应用：SDD + Harness 实战流程

三件套落地的完整路径（以 Hify--参考 Dify 的简化版 AI Agent 平台为例）：

| 步骤 | 做什么 | 关键动作 |
|---|---|---|
| 1. 标杆调研 | 梳理业界标杆产品的功能模块 | AI 给的信息不能直接信，要验证 |
| 2. 功能取舍 | 三问裁剪法 + MoSCoW 分层 | 明确做什么、不做什么 |
| 3. 技术选型 | 让 AI 对比候选方案优劣 | 维度：开发效率、生态成熟度、SDK 支持、运维复杂度 |
| 4. 应用架构 | 模块化单体 vs 微服务方案对比 | 拿到推荐方案后继续追问：依赖关系？循环依赖风险？维护成本？ |
| 5. 代码组织 | 定义分层结构与职责边界 | 具体到 AI 能直接执行 |
| 6. 外部调用 | LLM 调用的线程、容错、超时、重试方案 | 按"慢且不稳定"设计 |
| 7-9. 部署 / 性能 / 扩展 | 部署架构、瓶颈排序、分阶段扩展路径 | 触发条件驱动，条件不到不动 |
| 10. 数据模型 | 梳理核心数据表与关系 | 只要表名和关系，不展开字段 |
| 11-12. 数据库与接口规范 | 索引、分页、错误码、行为指令 | 建表时一次性写好 |
| 13. 整合 CLAUDE.md | 所有决策合并成一份完整规范 | 从项目概述到行为指令 |

每一步都是"先写清楚（SDD），再沉淀进 CLAUDE.md（Harness）"。

前端页面需求分三层描述：**结构层**（页面长什么样、组件怎么排列）、**行为层**（用户做了什么、页面发生什么）、**细节层**（动画速度、样式微调、边界处理）。静态交互用四维度描述，动态交互用时间线描述。

### 3.11 CLAUDE.md 模板核心要点（Hify 完整规范）

归档中的 Hify CLAUDE.md 模板是一份可直接套用的完整样例，核心要点如下。

**模块化单体的四层结构**（每个业务模块统一）：

| 层 | 职责 | 禁止 |
|---|---|---|
| `web/` | 接收请求、参数校验（@Valid）、调用本模块 `api/` 接口、返回 `Result<T>` | 直接调用其他模块 `domain/`、直接操作数据库 |
| `api/` | 定义跨模块调用的 interface 和 DTO | 包含业务逻辑实现 |
| `domain/` | 业务逻辑、领域对象、事务边界（@Transactional） | 直接依赖 Mapper、依赖 web 层 |
| `infra/` | Mapper、RepositoryImpl（PO 与领域对象转换）、外部 API 客户端 | 包含业务逻辑 |

模块划分示例：`hify-provider / hify-agent / hify-chat / hify-mcp / hify-workflow / hify-knowledge / hify-common`。单向依赖不循环，共用逻辑下沉 common。

**LLM 调用规范**：

- 双线程池隔离：`llmExecutor`（非流式，CallerRunsPolicy 满载不丢任务）+ `llmStreamExecutor`（流式 SSE，AbortPolicy 超限直接拒绝、上层返回 503）。
- 三层超时保护：OkHttp connectTimeout 5s -> readTimeout 120s（仅非流式，流式必须设 0）-> `CompletableFuture.get(90s)` 总体兜底。
- 重试：普通 LLM 最多 3 次指数退避（500ms 起、最大 10s），Ollama 最多 5 次；仅网络异常和 5xx 重试，4xx 不重试。
- 熔断：20 次请求内失败率 >50%，或慢调用（>30s）占比 >80% 触发；熔断 30s 后 half-open 放 5 次探测。

**部署要点**：生产 Docker + K8s；SSE 场景 Ingress 必须配 `proxy-buffering: "off"` 和 `proxy-read-timeout: "300"`；JVM 用 `-XX:MaxRAMPercentage=75.0 -XX:+UseG1GC`。

**数据库与索引检测**：大表阈值--行数 > 500 万或数据量 > 2GB。索引检测三阶段：开发阶段 p6spy 拦截 >10ms 查询自动 EXPLAIN；CI 阶段 IndexCoverageTest 中 type=ALL 即测试失败阻断合并；生产阶段定期查 `performance_schema` 找 `sum_no_index_used > 0` 的 SQL。

**编码规范**（基于阿里巴巴 Java 开发手册，精选）：

- 命名：Service 接口不加 I 前缀、实现类加 `Impl`；表名 `t_` 前缀，PO 用 `Po` 后缀，DTO 用 `Dto`/`Request`/`Response`。
- 异常：业务异常统一抛 `BizException(ErrorCode)`，只在顶层 GlobalExceptionHandler 转换为 HTTP 响应；禁止空 catch 和 `e.printStackTrace()`。
- 日志：`@Slf4j` + 占位符格式，禁止循环体内打日志；LLM 调用必须记录 provider、model、耗时、token 数、是否命中缓存。
- 并发：线程池显式创建（禁 `Executors.newFixedThreadPool`，无界队列 OOM）；`ThreadLocal` 用完必须 `remove()`；`CompletableFuture` 必须指定线程池，禁用默认 `ForkJoinPool.commonPool()`。

**性能瓶颈优先级**（一期处理清单）：

| 级别 | 瓶颈 | 一期处理方式 |
|---|---|---|
| P0 | LLM API 延迟高（3-30s） | 线程隔离 + 熔断 + Fallback |
| P0 | 向量检索无索引全表扫描 | 建 ivfflat 索引（建表时必须创建） |
| P1 | 对话消息深分页 | 游标分页（禁止 LIMIT offset） |
| P1 | N+1 查询 | MyBatis-Plus 批量查询，禁止循环单查 |
| P2 | 连接池耗尽 | HikariCP：maximumPoolSize=20，connectionTimeout=3000ms |

### 3.12 企业级 AI Agent OS 参考工程结构

## 四、2026 年实践建议

1. **把 CLAUDE.md / AGENTS.md 当作项目的第一行代码**  
   在写业务代码之前先写上下文规范。包含项目概述、架构设计、代码组织、接口规范、行为指令。规范越具体，AI 越稳定。

2. **SDD + TDD 组合使用**  
   0→1 阶段用 SDD 收敛需求；1→2/3 阶段用 TDD 锁住行为。不要只用其中一个。

3. **Harness 四支柱补齐再放量**  
   System Prompt、Tools、Context、Subagents 都到位后，再把复杂任务交给 AI。缺一个，Loop 都容易跑偏。

4. **LLM 调用按"慢且不稳定"设计**  
   独立线程池、熔断、Fallback、分层超时是标配。Fallback 配置示例：
   ```yaml
   hify.llm.fallback:
     openai: ollama
     claude: openai
     gemini: ollama
   ```

5. **数据库规范前置**  
   主键 BIGINT 自增、通用字段、逻辑删除、索引命名、游标分页、pgvector HNSW/ivfflat 索引，在建表时一次性写好，避免后期返工。

6. **用 Plan Mode 审计划，用 Headless 跑流水线**  
   危险操作、架构改动必须人工审批计划；重复性测试、文档生成、归档整理接入 CI/CD 无人值守。

7. **保持"架构师 + 工程团队"的角色感**  
   你是架构师，AI 是工程团队。产品边界、架构决策、技术取舍由你拍板；业务代码、接口、测试由 AI 生成，你验收。按依赖程度分三层：

   | 层级 | 内容 | 你的参与 |
   |---|---|---|
   | 第一层 | 产品边界、架构决策、技术取舍、跨模块一致性 | 必须你做，AI 只给方案对比 |
   | 第二层 | 业务代码、接口、前端页面、测试用例、文档 | AI 做，你验收，每行代码都要能说清在干什么 |
   | 第三层 | 格式化、样板代码、简单重构、启动脚本、Makefile | AI 全权处理，扫一眼没问题即可 |

8. **拿到 AI 输出后做三步检查：意图 → 质量 → 边界**  
   意图错了后面白查，顺序不能反。任何一行代码你都要能说清楚它在干什么。

9. **建立正确的 AI 预期：从确定性执行转向概率性协作**  
   不要期待 AI 一次给出完美答案。把 CLI 当作主动探索的执行者，自己保留决策权和判断权：方向对不对、边界清不清、结果可不可用，由人拍板。这与"架构师 + 工程团队"的角色感一致——AI 负责生成与尝试，人负责收敛与验收。

10. **多模型交替使用，按任务分派模型能力**  
    简单、重复、格式化的工作交给轻量模型（如 MiniMax、Haiku、GPT-4o-mini）；规划、架构、视觉理解、复杂推理交给旗舰模型（如 Claude Opus / Sonnet、GPT-4o、Gemini）。同时把 token 成本纳入考量，避免用大模型做低价值任务。

## 五、开发环境与版本控制纪律

再先进的方法论也依赖稳定、可回滚的工程环境。这里记录两条最基础但最容易被忽略的纪律。

### 5.1 用 NVM / fnm 管理 Node 版本

- 把 Node 版本管理交给版本管理器（nvm、nvm-windows、fnm 均可），不要直接安装全局 Node。
- 项目根目录放 `.nvmrc` 或 `.node-version`，锁定当前项目所需 Node 版本。
- 切换项目时先 `nvm use`，从根本上避免"全局 npm 包冲突""node-sass 编译失败""某个工具要求 Node 18+ 但系统是 16"这类问题。

### 5.2 每次修改先看 diff，善用分支与撤销

- **看 diff 是必修课**：AI 或自己改完代码后，先用 `git diff` 或 IDE 的变更视图过一遍，确认改动的意图、范围、副作用，再提交。
- **功能与实验独立分支**：不要直接在主分支上试错。新功能、AI 重构、样式调整都切独立分支，失败可随时丢弃。
- **熟悉撤销工具**：`git checkout --`、`git reset`、`git revert`、`git stash` 是安全网。记不住命令就用 IDEA / WebStorm / GitKraken 等图形化工具——关键是养成"先确认再提交、先分支再大胆改"的习惯。
- **提交前自检**：哪怕是小改动，也问自己三个问题：改了什么？为什么改？能回滚吗？

## 六、常见坑与补充

1. **坑：把 AI 当搜索引擎用**  
   AI 给的信息不能直接信，要验证。尤其是技术选型、竞品分析、第三方 API 行为。

2. **坑：需求描述越短越好**  
   "做一个登录功能"会偏差。"基于 Spring Security JWT、支持 RBAC、token 过期 2h、登录失败 5 次锁定 15min" 才是 AI 能执行的 spec。

3. **坑：让 AI 一次做完大功能**  
   大项目必须分任务、分步骤、每步验证。用 `/tasks` 拆分，用 `/implement` 逐步执行。

4. **坑：不在项目里沉淀上下文**  
   每次对话都从头描述项目，上下文会断裂。用 CLAUDE.md / AGENTS.md 把约定沉淀下来。

5. **坑：忽视 LLM 的延迟和失败**  
   外部 LLM API 慢且不稳定，必须做线程隔离、熔断、重试、Fallback，不能裸调。

> 💡 补充：AI 革掉的是"写代码"，没革掉的是"想清楚要写什么"。程序员的核心竞争力 = 业务理解 × 架构判断 × 驾驭 AI 的方法论。工具会换，方法论不会。

## 一、时代背景：什么变了，什么没变

### 1.1 软件工程的变化

| 工作 | 之前 | 之后 |
|---|---|---|
| 写一个 CRUD API | 2-3 小时 | 描述清楚，AI 10 分钟完成 |
| 写单元测试 | 1-2 小时 | Harness + AI，15 分钟 80% 覆盖率 |
| 从零搭框架 | 1-2 天 | Spec Kit，当天跑通 |
| 文档整理 | 半天 | AI 读代码自动生成，30 分钟 |
| Code Review | 看语法风格 | AI 做，人专注逻辑和架构 |

代码生成的边际成本趋近于零。70% 的 GitHub 新代码由 AI 辅助生成，顶级工程师的开发速度提升 10x。

### 1.2 没变的东西——这些才是判断力所在

- **系统设计**：模块怎么划分、接口怎么定义、数据怎么流 → AI 执行，人决策
- **架构权衡**：一致性 vs 可用性、耦合 vs 扩展性 → 没有标准答案，需要判断
- **业务理解**：知道要解决什么问题，比知道怎么解决更难，也更值钱
- **调试复杂问题**：分布式竞态、内存泄漏、边界 bug → AI 猜，人验证
- **技术选型**：Spring Boot vs Quarkus、Kafka vs RocketMQ → 懂底层才能选对

> AI 工具进化的速度，远快于这些能力被替代的速度。

### 1.3 三种程序员，三种结局

- **60% 原地踏步**：用了 AI 但没改变工作方式，效率提升 10-20%
- **30% 工具依赖**：熟练用 AI 工具，能做小项目，遇到企业级复杂度就卡
- **10% 能力跃迁**：改变思维和工作方式，把 AI 用在设计 + 执行双层，能主导企业级复杂项目

差异不在于用了什么工具，在于**改没改变思维方式和工作方式**。

## 二、大项目用 AI 特别抓瞎的根因

不是 AI 不够强，是三个问题没解决：

1. **上下文断裂**：代码太多，AI 记不住全局。改了 A 模块，AI 不知道 B 模块的依赖，写出来的代码无法集成。
2. **需求表达失真**："做一个登录功能" 写出来不符合你的架构规范和安全策略。需求越模糊，偏差越大。
3. **无法增量验证**：大项目不能一次写完。每写一步怎么知道对不对？没有验证机制，错误累积，越到后面越难纠。

> 这三个问题不是"换更好的 AI"能解决的，需要方法论。

## 三、三件套方法论

### 3.1 SDD（Spec-Driven Development）—— 解决"想清楚"

**核心**：先把要做的事写清楚，再让 AI 做。**不是多一个步骤，是把"想清楚"变成 AI 能读懂的格式**。

**流程**：

1. **先写 spec**：接口定义、约束、边界
2. **Clarify**：AI 主动找模糊点，你回答，spec 更新
3. **`/tasks → /implement`**：逐任务执行，每步可验证，错误不累积

**反例（没有 SDD）**：

```
"帮我做一个 Agent 模块"   → 写了，接口不对
"要能接 Spring 的"        → 改了，和数据库层冲突
"算了我自己改吧"         → 改完，AI 下次还是不记得
```

### 3.2 Harness Engineering —— 解决"做对"

**核心**：给 AI 搭建可靠的工作环境，由四个支柱组成：

| 支柱 | 作用 | 落地形式 |
|---|---|---|
| **System Prompt** | 行为规范 | 项目级约定：编码风格、技术栈、安全规则 |
| **Tools** | 能力边界 | MCP 协议 + 自定义工具（文件、DB、API 调用） |
| **Context** | 上下文管理 | CLAUDE.md / AGENTS.md，让 AI 始终知道项目结构、依赖、进度 |
| **Subagents** | 并行分治 | 复杂任务拆子任务，多 Subagent 并行，主 Agent 协调 |

> 四支柱齐备，AI 才能可靠地在大项目里工作，不乱、不断、不出轨。

### 3.3 Loop Engineering —— 解决"AI 自动做"

**核心**：让 AI 自主跑起来，最小化人工干预。本质是**设计并控制 ReAct 循环的工程方法**。

**ReAct 循环**：

```
Thought → Action → Observation
        ↻ 循环直到任务完成
```

**三个关键机制**：

- **Hooks**：在循环每步前后插入验证、日志、条件判断（pre / post 钩子）
- **Plan Mode**：AI 先规划再执行，人工审批计划
- **Headless Mode**：无人值守运行，接入 CI/CD pipeline

**三件套分工**：

```
SDD                  → 解决"想清楚"
Harness Engineering  → 解决"做对"
Loop Engineering     → 解决"AI 自动做"
```

# 架构师和工程团队

>  不了解技术细节，就没法给出精确的任务描述。技术能力是你当好“架构师”的前提。

AI时代哪些是AI该做的，哪些是架构师该做的：
- 第一层，必须你做的。产品边界、架构决策、技术取舍、跨模块一致性。拿 Hify 来说：做不做 RAG 知识库？用微服务还是模块化单体？线程池参数设多少？这些决策只有你能做。Claude Code 可以给你方案对比（后面第 04 讲你会看到这个过程），但拍板的必须是你。

- 第二层，AI 做你验收的。业务代码、接口开发、前端页面、测试用例、文档。这是工作量的大头。有一个硬标准：任何一行代码你都要能说清楚它在干什么。说不清楚，就不能用。

- 第三层，AI 全权处理的。格式化、样板代码、简单重构、启动脚本、Makefile。扫一眼没问题就行。

认知框架：你是架构师，Claude Code 是你的工程团队。你的工作重心从写代码变成做决策。

三步检查法：拿到 AI 输出后，先查意图、再查质量、最后查边界。意图错了后面白查，这个顺序不能反。

在 AI 辅助开发里，SDD 通常指 Spec-Driven Development，规格驱动开发；TDD 指 Test-Driven Development，测试驱动开发。

简单说：

SDD 先把“要做什么、为什么、边界是什么”写清楚，再让 AI/人实现。适合0-1
TDD 先把“什么结果才算正确”写成测试，再让 AI/人实现。适合1-2/3

> SDD 解决“AI 到底该做什么”的问题，TDD 解决“AI 做得对不对”的问题。
   最好的 AI 开发流程不是 SDD 或 TDD 单独使用，而是用 SDD 收敛需求，用 TDD 锁住行为。

“三问裁剪法”。
- 第一问：没有它产品还成立吗？区分核心和边缘。模型管理、Agent 配置、对话引擎、工具集成、管理控制台，这五个砍掉任何一个产品都不成立。知识库和工作流砍掉产品能用但价值大打折扣，降级做。可视化拖拽、多租户、插件市场、计费，砍掉不影响核心链路。
- 第二问：做到什么程度够用？核心功能不做满。模型管理只做 CRUD + 连通性测试。Agent 配置只做选模型、绑工具、设提示词。对话引擎只做流式  +  多轮。知识库只支持 TXT +  固定分块。工作流只支持 JSON 配置。管理控制台能用就行不追求精美。
- 第三问：能不能一句话说清楚？Hify：一个可本地部署的 AI Agent 开发平台，支持多模型管理、Agent 配置、知识库 RAG、简版工作流、对话交互和 MCP 工具接入，面向团队内部小规模使用。

按照 MoSCoW 分层：

|层级|含义|你应该怎么做|
|---|---|---|
|**Must 必须做**|没有它产品不成立|MVP 第一版必须有|
|**Should 应该做**|重要，但可以简化|第一版做轻量版，或第二版做|
|**Could 可选做**|有价值但不紧急|有余力再做|
|**Cut 先砍掉**|对当前约束不划算|不进入 MVP|

```
Controller 只做两件事：参数校验和调用 Service。不写业务逻辑、不做数据查询、不处理事务。为什么要这么严格？因为 Claude Code 特别喜欢在 Controller 里“顺手”加逻辑，它觉得方便，但你后面测试、重构、拆分全部受影响。

Service 处理所有业务逻辑，包括事务管理、数据校验、业务规则。Service 之间可以互相调用，但只能调接口（interface），不能直接 new 实现类。

Mapper 只做数据库操作。不要在 Mapper 的 XML 里写业务逻辑（比如复杂的条件判断），那是 Service 的事。

Entity 和数据库表一一对应。DTO 是给接口用的请求 / 响应对象。Entity 和 DTO 之间要做转换，不要把 Entity 直接返回给前端——Entity 里可能有敏感字段（API Key），DTO 可以控制暴露哪些字段。
```

### 数据库规范
通用字段：
- 主键 id BIGINT 自增，禁止 UUID
- 时间字段 created_at / updated_at，DATETIME(3)
- 逻辑删除 deleted TINYINT(1)
- 禁止 NULL，空值用空字符串或 0
- 枚举用 VARCHAR(32)，不用 MySQL ENUM

索引规则：
- 命名 idx_{表名}_{字段名}
- 逻辑删除字段必须加进组合索引
- 组合索引等值列在前，范围列在后
- 多对多关联表两个方向都要索引

- 不建数据库级外键约束，应用层维护

分页规则：
- 默认用游标分页（WHERE id < lastId ORDER BY id DESC LIMIT N）
- OFFSET 分页限制最大 10000 条
- COUNT 只在第一页查，翻页不重复查

大表预判：
- message：增长最快，必须建 (conversation_id, created_at) 索引
- document_chunk：MySQL 只存元数据，向量存 pgvector

pgvector 规范：
- 向量表建在 PostgreSQL，维度固定 1536
- 必须建 HNSW 索引
- 检索必须加 LIMIT，禁止全量排序

## 数据库规范

### MySQL 通用字段约定

每张表必须包含以下字段：

```sql
id          BIGINT          NOT NULL AUTO_INCREMENT,  -- 主键，禁用 UUID
created_at  DATETIME(3)     NOT NULL DEFAULT CURRENT_TIMESTAMP(3),
updated_at  DATETIME(3)     NOT NULL DEFAULT CURRENT_TIMESTAMP(3) ON UPDATE CURRENT_TIMESTAMP(3),
deleted     TINYINT(1)      NOT NULL DEFAULT 0,       -- 逻辑删除标志
PRIMARY KEY (id)
```

- 字符集：`utf8mb4`，排序规则：`utf8mb4_unicode_ci`
- 禁用 `VARCHAR` 无长度约束，text 类 content 字段用 `MEDIUMTEXT`
- 金额用 `DECIMAL(19,4)`，禁用 `FLOAT/DOUBLE`
- 布尔用 `TINYINT(1)`，不用 `BIT`

### 索引设计原则

1. **区分度低的字段不单独建索引**（如 deleted、status 枚举），必须与高区分度字段组合
2. **组合索引遵循最左前缀**：等值查询字段在左，范围查询字段在右
3. **查询条件中含 `deleted`**，必须将 `deleted` 纳入索引
4. **每表索引不超过 5 个**（含主键），写多读少的表控制在 3 个以内
5. **禁止在 `TEXT/BLOB` 类型字段上建普通索引**，需要时建前缀索引或全文索引

```sql
-- 正确示例：conversation_id 高区分度在左，deleted 次之，created_at 范围在右
INDEX idx_conv_created (conversation_id, deleted, created_at)
```

### 大表处理策略

判断为大表的阈值：行数 > 500 万 或 数据量 > 2GB

| 场景 | 策略 |
|------|------|
| t_message | 按 conversation_id 分区，或按月归档冷数据 |
| 知识库向量表 | ivfflat 索引，lists = sqrt(行数) |
| 日志类表 | 只保留 90 天，定期 DELETE + OPTIMIZE TABLE |

### 分页查询规范

- **禁止** `LIMIT offset, size` 深分页（offset > 1000 全表扫描）
- 对话记录类使用**游标分页**：

```sql
SELECT id, role, content, created_at FROM t_message
WHERE conversation_id = ?
  AND deleted = 0
  AND (created_at < ? OR (created_at = ? AND id < ?))
ORDER BY created_at DESC, id DESC
LIMIT 20;
```

- 管理后台必须分页时，用 `WHERE id > lastId LIMIT size` 替代 offset

### pgvector 索引规范

```sql
-- 余弦相似度索引，lists 值 = sqrt(总行数)，行数 <10 万时 lists=100
CREATE INDEX idx_embedding_ivfflat ON knowledge_embedding
USING ivfflat (embedding vector_cosine_ops) WITH (lists = 100);

-- 查询时设置 probes，精度和速度平衡
SET ivfflat.probes = 10;
SELECT * FROM knowledge_embedding
ORDER BY embedding <=> '[...]'::vector LIMIT 5;
```

### 索引检测措施

**开发阶段**：启用 p6spy，拦截执行 >10ms 的查询自动 EXPLAIN，type=ALL 时打印警告日志。

**CI 阶段**：关键查询写 `IndexCoverageTest`，EXPLAIN 结果中 type=ALL 则测试失败，阻断合并。

**生产阶段**：定期查询 `performance_schema.events_statements_summary_by_digest`，找出 `sum_no_index_used > 0` 的 SQL。

```sql
SELECT digest_text, count_star AS 执行次数, sum_no_index_used AS 未用索引次数
FROM performance_schema.events_statements_summary_by_digest
WHERE sum_no_index_used > 0
ORDER BY sum_no_index_used DESC LIMIT 20;
```

## 编码规范（基于阿里巴巴 Java 开发手册）

### 命名

1. **类名用 UpperCamelCase**，方法名、变量名用 lowerCamelCase，常量用 UPPER_SNAKE_CASE，包名全小写无下划线。
2. **禁止用拼音或拼音缩写**命名，禁止单字母变量（循环变量 `i/j/k` 除外）。
3. **方法名体现动词**：查询用 `get/list/query`，修改用 `update`，删除用 `delete/remove`，新增用 `create/add`，布尔返回值用 `is/has/can`。
4. **Service 接口不加 I 前缀**，实现类加 `Impl` 后缀（`AgentService` + `AgentServiceImpl`）。
5. **数据库表名用 `t_` 前缀**，列名用 snake_case；PO 类用 `Po` 后缀，DTO 用 `Dto`/`Request`/`Response`，Mapper 用 `Mapper` 后缀。

### 异常处理

6. **禁止 catch 后 `e.printStackTrace()` 或空 catch**，必须记录日志或向上抛出。
7. **业务异常统一抛 `BizException(ErrorCode)`**，不用 RuntimeException 传递业务语义。
8. **只在顶层（GlobalExceptionHandler）处理并转换为 HTTP 响应**，中间层不捕获再包装。
9. **finally 块不写 return**，不在 finally 中抛出新异常（会吞掉原始异常）。
10. **NPE 防御**：方法返回值优先返回空集合（`Collections.emptyList()`）而非 null，接口入参用 `@NonNull`/`@Valid` 注解声明约束。

### 日志

11. **使用 SLF4J 接口 + Logback 实现**，类中用 `@Slf4j`（Lombok），禁止用 `System.out.println`。
12. **禁止在循环体内打日志**，高频路径只在异常分支记录。
13. **占位符格式 `log.info("xxx {}", var)`**，禁止字符串拼接（避免无效 toString 开销）。
14. **日志分级约定**：DEBUG=详细调试，INFO=关键业务节点，WARN=可恢复异常或配置缺失，ERROR=需人工介入的故障。生产环境 INFO 级别，日志文件按天滚动，保留 30 天。
15. **LLM 调用必须记录**：provider、model、耗时、token 数、是否命中缓存，便于成本分析。

### 并发

16. **线程池必须显式创建**（`ThreadPoolExecutor`），禁止用 `Executors.newFixedThreadPool`（无界队列 OOM）。
17. **ThreadLocal 用完必须 `remove()`**，防止线程池场景下数据泄漏。
18. **加锁粒度最小化**：只锁共享变量操作，不锁 I/O 和 LLM 调用；优先用 `ReentrantLock` 替代 `synchronized`（可设超时）。
19. **单例 Bean 的成员变量必须是线程安全的**：无状态 Service 天然安全；有状态则用 `ThreadLocal` 或局部变量，禁止用实例变量存请求上下文。
20. **`CompletableFuture` 异步调用必须指定线程池**（`supplyAsync(task, llmExecutor)`），禁止用默认 `ForkJoinPool.commonPool()`（会影响其他异步任务）。
