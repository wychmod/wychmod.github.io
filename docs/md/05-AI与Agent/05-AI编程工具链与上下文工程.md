# AI 编程工具链与上下文工程

> 预计阅读：约 25 分钟
> 前置阅读：[AI 编程三件套方法论](/md/05-AI与Agent/00-AI编程三件套方法论.md)

## 一、核心概述

这篇文档承接三件套里的 **Harness Engineering** 与 **Loop Engineering**，重点回答一个问题：怎样把 AI 编程工具配置成稳定、可复用、可验证的工程环境。

工具链不要只理解成"会用命令"。它至少包含三层：

| 层级 | 解决的问题 | 典型载体 |
|---|---|---|
| 配置层 | 机器怎样执行 | settings、config、CLI flags、权限 |
| 上下文层 | AI 怎样理解项目 | `AGENTS.md`、`CLAUDE.md`、memory、rules |
| 能力层 | AI 能调用什么 | tools、MCP、skills、hooks、subagents、plugins |

## 二、Claude Code / Codex 配置分层

配置体系本质上分两条线：**机器可执行的配置**，以及**写给 AI 看的项目说明**。

| 内容 | Claude Code 常见位置 | Codex 常见位置 | 一句话理解 |
|---|---|---|---|
| 常规设置 / 权限 / Hooks / env | `~/.claude/settings.json`、`.claude/settings.json`、`.claude/settings.local.json` | `~/.codex/config.toml`、`.codex/config.toml`、CLI flags、profile | 机器直接执行的配置 |
| MCP 服务器 | `~/.claude.json`、`.mcp.json` | MCP 配置文件或宿主配置 | 外部工具接入 |
| 项目约定 | `~/.claude/CLAUDE.md`、仓库 `CLAUDE.md` | `~/.codex/AGENTS.md`、仓库 `AGENTS.md` | 写给 AI 看的工作说明 |
| Subagents | `~/.claude/agents/`、`.claude/agents/` | subagents 能力目录或宿主配置 | 可复用的子代理 |
| 会话级临时项 | `claude --model`、`/model`、`/config key=value`、`outputStyle` | CLI 参数、当前会话设置 | 只影响当前任务 |

两个原则：

- `AGENTS.md` / `CLAUDE.md` 是软指令，不是硬开关；关键约束要靠测试、脚本、Hook 和权限兜底。
- 会话级设置适合临时试验；团队约定应该落在仓库文件里，避免只存在某个人的本机配置中。

## 三、AGENTS.md / CLAUDE.md 的职责

一份项目级上下文应该让 AI 快速知道：

- 项目做什么、不做什么。
- 技术栈、部署方式和运行命令。
- 目录结构、模块边界和命名规则。
- 代码风格、测试要求和安全红线。
- 哪些文件不能动，哪些脚本必须跑。

示例结构：

```markdown
## 项目概述
- 做什么、不做什么
- 团队规模、部署方式
- 技术栈

## 架构设计
- 应用架构
- 模块划分
- 跨模块调用规则

## 数据库规范
- 通用字段
- 索引规则
- 分页规则

## 接口规范
- RESTful 路径
- 统一响应
- 错误码

## 行为指令
- 写代码时
- 改代码时
- 不确定时
```

写这类文件时要避免抽象口号。比如"保持代码整洁"没用，"Controller 不写业务逻辑，只做参数校验并调用 Service"才可执行。

## 四、Auto-memory：自动记忆

Auto-memory 解决的是跨会话偏好和经验积累问题。它和 `CLAUDE.md` 的分工不同：

| 对比维度 | CLAUDE.md / AGENTS.md | Auto-memory |
|---|---|---|
| 谁写 | 人 | AI 自己 |
| 内容 | 指令、规则、项目约定 | 经验、偏好、纠正记录 |
| 作用域 | 用户 / 项目 / 本地覆盖 | 通常按仓库隔离 |
| 维护方式 | 人主动维护 | AI 判断是否值得写入 |

适合写入 memory 的内容：

- 用户长期偏好，例如输出风格、审查重点。
- 被用户明确纠正过的非显然做法。
- 外部系统入口，例如 issue 看板、dashboard、文档索引。
- 无法从代码或 git 历史推导出的项目事实。

不适合写入 memory 的内容：

- 代码结构和文件路径，读仓库即可得到。
- 临时任务状态，完成后就失效。
- `AGENTS.md` 已经写明的规则。
- 调试过程中一次性的修复配方。

> 💡 补充：记忆是"当时为真"的快照。再次使用前要验证当前仓库状态，发现过期就更新或删除。

## 五、Rules & paths：按范围懒加载规则

规则文件适合把项目约定拆成多个主题，并按文件范围加载。

| 类型 | 何时加载 | 适合内容 |
|---|---|---|
| 无条件规则 | 每次会话启动 | 全局风格、安全红线、通用工作流 |
| 带 `paths` 的规则 | 读取匹配文件时 | 只对某类文件或目录有意义的约定 |
| Skill | 显式调用或判定相关时 | 可复用任务流程、发布清单、参考手册 |

常见 glob 例子：

| glob | 匹配 |
|---|---|
| `**/*.ts` | 任意目录下所有 `.ts` 文件 |
| `src/**/*` | `src/` 下所有文件 |
| `*.md` | 项目根目录的 Markdown 文件 |
| `src/components/*.tsx` | 指定目录下的组件文件 |

判断规则：

- 任何任务都该知道：放根 `AGENTS.md` / `CLAUDE.md`。
- 只在碰某类文件时需要：放带 `paths` 的 rules。
- 偶尔使用的任务型流程：做成 Skill。

## 六、扩展机制速查

一句话记忆：**Subagent 解决上下文限制，Skill 解决重复流程，Hook 解决硬性门禁，MCP 解决外部系统调用，Plugin 解决团队分发。**

| 机制 | 解决什么 | 一句话理解 |
|---|---|---|
| Subagent | 上下文限制 | 大任务拆给独立子代理，各自拥有独立上下文 |
| Skill | 重复流程 | 把固定流程打包成按需加载的说明和脚本 |
| Hook | 模型不听话 | 在固定生命周期事件强制执行脚本 |
| MCP | 外部系统能力 | 让 Agent 调用数据库、浏览器、服务 API 等工具 |
| Plugin | 团队配置分发 | 把 skill、hook、MCP、subagent 打包成一套 |

### 6.1 Skill 与 Plugin 的区别

| 维度 | Skill | Plugin |
|---|---|---|
| 本质 | 单个可复用能力 | 打包与分发单位 |
| 组成 | `SKILL.md` + 辅助文件 | manifest + 多个 skill / command / hook / MCP / subagent |
| 适合 | 个人或团队共享一个流程 | 团队启用一整套工具集 |
| 加载 | 按需加载 | 启用插件后，其内部能力各自按需加载 |

选型规则：

- 只沉淀一个任务流程：用 Skill。
- 要把多项能力统一安装、启用、升级：用 Plugin。

## 七、Headless 与 Agent SDK

交互模式是聊天窗口，非交互模式是函数调用。

| 维度 | CLI Headless | Agent SDK |
|---|---|---|
| 调用方式 | shell 命令 / 子进程 | 代码里 import 后调用 |
| 适合场景 | CI、脚本、一次性批处理 | 在产品里嵌入 agent |
| 输出处理 | 文本或 JSON 流，自己解析 | 类型化事件回调 |
| 会话控制 | 通过 resume 等参数恢复 | 程序原生管理状态 |

典型用法：

```bash
claude -p "分析这个仓库的性能瓶颈，输出一份报告"
```

不要把模型 API 和 Agent SDK 混为一谈：

- 模型 API 调用的是模型本身，只有推理能力。
- Claude Code / Codex / Agent SDK 调用的是完整 agent，包含工具循环、文件读写、命令执行和权限管理。

## 八、落地清单

开始把 AI 放进真实项目之前，至少检查这些项：

- 仓库根目录有清晰的 `AGENTS.md` / `CLAUDE.md`。
- 禁止修改的目录、危险命令、验证脚本写清楚。
- 常用任务有固定流程，例如新增文档、改 API、发版、回滚。
- 测试、lint、链接检查等门禁能被命令一键执行。
- 大任务先走 Plan Mode。
- 重复性检查可接入 Hook 或 CI。
- 外部服务通过 MCP 或 SDK 暴露清晰工具边界。
- 子代理只做清晰、可回收的子任务，主代理负责整合和验收。
